# 학습목표
- 목록에서 선택한 데이터의 ID를 이용해 상세보기(Detail View)를 구현할 수 있다.
- 모달(Modal) 또는 별도 상세영역을 이용해 사용자의 탐색 흐름이 끊기지 않도록 설계할 수 있다.
- 로딩·데이터 없음·오류 상태를 포함한 인터랙션(Interaction)을 설계하고 팀 프로젝트에 적용할 수 있다.
---
# 준비물 및 수업환경
- 9주차 검색·필터·정렬 기능이 적용된 목록 화면을 준비한다.
- 각 데이터에 고유 ID가 존재하는지 확인한다.
- 4주차 와이어프레임의 상세화면 설계를 다시 확인한다.
- 공통 프로젝트 B의 여행지 탐색 서비스 파일을 준비한다.
<callout icon="💡" color="yellow_bg">
	- 10주차의 핵심은 상세화면을 하나 더 만드는 것이 아니라 목록에서 사용자가 선택한 데이터와 상세정보를 정확하게 연결하는 것이다.
	- 상세보기 이후 사용자가 다시 목록으로 돌아가거나 저장 행동을 이어갈 수 있어야 한다.
</callout>
# 1. \[이론+실습\] 목록과 상세 데이터 연결
## 1.1 상세보기(Detail View)의 역할
### 1.1.1 목록과 상세의 정보 차이
- 목록은 여러 항목을 빠르게 비교하기 위한 화면이다.
- 상세보기는 하나의 항목을 선택한 뒤 판단에 필요한 추가 정보를 확인하는 화면이다.
- 목록에 모든 정보를 넣으면 비교가 어려워지고 상세화면에 핵심 정보가 없으면 다시 목록으로 돌아가야 한다.
<table header-row="true">
<tr><td>정보</td><td>목록</td><td>상세</td></tr>
<tr><td>제목</td><td>필수</td><td>필수</td></tr>
<tr><td>대표 조건</td><td>핵심만</td><td>전체</td></tr>
<tr><td>긴 설명</td><td>요약</td><td>전체</td></tr>
<tr><td>태그</td><td>일부</td><td>전체</td></tr>
<tr><td>개인화 행동</td><td>선택</td><td>권장</td></tr>
</table>
---
## 1.2 ID로 데이터 찾기
### 1.2.1 왜 ID를 사용하는가
- 제목은 중복될 수 있지만 ID는 데이터마다 고유해야 한다.
- 목록 카드의 ID를 읽어 원본 배열에서 같은 항목을 찾을 수 있다.
- 이후 LocalStorage의 즐겨찾기 목록도 같은 ID 기준으로 연결할 수 있다.
---
### 1.2.2 find 예시
```javascript
function findItemById(items, id) {
  return items.find(item => item.id === id);
}
```
- find는 조건에 맞는 첫 번째 항목을 반환한다.
- 일치하는 항목이 없을 수 있으므로 결과가 없는 경우도 처리한다.
---
## 1.3 카드 클릭과 ID 전달
### 1.3.1 data-id 활용 예시
```javascript
const list = document.querySelector('#item-list');

list.addEventListener('click', event => {
  const card = event.target.closest('.item-card');
  if (!card) return;

  const rawId = card.dataset.id;
  const id = typeof allItems[0]?.id === 'number' ? Number(rawId) : rawId;
  openDetail(id);
});
```
- 카드 내부 이미지나 제목을 클릭해도 가장 가까운 카드 요소를 찾도록 처리할 수 있다.
- data-id는 HTML에서 문자열로 읽히므로 6주차 데이터 명세에서 정한 ID 자료형과 맞춰 변환한다.
- 수업 공통 예시는 숫자형 ID를 사용하지만 문자열 ID를 설계한 팀은 Number로 강제 변환하지 않는다.

# 2. \[이론+실습\] 상세화면과 인터랙션 설계
## 2.1 모달(Modal)과 별도 상세영역
### 2.1.1 모달이 적합한 경우
- 사용자가 현재 목록 맥락을 유지하면서 짧은 상세정보를 확인할 때 적합하다.
- 닫기 행동이 명확해야 한다.
- 모바일에서는 화면 크기와 스크롤을 함께 고려한다.
---
### 2.1.2 별도 상세화면이 적합한 경우
- 상세정보가 길거나 여러 섹션으로 구성될 때 적합하다.
- URL이나 페이지 전환을 이용할 수 있다.
- 목록으로 돌아갔을 때 기존 검색·필터 상태를 유지하는 것이 좋다.
- 별도 페이지를 사용하는 경우 URLSearchParams를 이용해 선택 ID와 필요한 탐색 상태를 쿼리스트링으로 전달할 수 있다.
```javascript
const params = new URLSearchParams({
  id: selectedId,
  keyword: currentKeyword,
  region: currentRegion
});

location.href = `detail.html?${params.toString()}`;
```
- 상세 페이지에서 URLSearchParams로 값을 다시 읽고 목록 복귀 링크에도 같은 조건을 전달하면 검색·필터 상태를 복원할 수 있다.
- 상태 항목이 많아지면 URL에 반드시 필요한 값만 전달하고 나머지는 별도 상태 관리 방식으로 정리한다.
---
## 2.2 상세 렌더링 함수
### 2.2.1 상세 열기와 출력 예시
```javascript
function openDetail(id) {
  const item = findItemById(allItems, id);

  if (!item) {
    renderDetailError();
    return;
  }

  renderDetail(item);
}

function renderDetail(item) {
  const detail = document.querySelector('#detail');
  const displayTitle = item.title ?? item.name;

  detail.innerHTML = `
    <h2>${displayTitle}</h2>
    <p>${item.region ?? item.category ?? ''}</p>
    <p>${item.description ?? ''}</p>
  `;
}

function renderDetailError() {
  const detail = document.querySelector('#detail');
  detail.innerHTML = '<p>항목을 찾을 수 없습니다</p>';
}
```
- openDetail은 선택 ID로 데이터를 찾고 성공과 실패를 분기한다.
- 공통 프로젝트 B는 name을 사용할 수 있고 팀 프로젝트는 6주차 명세에 따라 title을 사용할 수 있으므로 필드명 규칙을 프로젝트 안에서 일관되게 유지한다.
- 실제 팀 프로젝트에서는 title 또는 name 중 하나를 대표 제목 필드로 정해 통일하는 것을 권장한다.
---
## 2.3 사용자 피드백(User Feedback)
### 2.3.1 행동 결과를 알려주기
- 사용자가 상세보기를 열면 선택한 항목이 명확하게 보여야 한다.
- 즐겨찾기를 눌렀다면 저장 여부가 아이콘이나 문구로 바로 바뀌어야 한다.
- 닫기 버튼을 눌렀다면 목록으로 돌아갔다는 것을 자연스럽게 인식할 수 있어야 한다.
- 클릭했는데 아무 변화가 없는 상태를 피한다.
---
### 2.3.2 마이크로 인터랙션(Microinteraction)
- 작은 상태 변화로 사용자 행동의 결과를 알려주는 인터랙션을 의미한다.
- 즐겨찾기 아이콘 채우기, 선택된 필터 표시, 저장 완료 문구 등이 예시다.
- 애니메이션 자체보다 상태 변화가 이해되는지가 중요하다.
---
# 3. \[실습\] 공통 프로젝트 B와 팀 프로젝트 상세보기 구현
## 3.1 공통 프로젝트 B 상세보기
### 3.1.1 구현 순서
- 여행지 카드에 ID를 연결한다.
- 카드 클릭 시 선택 ID를 읽는다.
- 원본 데이터에서 같은 ID의 장소를 찾는다.
- 이름·지역·테마·설명·평점 등 상세정보를 출력한다.
- 상세영역 닫기 또는 목록 복귀 기능을 구현한다.
---
### 3.1.2 목록 상태 유지
- 상세보기를 닫았을 때 검색어와 필터 조건이 그대로 남아 있는지 확인한다.
- 사용자가 다시 처음부터 검색하지 않도록 한다.
- 스크롤 위치 유지 여부도 사용자 경험 관점에서 검토할 수 있다.
---
## 3.2 상세화면에서 다음 행동 연결
### 3.2.1 단순 정보 확인으로 끝내지 않기
- 즐겨찾기
- 관련 항목 다시 탐색
- 외부 공식 페이지 이동
- 위치 확인
- 프로젝트 특화 행동
- 상세화면에서 핵심 사용자 목표와 연결되는 다음 행동을 최소 하나 제공한다.
---
### 3.2.2 프로젝트별 예시

<tr><td>프로젝트</td><td>상세에서 확인할 정보</td><td>다음 행동</td></tr>
<tr><td>공모전</td><td>대상, 마감일, 시상, 제출물</td><td>관심 공모전 저장</td></tr>
<tr><td>자격증</td><td>시험일, 과목, 난이도, 관련 직무</td><td>준비 목록 저장</td></tr>
<tr><td>식물</td><td>빛, 물주기, 난이도, 주의사항</td><td>관심 식물 저장</td></tr>
</table>

## 3.3 예외 상태(Error State)
### 3.3.1 데이터가 없는 경우
- 선택한 ID가 존재하지 않으면 상세정보를 임의로 만들지 않는다.
- 항목을 찾을 수 없다는 안내를 보여준다.
- 목록으로 돌아갈 수 있는 행동을 제공한다.
---
### 3.3.2 이미지 또는 선택 필드 누락
- 이미지가 없으면 기본 이미지를 사용하거나 이미지 영역을 숨긴다.
- 선택 필드가 없으면 빈 텍스트를 그대로 노출하지 않는다.
- 필수 필드 누락은 데이터 명세 오류로 기록해 수정한다.
---
## 3.4 심화 트랙｜상세 데이터 추가 조회
### 3.4.1 로딩 상태(Loading State)
- API나 DB에서 상세정보를 기다리는 동안 로딩 중임을 표시한다.
- 버튼을 여러 번 누르지 않도록 필요한 경우 일시적으로 상태를 제어한다.
---
### 3.4.2 실패 상태
- 네트워크 오류인지 데이터 없음인지 구분할 수 있으면 각각 다른 안내를 제공한다.
- 다시 시도 행동을 제공할 수 있다.
- 최소 기본 정보는 JSON 데이터로 유지하는 방식도 고려한다.
---
## 3.5 접근성(Accessibility) 기본 점검
### 3.5.1 모달을 사용할 때
- 닫기 버튼에 명확한 레이블을 제공한다.
- 키보드로 닫기와 주요 조작이 가능한지 확인한다.
- 배경과 모달 내용이 시각적으로 구분되는지 확인한다.
- 이미지에는 적절한 대체 텍스트를 제공한다.
<callout icon="📌" color="blue_bg">
	- 접근성(Accessibility)은 특정 사용자만을 위한 추가 기능이 아니라 다양한 사용자가 서비스를 이해하고 조작할 수 있게 만드는 기본 품질 기준이다.
	- 참고 자료｜[W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/)
</callout>

# 10주차 핵심 정리
- 상세보기는 선택한 데이터의 ID를 기준으로 목록과 연결한다.
- 목록은 비교, 상세는 판단에 필요한 추가 정보 제공에 집중한다.
- 상세보기 이후 다음 행동과 목록 복귀 흐름을 함께 설계한다.
- 사용자 행동에는 즉각적인 피드백이 필요하다.
- 심화 트랙은 로딩·오류·데이터 없음 상태까지 포함해 외부 연결 실패를 설계한다.
