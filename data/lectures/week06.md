# 학습목표
- 서비스 화면과 기능에 필요한 데이터를 JSON 구조로 설계할 수 있다.
- 데이터 명세(Data Specification)를 작성하고 필드(Field), 자료형(Data Type), 식별자(Identifier, ID)의 역할을 설명할 수 있다.
- 검색·필터·정렬·상세보기·개인화 기능에 필요한 데이터 구조를 미리 검증할 수 있다.

# 1. \[이론+실습\] JSON과 구조화 데이터
## 1.1 JSON의 역할
### 1.1.1 이번 프로젝트에서 JSON이 맡는 역할
- JSON은 서비스가 공통으로 제공하는 기본 데이터를 저장한다.
- 팀원이 같은 파일을 GitHub로 공유할 수 있다.
- 브라우저가 파일을 읽어 목록·검색·필터·상세화면에 사용할 수 있다.
- 사용자 개인 상태는 JSON 파일이 아니라 LocalStorage에서 분리해 관리한다.
---
### 1.1.2 JSON과 LocalStorage 다시 구분하기
<table header-row="true">
<tr><td>구분</td><td>JSON</td><td>LocalStorage</td></tr>
<tr><td>주요 역할</td><td>서비스 기본 데이터</td><td>사용자 개인 상태</td></tr>
<tr><td>팀원 공유</td><td>가능</td><td>불가</td></tr>
<tr><td>GitHub 포함</td><td>가능</td><td>불가</td></tr>
<tr><td>예시</td><td>장학금명, 조건, 마감일</td><td>즐겨찾기한 장학금 ID</td></tr>
</table>
---
## 1.2 JSON 기본 구조
### 1.2.1 객체와 배열
```json
[
  {
    "id": 1,
    "title": "웹서비스 기획 특강",
    "category": "기획",
    "target": "1~2학년",
    "deadline": "2026-09-30"
  },
  {
    "id": 2,
    "title": "프론트엔드 입문 특강",
    "category": "개발",
    "target": "전체",
    "deadline": "2026-10-10"
  }
]
```
- 배열은 여러 데이터 항목을 묶는다.
- 객체는 한 항목의 여러 속성을 묶는다.
- 각 속성은 키와 값으로 구성된다.
---
### 1.2.2 사용할 수 있는 값의 형태
- 문자열(String)은 제목, 카테고리, 설명처럼 문자 데이터를 표현한다.
- 숫자(Number)는 가격, 점수, 난이도 수치처럼 계산이나 정렬에 사용할 수 있다.
- 불리언(Boolean)은 가능/불가능처럼 두 상태를 표현한다.
- 배열(Array)은 태그처럼 여러 값을 한 필드에 담을 때 사용한다.
- null은 값이 없음을 명시적으로 표현할 때 사용한다.
---
## 1.3 JSON 문법 오류 찾기
### 1.3.1 자주 발생하는 오류
- 키와 문자열 값에 큰따옴표가 빠진 경우
- 마지막 항목 뒤에 불필요한 쉼표가 있는 경우
- 중괄호와 대괄호가 닫히지 않은 경우
- 같은 의미의 필드에 서로 다른 자료형을 섞은 경우
- 같은 필드를 팀원마다 다른 이름으로 작성한 경우
---
### 1.3.2 실습｜오류 JSON 수정
- 아래 오류 JSON을 복사해 errors.json으로 저장한 뒤 문법 오류와 구조 불일치를 직접 수정한다.
```json
[
  {
    "id": 1,
    "title": "UX 기초 특강",
    "category": "기획",
    "deadline": "2026-10-10",
  },
  {
    "id": "2",
    "title": "프론트엔드 특강",
    "category": "개발",
    "deadline": "10월 20일"
  },
  {
    "id": 3,
    "title": "포트폴리오 특강",
    "categoryName": "취업",
    "deadline": "2026-11-01"
  }
]
```
- 첫 번째 데이터의 마지막 속성 뒤 불필요한 쉼표를 제거한다.
- id의 자료형을 한 가지 규칙으로 통일한다.
- category와 categoryName처럼 같은 의미의 필드명을 통일한다.
- 날짜 형식을 하나의 규칙으로 통일한다.
- 수정 후 데이터 3건이 같은 필드 구조와 자료형을 사용하는지 확인한다.

# 2. \[이론+실습\] 데이터 명세와 필드 설계
## 2.1 데이터 명세(Data Specification)
### 2.1.1 데이터 명세에 포함할 항목
- 필드명
- 의미
- 자료형
- 필수 여부
- 예시값
- 사용 화면
- 검색·필터·정렬 사용 여부
<table header-row="true">
<tr><td>필드명</td><td>의미</td><td>자료형</td><td>필수</td><td>사용 목적</td></tr>
<tr><td>id</td><td>항목 식별자</td><td>Number</td><td>필수</td><td>상세보기·즐겨찾기 연결</td></tr>
<tr><td>title</td><td>제목</td><td>String</td><td>필수</td><td>목록·검색</td></tr>
<tr><td>category</td><td>분류</td><td>String</td><td>필수</td><td>필터</td></tr>
<tr><td>deadline</td><td>마감일</td><td>String</td><td>선택</td><td>정렬·상세</td></tr>
</table>
---
## 2.2 식별자(Identifier, ID)
### 2.2.1 ID가 필요한 이유
- 제목이 같아도 서로 다른 데이터일 수 있다.
- 목록에서 클릭한 항목을 상세 데이터와 연결할 때 ID를 사용할 수 있다.
- LocalStorage에는 전체 객체보다 ID만 저장해 원본 데이터와 연결하는 방식이 안정적이다.
---
### 2.2.2 좋은 ID 규칙
- 데이터마다 중복되지 않는다.
- 한 번 정한 ID를 임의로 바꾸지 않는다.
- 화면에 보이는 순서와 ID를 같은 개념으로 생각하지 않는다.
- 데이터 삭제 후 기존 ID를 재사용하지 않는 편이 안전하다.
---
## 2.3 검색·필터·정렬을 위한 필드
### 2.3.1 검색 필드
- 제목과 설명처럼 사용자가 입력한 단어와 비교할 정보가 필요하다.
- 검색 대상 필드를 미리 정해두면 구현 기준이 명확해진다.
---
### 2.3.2 필터 필드
- category, target, region처럼 값의 종류가 일정해야 한다.
- 팀원마다 서울, 서울시, 서울특별시처럼 다른 표현을 쓰면 필터 결과가 불안정해진다.
- 필터에 사용할 값은 가능한 한 목록을 먼저 정한다.
---
### 2.3.3 정렬 필드
- 날짜, 가격, 점수처럼 순서를 비교할 수 있는 데이터가 필요하다.
- 화면에 보이는 날짜 표현과 실제 정렬에 사용하기 좋은 데이터 형식을 구분할 수 있다.
---
## 2.4 데이터 정합성(Data Consistency)
### 2.4.1 같은 의미는 같은 규칙으로 작성하기
- 날짜 형식을 통일한다.
- 카테고리 이름을 통일한다.
- 불리언 값은 true/false로 통일한다.
- 빈 값 표현 방법을 통일한다.
- 이미지 경로 규칙을 통일한다.
---
### 2.4.2 좋지 않은 예
```json
[
  { "category": "개발", "deadline": "2026-09-20" },
  { "category": "개발분야", "deadline": "9월 25일" },
  { "category": "Development", "deadline": "2026/10/01" }
]
```
- 사람이 보기에는 비슷해도 JavaScript가 조건을 비교할 때 서로 다른 값으로 처리될 수 있다.
---
# 3. \[실습\] 공통 프로젝트 A와 팀 데이터셋 제작

- title
- category
- year
- rating
- tags
- image
- description
- 최소 8개 이상의 의미 있는 필드를 구성한다.

## 3.2 팀 프로젝트 데이터 명세 작성
### 3.2.1 화면에서 필드 찾기
- 4주차 와이어프레임의 모든 텍스트와 상태를 확인한다.
- JSON에서 와야 하는 기본 데이터를 표시한다.
- LocalStorage에서 와야 하는 사용자 상태는 제외해 별도 목록으로 작성한다.
- 검색·필터·정렬 기능과 연결되는 필드를 표시한다.
---
### 3.2.2 데이터 규모 기준
- 최종 프로젝트는 기본 데이터 30건 이상을 목표로 한다.
- 의미 있는 필드는 최소 8개를 설계하고 8\~10개 정도를 권장한다.
- 모든 데이터가 완전히 같은 내용이 아니라 필터와 정렬을 시험할 수 있게 값의 분포를 다양하게 만든다.
- 빈 결과가 나오는 조건도 테스트할 수 있게 구성한다.
---
## 3.3 샘플 JSON 작성
### 3.3.1 먼저 5\~10건으로 검증하기
- 처음부터 30건을 모두 작성하지 않는다.
- 5\~10건으로 구조와 기능 가능성을 먼저 확인한다.
- 필드 구조가 확정된 뒤 데이터 수를 늘린다.
---
### 3.3.2 샘플 데이터 검수
- 모든 객체에 필수 필드가 있는가
- 같은 필드는 같은 자료형을 사용하는가
- ID가 중복되지 않는가
- 필터 값 표현이 통일되어 있는가
- 검색 결과가 여러 건과 0건 모두 나올 수 있는가
- 정렬 결과를 확인할 값이 충분히 다른가
---
## 3.4 심화 트랙｜외부 데이터 대응 구조
### 3.4.1 내부 데이터 모델(Data Model) 유지
- 외부 API의 필드명을 그대로 화면 전체에서 사용하지 않는 편이 좋다.
- 외부 데이터를 우리 프로젝트 내부 구조로 변환하면 화면 코드가 데이터 출처에 덜 의존한다.
- 예를 들어 외부 API의 name, itemName, titleText가 무엇이든 내부에서는 title로 통일할 수 있다.
---
### 3.4.2 대체 데이터 준비
- API 호출이 실패해도 화면 개발을 계속할 수 있도록 같은 구조의 JSON 샘플을 유지한다.
- 클라우드 DB를 사용할 팀도 초기 개발용 JSON을 유지한다.
---
# 6주차 핵심 정리
- JSON은 서비스 공통 기본 데이터를 표현한다.
- 데이터 명세는 어떤 필드가 왜 필요한지 팀이 합의하는 문서다.
- 검색·필터·정렬 기능은 데이터 설계 단계에서 이미 절반이 결정된다.
- ID는 목록·상세·LocalStorage 상태를 연결하는 중요한 기준이다.
- 데이터 정합성이 낮으면 같은 기능도 예측하지 못한 결과를 만들 수 있다.
