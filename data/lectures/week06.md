# 1. JSON과 구조화 데이터
## 1.1 JSON의 역할
### 1.1.1 이번 프로젝트에서 JSON이 맡는 역할
JSON(JavaScript Object Notation)은 서비스가 모든 사용자에게 공통으로 제공하는 기본 데이터를 저장하는 원본 데이터셋으로 사용. 팀원이 같은 파일을 GitHub로 공유할 수 있고, 브라우저는 이 데이터를 읽어 목록·검색·필터·정렬·상세화면에 활용
- 즐겨찾기나 최근 본 항목처럼 사용자마다 달라지는 상태는 JSON에 섞지 않고 LocalStorage로 분리해 관리

## 1.2 JSON 기본 구조
### 1.2.1 객체와 배열
```json
[
  {
    "id": 1,
    "title": "웹서비스 기획 특강",
    "category": "기획",
    "target": "1~2학년",
    "deadline": "2026-09-30"
  },
  {
    "id": 2,
    "title": "프론트엔드 입문 특강",
    "category": "개발",
    "target": "전체",
    "deadline": "2026-10-10"
  }
]
```
- 배열은 여러 데이터 항목을 묶음
- 객체는 한 항목의 여러 속성을 묶음
- 각 속성은 키와 값으로 구성됨
- 5주차 3.3에서 본 JavaScript 배열·객체와 같은 구조이며, 파일로 저장하기 위한 문법만 조금 더 엄격함(1.2.3 참고)
---
### 1.2.2 사용할 수 있는 값의 형태
JSON에서 자료형을 구분하는 이유는 문법 시험을 위한 것이 아니라 화면에 표시할지, 조건으로 비교할지, 계산·정렬할지에 따라 데이터의 역할이 달라지기 때문으로 같은 의미의 필드는 데이터마다 같은 자료형을 유지해야 이후 기능이 안정적으로 동작
- 문자열(String)은 제목, 카테고리, 설명처럼 문자 데이터를 표현
- 숫자(Number)는 가격, 점수, 난이도 수치처럼 계산이나 정렬에 사용할 수 있음
- 불리언(Boolean)은 가능/불가능처럼 두 상태를 표현
- 배열(Array)은 태그처럼 여러 값을 한 필드에 담을 때 사용
- null은 값이 없음을 명시적으로 표현할 때 사용
- 4주차 매핑 표의 “지정 값(quiet·normal·talkable)”처럼 정해진 목록 중 하나만 허용하는 필드는 자료형은 문자열이지만 허용값 목록을 함께 관리(2.3.2 참고)
---

#### 파일 저장 규칙
- 5주차 2.1.2 폴더 구조의 `data/` 폴더에 저장하고 `js/app.js`에서는 배열을 제거하지 않고 그대로 둠(이후 주차에 fetch로 교체)
- 파일명은 영문 소문자로 작성하며, 이후 주차 예시 코드는 `data/items.json`을 기준으로 함. 팀 파일명을 다르게 정했다면 이후 주차에서 경로만 바꿔 읽음
- 파일 인코딩은 UTF-8로 저장해야 한글 값이 깨지지 않음(VS Code 기본값)
- 저장 후 GitHub에 커밋해 팀원이 같은 파일을 보도록 함
<callout icon="📌" color="blue_bg">
	VS Code는 `.json` 파일을 열면 문법 오류 위치에 빨간 밑줄을 표시하므로, 파일을 저장한 뒤 밑줄이 없는지 먼저 확인하면 이후 주차 fetch 단계에서 원인을 찾기 어려운 오류를 미리 막을 수 있음
</callout>

### <span color="blue">1.3.2 🖇️ 실습｜오류 JSON 수정</span>
#### 실습 절차
- 아래 오류 JSON을 복사해 `data/errors.json`으로 저장하고 VS Code의 빨간 밑줄 위치를 먼저 확인
- 문법 오류를 고쳐 밑줄이 사라지게 한 뒤, 밑줄이 없는데도 남아 있는 구조 오류를 찾음
- 수정한 파일을 팀원과 비교해 서로 다른 규칙으로 고치지 않았는지 확인
```json

  {
    "id": 1,
```

## 2.2 식별자(Identifier, ID)
### 2.2.1 ID가 필요한 이유
제목이나 이름은 중복될 수 있지만 ID는 데이터 한 건을 다른 항목과 구분하는 고유 식별자로 사용. 목록에서 사용자가 선택한 항목을 상세 데이터와 연결하거나 LocalStorage의 즐겨찾기 상태를 원본 데이터와 다시 연결할 때 같은 ID를 기준으로 처리하면 구조가 안정적
---
### 2.2.2 좋은 ID 규칙
- 데이터마다 중복되지 않음
- 한 번 정한 ID를 임의로 바꾸지 않음
- 화면에 보이는 순서와 ID를 같은 개념으로 생각하지 않음
- 데이터 삭제 후 기존 ID를 재사용하지 않는 편이 안전함
- 5주차에 HTML 카드의 `data-id` 속성에 넣은 값과 같은 값을 사용
<callout icon="⚠️" color="yellow_bg">
	JSON의 id를 숫자로 정해도 HTML의 `data-id` 속성으로 나가면 문자열 `"3"`이 됨. 이후 주차 상세 연결에서 `3 === "3"`은 거짓이므로 비교 전에 `Number()`로 변환하거나 처음부터 문자열로 통일해야 함. 어느 쪽으로 할지 이번 주차 명세서의 ID 규칙에 함께 기록(5주차 2.3.5 typeof 확인 항목과 연결)
</callout>
---
## 2.3 검색·필터·정렬을 위한 필드
### 2.3.1 검색 필드
- 제목과 설명처럼 사용자가 입력한 단어와 비교할 정보가 필요함
- 검색 대상 필드를 미리 정해두면 구현 기준이 명확해짐
- 5주차 4.2.2에서 “이 값을 어느 항목과 비교할지” 정한 결과가 검색 필드가 됨
---
### 2.3.2 필터 필드
- category, target, region처럼 값의 종류가 일정해야 함
- 팀원마다 서울, 서울시, 서울특별시처럼 다른 표현을 쓰면 필터 결과가 불안정해짐
- 필터에 사용할 값은 가능한 한 목록을 먼저 정하고, 5주차 4.2.1 필터 버튼에 사용한 값과 같은 표기를 사용
- 참·거짓으로 답할 수 있는 조건(콘센트 유무 등)은 문자열 “있음/없음” 대신 불리언 true/false로 저장해야 이후 주차 조건 비교가 단순해짐
---
### 2.3.3 정렬 필드
- 날짜, 가격, 점수처럼 순서를 비교할 수 있는 데이터가 필요함
- 화면에 보이는 날짜 표현과 실제 정렬에 사용하기 좋은 데이터 형식을 구분할 수 있음
> <span color="gray">예시) 화면에는 “오후 10시”로 보여도 데이터에는 </span><span color="gray">`"22:00"`</span><span color="gray">으로 저장해야 문자열 비교만으로 정렬이 가능하며, 표시 형식은 이후 주차 렌더링 함수에서 바꿈</span>
---
## 2.4 데이터 정합성(Data Consistency)
### 2.4.1 같은 의미는 같은 규칙으로 작성하기
- 날짜 형식을 통일(`YYYY-MM-DD`)
- 시간 형식을 통일(`HH:MM` 24시 표기)
- 카테고리·허용값 이름을 통일
- 불리언 값은 true/false로 통일
- 빈 값 표현 방법을 통일(null 또는 빈 문자열 중 하나)
- 이미지 경로 규칙을 통일(`./asset/파일명.jpg`, 파일명은 영문 소문자)
---
### 2.4.2 좋지 않은 예
```json
[
  { "category": "개발", "deadline": "2026-09-20" },
  { "category": "개발분야", "deadline": "9월 25일" },
  { "category": "Development", "deadline": "2026/10/01" }
]
```
- 사람이 보기에는 비슷해도 JavaScript가 조건을 비교할 때 서로 다른 값으로 처리될 수 있음
---

## 3.1 데이터 제작 순서
이번 주차 데이터셋은 아래 순서로 제작하며, 단계마다 자세한 방법은 괄호 안의 항목에서 확인
1. 5주차 HTML 카드와 화면 명세에서 필요한 필드·이미지 목록 확인(아래 요청문, 3.2)
2. 데이터 명세서에 2.1.1의 7개 항목(필드명·의미·자료형·필수 여부·예시값·사용 화면·검색·필터·정렬 사용 여부) 기록(2.1, 3.4)
3. 팀에 맞는 데이터 확보 방법을 선택하고 출처·라이선스·생성 방식을 기록(3.0, 3.1.1)
4. 원본 자료를 프로젝트에서 사용할 필드명과 값 규칙으로 변환(3.1.1 ①·⑤)

#### ④ 목록 이미지 준비

## <span color="blue">3.5 🖇️ 실습｜샘플 JSON 작성과 검수</span>
### 3.5.1 먼저 5\~10건으로 검증하기
- 처음부터 300건을 모두 작성하지 않음
- 5주차 4.4.1 배열의 2\~3건을 1.2.3 규칙(키 큰따옴표, 마지막 쉼표·주석·`const` 제거)대로 JSON 파일로 옮기는 것에서 시작
- 5\~10건으로 구조와 기능 가능성을 먼저 확인
- 필드 구조가 확정된 뒤 데이터 수를 늘림
#### 실습 절차
- `data/` 폴더에 팀 JSON 파일을 만들고 5주차 배열 2\~3건을 먼저 옮김
- VS Code 밑줄과 브라우저 직접 열기로 문법 오류가 없는지 확인(1.3.1 문법 오류)
- 밑줄이 없어도 필드명·자료형·표기가 건마다 다른 구조 오류가 없는지 3.5.2 검수로 확인(1.3.1 구조 오류)
- 명세서 기준으로 5\~10건까지 늘리되 필터 값·정렬 값의 분포를 다르게 작성(2.3)
- 조건을 겹쳤을 때 결과가 0건이 되는 조합을 하나 이상 만들어 기록(2.3)
- 파일을 GitHub에 커밋하고 팀원이 같은 파일을 열어 확인
- 최종 300건까지 누가 어떤 출처에서 어떻게 수집할지 계획을 작성

## \[옵션\] 심화 트랙 준비
### 내부 데이터 모델(Data Model) 유지
- 외부 API의 필드명을 그대로 화면 전체에서 사용하지 않는 편이 좋음
- 외부 데이터를 우리 프로젝트 내부 구조로 변환하면 화면 코드가 데이터 출처에 덜 의존함
- 예를 들어 외부 API의 name, itemName, titleText가 무엇이든 내부에서는 title로 통일할 수 있음
### 대체 데이터 준비
- API 호출이 실패해도 화면 개발을 계속할 수 있도록 같은 구조의 JSON 샘플을 유지
- 클라우드 DB를 사용할 팀도 초기 개발용 JSON을 유지
- 심화 트랙을 검토 중인 팀은 외부 데이터 필드 → 내부 필드 대응표를 이번 주차 명세서에 한 열로 추가

## 3.7 핵심 정리
- JSON은 서비스 공통 기본 데이터를 표현하며 사용자 개인 상태는 LocalStorage로 분리
- 5주차 배열과 JSON은 같은 구조이지만 파일 문법이 더 엄격하므로 1.2.3 규칙대로 옮김
- 데이터 명세는 어떤 필드가 왜 필요한지 팀이 합의하는 문서이며 5주차 인계 정리표를 그대로 확장한 것임
- 검색·필터·정렬 기능은 데이터 설계 단계에서 이미 절반이 결정
- ID는 목록·상세·LocalStorage 상태를 연결하는 기준이며 `data-id`와의 자료형 차이를 미리 정해 둠
- 데이터 정합성이 낮으면 같은 기능도 예측하지 못한 결과를 만들며, 구조 오류는 파일이 열리기 때문에 검수로만 발견할 수 있음
