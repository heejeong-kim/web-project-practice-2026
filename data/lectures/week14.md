# 1. \[이론+실습\] 최종 개선과 품질 점검

- 데이터가 잘못 표시되는 문제를 다음 우선순위로 본다.
- 사용자가 기능을 찾기 어려운 사용성 문제를 개선한다.
- 글자 간격이나 장식처럼 핵심 흐름에 영향이 작은 문제는 마지막에 처리한다.

### 1.2.2 역할을 나눠 점검하기

- 한 사람은 데이터와 LocalStorage 상태를 확인한다.

---
## 1.3 반응형 웹(Responsive Web) 최종 점검
### 1.3.1 모바일에서 확인할 것
- 검색창과 필터가 화면 밖으로 나가지 않는가
- 카드가 지나치게 좁아지지 않는가
- 버튼을 손가락으로 누르기 어려울 정도로 작지 않은가
- 상세보기 모달이 화면보다 커지지 않는가
- 긴 제목이 레이아웃을 깨지 않는가
- 결과 없음 문구와 주요 행동이 잘 보이는가
---
### 1.3.2 데스크톱에서 확인할 것
- 콘텐츠가 지나치게 넓게 퍼지지 않는가
- 목록과 상세정보의 시각적 위계가 명확한가
- 필터와 결과 영역의 관계가 이해되는가
- 빈 공간과 카드 배치가 일관적인가
---
## 1.4 콘텐츠와 데이터 최종 검수
### 1.4.1 데이터 확인
- 최종 데이터 수가 프로젝트 기준을 충족하는가
- ID 중복이 없는가
- 카테고리 값이 통일되어 있는가
- 날짜와 숫자 형식이 통일되어 있는가
- 이미지 경로가 모두 정상인가
- 테스트용 임시 데이터가 남아 있지 않은가
---
### 1.4.2 문구 확인
- 개발 중 임시 문구가 남아 있지 않은가
- 버튼 이름이 화면마다 다르게 쓰이지 않는가
- 결과 없음과 오류 문구에 다음 행동이 포함되어 있는가
- 실제 개인정보나 불필요한 민감 정보가 들어 있지 않은가
---
# 2. \[이론+실습\] 실제 배포와 운영 환경 점검
## 2.1 배포(Deployment)
### 2.1.1 배포의 의미
- 배포는 내 컴퓨터에서만 실행되던 프로젝트를 다른 사용자가 인터넷 주소로 접속할 수 있게 만드는 과정이다.
- 수업 프로젝트도 실제 URL에서 실행해봐야 파일 경로와 브라우저 저장 상태 문제를 발견할 수 있다.
---
## 2.2 정적 호스팅(Static Hosting)
### 2.2.1 표준 프로젝트 폴더 구조
```plain text
project/
├─ index.html
├─ css/
│  └─ style.css
├─ js/
│  ├─ app.js
│  ├─ storage.js
│  └─ api.js
├─ data/
│  └─ items.json
├─ images/
└─ README.md
```
- 7주차부터 사용하는 기본 JSON 경로는 ./data/items.json 형식으로 통일한다.
- 팀 프로젝트에서 파일명이 다르더라도 HTML, JavaScript, data, images의 상대 경로 규칙을 문서로 남긴다.
- 로컬 서버와 배포 서버에서 같은 상대 경로가 동작하도록 루트 기준 절대경로보다 상대경로 사용을 우선한다.
---
### 2.2.2 필수 트랙 배포 후보
- GitHub Pages
- Netlify
- Vercel
- 순수 HTML·CSS·JavaScript와 JSON 파일은 정적 호스팅으로 배포할 수 있다.
- 팀은 한 가지 방식을 선택해 실제 URL을 만든다.
---
### 2.2.3 GitHub Pages 배포 기본 흐름
- 프로젝트 파일을 GitHub 저장소에 올린다.
- 저장소 설정에서 Pages 배포를 활성화한다.
- 배포할 브랜치와 폴더를 선택한다.
- 생성된 주소에서 프로젝트를 연다.
- 팀원이 아닌 다른 기기에서도 접속한다.
---
## 2.3 배포 후 반드시 다시 확인할 것
### 2.3.1 파일 경로
- JSON 파일이 정상적으로 불러와지는가
- 이미지가 정상적으로 보이는가
- 대소문자가 다른 파일명 때문에 오류가 나지 않는가
- 상대 경로가 배포 환경에서도 맞는가
---
### 2.3.2 LocalStorage
- 배포 URL은 로컬 개발 주소와 다른 저장 공간을 사용한다.
- 배포 직후에는 즐겨찾기와 최근 본 항목이 비어 있을 수 있다.
- 발표 전에 배포 URL에서 필요한 시연 상태를 다시 준비한다.
---
## 2.4 심화 트랙｜배포 환경(Production Environment)
### 2.4.1 API 팀 점검
- 배포 주소에서 API 호출이 허용되는가
- API 키가 공개 저장소에 노출되어 있지 않은가
- 호출 실패 시 오류 상태가 정상적으로 보이는가
- 호출 제한을 초과했을 때 서비스가 완전히 멈추지 않는가
---
### 2.4.2 클라우드 DB 팀 점검
- 배포 주소에서 데이터 조회가 가능한가
- 필요한 쓰기 기능이 정상 동작하는가
- 다른 브라우저에서 같은 공유 데이터가 보이는가
- 보안 규칙(Security Rules)이 지나치게 열려 있지 않은가
- 테스트용 데이터와 실제 시연용 데이터를 구분했는가
---
### 2.4.3 환경 변수(Environment Variable)
- 배포 서비스에서 별도로 관리해야 하는 설정값이 있는지 확인한다.
- 비밀 키를 HTML이나 JavaScript에 직접 넣지 않는다.
- 프론트엔드 공개 사용을 전제로 한 키와 서버에서만 사용해야 하는 비밀 키를 구분한다.
---

# 4. \[실습\] 최종 리허설과 제출물 정리
## 4.1 최종 리허설
### 4.1.1 팀 내부 리허설
- 정해진 시간 안에 발표가 끝나는지 확인한다.
- 발표자와 시연 담당자의 전환이 자연스러운지 확인한다.
- 실제 배포 주소에서 시연한다.
- 질문을 받을 수 있는 데이터 구조와 기술 선택 근거를 팀원 모두가 설명할 수 있게 한다.
---
### 4.1.2 질문 대비
- 왜 이 사용자를 선택했는가
- 왜 이 기능이 핵심인가
- 왜 JSON과 LocalStorage를 이렇게 나눴는가
- 심화 기술을 선택했다면 왜 필요한가
- 사용자 테스트에서 가장 큰 문제는 무엇이었는가
- 시간이 더 있다면 무엇을 개선할 것인가
---
## 4.2 최종 배포 상태 고정
### 4.2.1 릴리스 후보(Release Candidate, RC)
- 최종 발표에 사용할 버전을 릴리스 후보로 정한다.
- 발표 직전 새로운 기능을 무리하게 추가하지 않는다.
- 문제가 없는 최종 버전을 GitHub에 기록한다.
- 배포 주소와 해당 코드 버전을 일치시킨다.
