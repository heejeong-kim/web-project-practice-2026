# 학습목표
- 2주차 조사 결과를 근거로 핵심 사용자(Target User)를 구체적으로 정의할 수 있다.
- 페르소나(Persona)의 사용자 문제(Pain Point)와 요구(Needs)를 프로젝트 문제 정의문(Problem Statement)으로 연결할 수 있다.
- 팀별 후보 주제를 비교해 한 학기 안에 구현 가능한 최종 프로젝트 주제와 트랙을 결정할 수 있다.
---
# 준비물 및 수업환경
- 2주차 서비스 역분석 보고서와 경쟁서비스 비교표를 준비한다.
- 2주차에 작성한 프로젝트 후보 문제 영역 2개 이상을 준비한다.
- 팀 활동을 기록할 Notion 페이지 또는 공동 문서를 준비한다.
- 팀원과 함께 조사 근거를 바로 확인할 수 있도록 출처 링크와 화면 캡처를 정리한다.
<callout icon="💡" color="yellow_bg">
	- 3주차에는 기능부터 정하지 않는다.
	- 먼저 누구의 어떤 문제를 해결할지 정한 뒤 주제를 선택한다.
</callout>
# 1. \[이론+실습\] 사용자 분석과 핵심 사용자 정의
## 1.1 사용자 세분화(User Segmentation)
### 1.1.1 모든 사람을 위한 서비스의 문제
- 모든 대학생을 사용자로 정하면 서로 다른 상황과 요구가 한 문장에 섞이기 쉽다.
- 같은 대학생이라도 신입생, 취업 준비생, 통학생, 자취생은 필요한 정보와 행동이 다르다.
- 핵심 사용자는 나이만으로 정하지 않고 상황, 목표, 행동, 제약 조건을 함께 본다.
- 좋은 사용자 정의는 이후 기능을 선택할 때 포함하거나 제외할 기준이 된다.
---
### 1.1.2 사용자 후보를 나누는 네 가지 기준
- 상황은 언제 어떤 맥락에서 서비스를 사용하는지를 의미한다.
- 목표는 사용자가 서비스에서 끝내고 싶은 일을 의미한다.
- 행동은 현재 문제를 해결하기 위해 어떤 방법을 쓰는지를 의미한다.
- 제약은 시간, 정보 부족, 비용, 위치, 경험 부족처럼 행동을 어렵게 만드는 조건을 의미한다.

## 1.2 핵심 사용자(Target User) 선정
### 1.2.1 핵심 사용자와 보조 사용자
- 핵심 사용자는 이번 프로젝트의 가장 중요한 사용자 경험을 설계할 기준이 되는 사용자다.
- 보조 사용자는 서비스를 사용할 수 있지만 핵심 기능과 화면을 결정하는 첫 기준은 아니다.
- 첫 학기 프로젝트에서는 핵심 사용자 1개 유형을 우선하고 필요한 경우 보조 사용자 1개 유형만 추가한다.

- 필요한 데이터를 한 학기 안에 확보할 수 있는가
- 이번 수업의 기술 범위로 핵심 흐름을 구현할 수 있는가
- 팀이 실제 사용 상황을 설명할 수 있는가

### 1.2.3 실습｜사용자 후보 3개 비교
- 2주차 분석 결과에서 사용자 후보를 3개 작성한다.
- 각 후보의 상황, 목표, 현재 행동, 불편, 필요한 정보를 작성한다.
- 다섯 가지 선정 기준으로 후보를 비교한다.
- 핵심 사용자 1개와 보조 사용자 1개를 선택한다.
- 제외한 후보는 제외 이유를 한 줄로 남긴다.

# 2. \[이론+실습\] 페르소나와 문제 정의
## 2.1 페르소나(Persona)
### 2.1.1 페르소나의 역할
- 페르소나는 예쁜 프로필 카드를 만드는 활동이 아니라 팀이 같은 사용자를 바라보기 위한 의사결정 도구다.
- 이름이나 사진보다 목표, 행동, 불편, 사용 환경이 중요하다.
- 근거 없이 취미나 성격을 과도하게 꾸미지 않는다.
- 2주차 조사에서 확인한 사용자 특징과 관찰 내용을 근거로 작성한다.
---
### 2.1.2 페르소나에 포함할 항목
- 한 줄 사용자 설명
- 서비스를 사용하는 상황
- 가장 중요한 목표 1\~2개
- 현재 문제 해결 방식
- 사용자 문제 3개
- 필요한 정보와 요구
- 디지털 사용 환경과 제약 조건

- 사용자 문제는 현재 사용자가 겪는 어려움이다.
- 요구는 그 어려움이 해결된 상태에서 사용자가 필요로 하는 것이다.
- 기능은 문제와 요구를 해결하기 위해 팀이 제안하는 방법이다.

### 2.2.2 문제 우선순위 정하기
- 문제를 중요도와 발생 빈도로 비교한다.
- 자주 발생하지만 영향이 작은 문제와 드물지만 매우 큰 문제를 구분한다.
- 핵심 프로젝트 문제는 사용자 목표를 막는 문제를 우선한다.
- 화면 색상이 마음에 들지 않는다처럼 취향에 가까운 문제는 핵심 문제로 사용하지 않는다.
---
## 2.3 문제 정의문(Problem Statement)
### 2.3.1 문제 정의문의 구조
- 핵심 사용자 + 사용 상황 + 현재 어려움 + 그로 인한 영향을 한 문장으로 작성한다.
- 기능명이나 해결 방법을 문제 정의문에 먼저 넣지 않는다.
- 검색 기능이 필요하다는 문장은 문제 정의가 아니라 해결책 제안에 가깝다.

## 2.4 가치 제안(Value Proposition)
### 2.4.1 가치 제안 작성
- 가치 제안은 기능 목록이 아니라 사용자가 얻는 변화와 결과를 설명한다.
- 누구에게 어떤 문제를 어떤 방식으로 줄여 어떤 결과를 제공하는지 작성한다.
- 예시｜지원 조건을 직접 비교하기 어려운 학생에게 조건 중심의 탐색 구조를 제공해 지원 가능한 장학금을 빠르게 찾도록 돕는다.
---
### 2.4.2 실습｜문제에서 가치까지 연결
- 핵심 페르소나 1개를 완성한다.
- 사용자 문제를 최소 3개 작성한다.
- 문제별 요구를 연결한다.
- 가장 중요한 문제 1개를 선정한다.
- 문제 정의문 2개를 작성한 뒤 더 구체적인 문장을 선택한다.
- 가치 제안을 한 문장으로 작성한다.

# 3. \[실습\] 팀프로젝트 주제 선정과 확정
## 3.1 주제 선정 기준
### 3.1.1 좋은 프로젝트 주제의 조건
- 사용자와 사용 상황을 한 문장으로 설명할 수 있다.
- JSON으로 구성할 기본 데이터가 충분하다.
- 검색·필터·정렬·상세보기 중 여러 기능이 자연스럽게 필요하다.
- LocalStorage 개인화가 사용자 경험에 실제로 의미가 있다.
- 14주차까지 핵심 흐름을 완성할 수 있다.
- 팀마다 도메인 특화 핵심 기능을 하나 이상 설계할 수 있다.
---
### 3.1.2 피해야 할 주제
- 화면 소개만으로 끝나는 홍보 사이트
- 데이터가 5개 이하라 검색과 필터가 의미 없는 서비스
- 실시간 다중 사용자 기능이 없으면 성립하지 않는 서비스
- 결제, 실시간 채팅, 복잡한 관리자 기능이 핵심인 서비스
- 수업 공통 레퍼런스 프로젝트와 거의 동일한 서비스
---
## 3.2 선택 불가 공통 실습 주제
### 3.2.1 공통 레퍼런스 프로젝트 제외
- 영화·도서 콘텐츠 탐색과 매우 유사한 주제는 선택하지 않는다.
- 여행지 탐색과 매우 유사한 주제는 선택하지 않는다.
- 학습 콘텐츠·목표 관리와 매우 유사한 주제는 선택하지 않는다.
- 공통 프로젝트는 기술 패턴을 배우기 위한 수업 예제이므로 최종 팀프로젝트에서는 다른 문제 영역을 선택한다.
---

## 3.5 필수 트랙과 심화 트랙 결정
### 3.5.1 필수 트랙 판단
- 서비스의 핵심 가치가 미리 준비한 데이터 탐색과 개인 저장으로 완성되면 필수 트랙을 선택한다.
- 심화 기능 없이도 핵심 사용자 목표가 끝까지 완료되어야 한다.
---
### 3.5.2 심화 트랙 판단
- 최신 외부 데이터가 없으면 서비스 가치가 크게 떨어지는지 확인한다.
- 사용자 간 공유 데이터가 반드시 필요한지 확인한다.
- API나 클라우드 DB가 실패해도 기본 서비스가 완전히 멈추지 않도록 대체 흐름을 설계할 수 있는지 확인한다.
- 아직 판단이 어렵다면 필수 트랙으로 시작하고 11\~12주차에 심화 여부를 다시 결정한다.
---
## 3.6 최종 주제 확정
### 3.6.1 팀별 확정 절차
- 팀을 2\~3명으로 구성한다.
- 후보 주제 3개를 제출한다.
- 다른 팀과의 중복과 범위를 검토한다.
- 교수자 조정 후 최종 주제 1개를 확정한다.
- 핵심 사용자와 문제 정의문을 함께 확정한다.
- 한 문장 프로젝트 정의를 작성한다.
---
### 3.6.2 한 문장 프로젝트 정의 예시
- 공모전 정보를 여러 사이트에서 확인하는 대학생이 관심 분야와 마감일을 기준으로 공모전을 빠르게 찾고 관심 목록으로 관리하도록 돕는 웹서비스
- 식물을 처음 키우는 사용자가 집의 빛 환경과 관리 난이도를 기준으로 적합한 식물을 찾고 관심 식물의 관리 정보를 저장하도록 돕는 웹서비스
---
# 3주차 핵심 정리
- 핵심 사용자는 서비스의 모든 화면과 기능을 결정하는 첫 기준이다.
- 페르소나는 꾸며낸 캐릭터가 아니라 사용자 근거를 팀이 공유하기 위한 도구다.
- 사용자 문제와 요구를 먼저 정의한 뒤 기능을 결정한다.
- 프로젝트 주제는 이름이 아니라 사용자 + 문제 + 데이터 + 핵심 흐름으로 판단한다.
- 심화 트랙은 기술 수준이 높은 팀을 의미하지 않고 프로젝트 문제상 API나 공유 데이터가 필요한 팀을 의미한다.
