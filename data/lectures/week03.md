# 1. 개인 아이디어 취합과 프로젝트 후보 선택
<figure class="chapter-image"><img src="/web-project-practice-2026/asset/3_1.png" alt="1장 개인 아이디어 취합과 프로젝트 후보 선택" loading="eager"></figure>
## 1.1 개인 아이디어 공유 → 팀 아이디어 선택
2주차에서는 각자 관심 서비스를 역분석하고 경쟁 서비스와 시장·트렌드를 조사하면서 어떤 사용자 문제가 반복되고 어떤 부분에 프로젝트 기회가 있는지 개인 단위로 관찰했다. 3주차에는 이 결과로 곧바로 팀 주제를 정하지 않고 먼저 팀원별 아이디어와 문제 후보를 한곳에 모아 비교한다.

팀 활동의 목적은 가장 말하기 좋은 아이디어를 고르는 것이 아니라 조사 근거가 있고, 사용자가 분명하며, 한 학기 안에 데이터와 기능으로 구현할 수 있는 후보를 찾는 것이다. 아이디어 이름보다 어떤 문제를 발견했고 왜 해결 가치가 있다고 판단했는지를 함께 설명한다.

### 팀 아이디어 풀 만들기
팀원 아이디어를 모두 들은 직후 다수결로 하나를 고르면 친숙하거나 설명이 쉬운 주제가 선택되기 쉽다. 프로젝트 주제는 선호도보다 **사용자 문제의 명확성·조사 근거·데이터 확보·기술 범위·차별 가능성**을 기준으로 비교한다.

유사한 아이디어는 하나의 문제 영역으로 묶고, 표현은 다르지만 같은 사용자를 다루는 후보는 합쳐서 다시 정의해 개인 아이디어 목록을 팀의 프로젝트 후보 3~5개 정도로 압축한다.

- 비슷한 사용자·문제 영역의 아이디어를 묶어 하나의 후보로 정리
- 각 후보에 예상 사용자, 문제, 조사 근거, 데이터, 핵심 기능을 작성

# 2. 사용자 분석과 핵심 사용자 정의
<figure class="chapter-image"><img src="/web-project-practice-2026/asset/3_2.png" alt="2장 사용자 분석과 핵심 사용자 정의" loading="eager"></figure>
## 2.1 사용자 세분화(User Segmentation)
### 2.1.1 모든 사람을 위한 서비스의 문제
“모든 대학생”처럼 사용자를 넓게 정의하면 서로 다른 상황과 요구가 한 문장에 섞여 프로젝트 기준이 흐려질 수 있다. 같은 대학생이라도 신입생·취업 준비생·통학생·자취생과 같이 세분화하고, 사용 상황·목표·현재 행동·제약 조건을 함께 본다.
---
### 2.1.2 사용자 후보를 나누는 네 가지 기준
- **상황**: 언제 어떤 맥락에서 서비스를 사용하는가
- **목표**: 사용자가 서비스에서 끝내고 싶은 일은 무엇인가
- **행동**: 현재 문제를 해결하기 위해 어떤 방법을 쓰는가
- **제약**: 시간·정보 부족·비용·위치·경험 부족처럼 행동을 어렵게 만드는 조건은 무엇인가

<tr><td>구분</td><td>너무 넓은 표현</td><td>구체적인 표현 예시</td></tr>
<tr><td>사용자</td><td>대학생</td><td>공강 1시간 안에 참여 가능한 교내 프로그램을 찾는 1학년 학생</td></tr>

## 2.2 핵심 사용자(Main Target) 선정
### 2.2.1 핵심 사용자와 보조 사용자
핵심 사용자 1개 유형을 우선하고 필요한 경우 보조 사용자 1개 유형만 추가한다.
- 핵심 사용자는 이번 프로젝트의 가장 중요한 사용자 경험을 설계할 기준이 되는 사용자
- 보조 사용자는 서비스를 사용할 수 있지만 핵심 기능과 화면을 결정하는 첫 기준은 아닌 사용자
---
### 2.2.2 핵심 사용자 선정 기준
- 문제의 빈도가 충분히 반복되는가
- 해결했을 때 사용자 가치가 분명한가
- 필요한 데이터를 한 학기 안에 확보할 수 있는가
- 이번 수업의 기술 범위로 핵심 흐름을 구현할 수 있는가
- 팀이 실제 사용 상황을 설명할 수 있는가
---
## <span color="blue">2.3 🖇️ 실습｜핵심 사용자 및 보조 사용자 선정</span>
후보를 많이 만드는 것이 아니라 **왜 한 유형을 핵심 사용자로 선택했는지 설명 가능한 근거**를 만드는 것이 목적이다.

<tr><td>B. 팀 프로젝트 모임 대학생</td><td>팀원 3~4명과 논의하며 작업</td><td>단체석, 대화 가능, 넓은 테이블</td></tr>
<tr><td>C. 재택 근무 직장인</td><td>평일 낮 업무 처리, 화상회의 포함</td><td>와이파이, 콘센트, 조용함</td></tr>
<tr><td>D. 취업 준비생</td><td>평일 종일 장시간 체류</td><td>24시, 시간제한 없음, 콘센트</td></tr>
</table>

**핵심 사용자 — 과제·시험 준비 대학생**
과제나 시험 준비를 위해 공강 시간이나 방과 후 3시간 이상 혼자 집중할 공간을 찾는 대학생. 도서관 좌석이 없거나 이동 중일 때 출발 전 휴대폰으로 조건에 맞는 카페를 찾으며, 콘센트·소음·영업시간을 목록에서 비교하고 괜찮았던 곳을 저장해 다시 찾기를 원한다.

**보조 사용자 — 팀 프로젝트 모임 대학생**
핵심 사용자와 달리 조용함보다 대화 가능한 환경, 1인석보다 단체석을 요구한다. 별도 화면을 만들지 않고 필터 값으로 수용한다.
</details>

# 3. 페르소나와 문제 정의
<figure class="chapter-image"><img src="/web-project-practice-2026/asset/3_3.png" alt="3장 페르소나와 문제 정의" loading="eager"></figure>
## 3.1 페르소나(Persona)
### 3.1.1 페르소나의 역할
페르소나는 예쁜 프로필 카드를 만드는 활동이 아니라 팀이 같은 사용자를 바라보기 위한 의사결정 도구다. 사용자의 목표·현재 행동·불편·사용 환경이 중요하며, 근거 없이 취미나 성격을 과도하게 꾸미지 않는다.
---
### 3.1.2 페르소나에 포함할 항목
- 한 줄 사용자 설명
- 서비스를 사용하는 상황
- 가장 중요한 목표 1~2개
- 현재 문제 해결 방식
- 사용자 문제 3개
- 필요한 정보와 요구
- 디지털 사용 환경과 제약 조건
---
## 3.2 사용자 문제(Pain Point)와 요구(Needs)
### 3.2.1 문제와 해결책을 구분하기
사용자 문제(Pain Point)는 현재 사용자가 겪고 있는 어려움이고, 요구(Needs)는 그 어려움이 해결된 상태에서 사용자가 필요로 하는 것이다. 기능(Feature)은 문제와 요구를 해결하기 위해 팀이 제안하는 방법이다.

기획에서는 **문제 → 요구 → 기능** 순서로 연결한다.
<table header-row="true">
<tr><td>구분</td><td>예시</td></tr>
<tr><td>사용자 문제</td><td>프로그램 정보가 여러 게시판에 흩어져 자신에게 해당되는지 빠르게 판단하기 어려움</td></tr>
<tr><td>요구</td><td>대상과 분야 조건을 기준으로 참여 가능한 항목만 보고 싶음</td></tr>
<tr><td>기능 후보</td><td>대상 필터와 분야 필터</td></tr>
</table>
---
### 3.2.2 문제 우선순위 정하기
- 문제를 중요도와 발생 빈도로 비교
- 자주 발생하지만 영향이 작은 문제와 드물지만 매우 큰 문제를 구분
- 핵심 프로젝트 문제는 사용자 목표를 막는 문제를 우선
- 화면 색상처럼 취향에 가까운 문제는 핵심 문제로 사용하지 않음
---
## 3.3 문제 정의문(Problem Statement)
### 3.3.1 문제 정의문의 구조
**핵심 사용자 + 사용 상황 + 현재 어려움 + 그로 인한 영향**을 한 문장으로 작성한다. 기능명이나 해결 방법을 문제 정의문에 먼저 넣지 않는다.
---
### 3.3.2 좋은 예와 부족한 예
<table header-row="true">
<tr><td>구분</td><td>문장</td><td>판단</td></tr>
<tr><td>부족한 예</td><td>대학생에게 장학금 검색 서비스가 필요함</td><td>왜 필요한지와 어떤 상황인지 알 수 없음</td></tr>
<tr><td>좋은 예</td><td>처음 장학금을 알아보는 학생은 공고마다 지원 조건과 마감일 표현이 달라 자신이 지원 가능한 장학금을 짧은 시간 안에 비교하기 어려움</td><td>사용자, 상황, 문제와 영향이 드러남</td></tr>
</table>
---
## 3.4 가치 제안(Value Proposition)
가치 제안은 기능 목록이 아니라 사용자가 얻는 변화와 결과를 설명한다. **누구에게 어떤 문제를 어떤 방식으로 줄여 어떤 결과를 제공하는지** 작성한다.
> 예시) 지원 조건을 직접 비교하기 어려운 학생에게 조건 중심의 탐색 구조를 제공해 지원 가능한 장학금을 빠르게 찾도록 도움
---

**문제 정의문**
과제·시험 준비로 3시간 이상 집중할 카페를 찾는 대학생은 콘센트·소음·시간제한 같은 체류 조건이 필터로 제공되지 않아 후보마다 리뷰를 일일이 읽어야 하고, 이동 전 짧은 시간 안에 방문할 곳을 결정하지 못한다.

**가치 제안**
리뷰를 일일이 읽어야만 체류 조건을 확인할 수 있던 대학생에게 조건 중심의 목록 비교 구조를 제공해, 이동 전 짧은 시간 안에 작업할 카페를 결정하고 관심 공간을 저장해 다시 찾도록 돕는다.
</details>

# 4. 팀프로젝트 주제 및 트랙 확정
<figure class="chapter-image"><img src="/web-project-practice-2026/asset/3_4.png" alt="4장 팀프로젝트 주제 및 트랙 확정" loading="eager"></figure>
## 4.1 팀 주제 확정
- 팀을 2~3명으로 구성(사전 확정)
- 다른 팀과의 중복과 범위를 검토(아이디어 현황표로 확인)
- 교수자 조정 후 최종 주제 1개를 확정
### 좋은 프로젝트 주제의 조건
- 사용자와 사용 상황을 한 문장으로 설명할 수 있음
- JSON으로 구성할 기본 데이터가 충분함
- 검색·필터·정렬·상세보기 중 여러 기능이 자연스럽게 필요함
- LocalStorage 개인화가 사용자 경험에 실제로 의미가 있음
- 14주차까지 핵심 흐름을 완성할 수 있음
- 팀마다 도메인 특화 핵심 기능을 하나 이상 설계할 수 있음
---
### 피해야 할 주제
- 화면 소개만으로 끝나는 홍보 사이트
- 데이터가 5개 이하라 검색과 필터가 의미 없는 서비스
- 실시간 다중 사용자 기능이 없으면 성립하지 않는 서비스
- 결제, 실시간 채팅, 복잡한 관리자 기능이 핵심인 서비스
- <span color="red">**같은 반 공통 레퍼런스 프로젝트와 거의 동일한 서비스 절대 불가**</span>
---
## 4.2 트랙 방향 검토
아직 판단이 어렵다면 필수 트랙으로 시작하고 11~12주차에 심화 여부를 다시 결정해도 무관하다. 팀프로젝트 등록 시 우선 필수 트랙으로 체크한다.
### 필수 트랙
- 서비스의 핵심 가치가 미리 준비한 데이터 탐색과 개인 저장으로 완성되면 필수 트랙 선택
- 심화 기능 없이도 핵심 사용자 목표가 끝까지 완료되어야 함
---
### 심화 트랙
- 최신 외부 데이터가 없으면 서비스 가치가 크게 떨어지는지 확인
- 사용자 간 공유 데이터가 반드시 필요한지 확인
- API나 클라우드 DB가 실패해도 기본 서비스가 완전히 멈추지 않도록 대체 흐름을 설계할 수 있는지 확인
---
