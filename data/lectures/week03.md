# 2. 사용자 분석과 핵심 사용자 정의
## 2.1 사용자 세분화(User Segmentation)
### 2.1.1 모든 사람을 위한 서비스의 문제
모든 대학생처럼 사용자를 넓게 정의하면 서로 다른 상황과 요구가 한 문장에 섞여 프로젝트 기준이 흐려질 수 있으므로 같은 대학생이라도 신입생·취업 준비생·통학생·자취생과 같이 세분화가 필요
핵심 사용자는 나이만으로 정하는 것이 아니라 사용 상황·목표·현재 행동·제약 조건을 함께 보면서 확정하고, 구체화한 사용자 정의는 이후 기능을 포함하거나 제외할 때 팀이 공통으로 사용할 판단 기준으로 활용

- 해결했을 때 사용자 가치가 분명한가

# 3. 페르소나와 문제 정의
## 3.1 페르소나(Persona)
### 3.1.1 페르소나의 역할
페르소나는 예쁜 프로필 카드를 만드는 활동이 아니라 팀이 같은 사용자를 바라보기 위한 의사결정 도구로서 사용자의 목표·현재 행동·불편·사용 환경이 중요하며, 근거 없이 취미나 성격을 과도하게 꾸미지 않음
2주차 조사에서 확인한 사용자 특징과 관찰 내용을 근거로 작성하고, 이후 기능·화면·문구를 결정할 때 “이 사용자가 실제로 필요로 하는가”를 판단하는 기준으로 활용
---
### 3.1.2 페르소나에 포함할 항목
페르소나는 인물 소개서가 아니라 이후 기능과 화면을 결정할 때 반복해서 참고하는 설계 기준이므로, 인구통계 정보보다 사용 상황·목표·현재 행동·불편·제약이 드러나도록 정의 
**페르소나 정의 항목**
- 한 줄 사용자 설명
- 서비스를 사용하는 상황
- 가장 중요한 목표 1\~2개
- 현재 문제 해결 방식
- 사용자 문제 3개
- 필요한 정보와 요구
- 디지털 사용 환경과 제약 조건
---
## 3.2 사용자 문제(Pain Point)와 요구(Needs)
### 3.2.1 문제와 해결책을 구분하기
사용자 문제(Pain Point)는 현재 사용자가 겪고 있는 어려움이고, 요구(Needs)는 그 어려움이 해결된 상태에서 사용자가 필요로 하는 것으로 기능(Feature)은 문제와 요구를 해결하기 위해 팀이 제안하는 방법이므로 세 개념을 같은 의미로 사용하지 않음
기획에서는 **‘문제 → 요구 → 기능’ 순서로** 연결해야 기능부터 정한 뒤 이유를 끼워 맞추는 상황을 줄일 수 있음

### 3.2.2 문제 우선순위 정하기
- 문제를 중요도와 발생 빈도로 비교
- 자주 발생하지만 영향이 작은 문제와 드물지만 매우 큰 문제를 구분
- 핵심 프로젝트 문제는 사용자 목표를 막는 문제를 우선
- 화면 색상이 마음에 들지 않는다처럼 취향에 가까운 문제는 핵심 문제로 사용하지 않음
---
## 3.3 문제 정의문(Problem Statement)
### 3.3.1 문제 정의문의 구조
- 핵심 사용자 + 사용 상황 + 현재 어려움 + 그로 인한 영향을 한 문장으로 작성
- 기능명이나 해결 방법을 문제 정의문에 먼저 넣지 않음
- 검색 기능이 필요하다는 문장은 문제 정의가 아니라 해결책 제안에 가까움

## 3.4 가치 제안(Value Proposition)
### 3.4.1 가치 제안 작성
- 가치 제안은 기능 목록이 아니라 사용자가 얻는 변화와 결과를 설명
- 누구에게 어떤 문제를 어떤 방식으로 줄여 어떤 결과를 제공하는지 작성
- 예시｜지원 조건을 직접 비교하기 어려운 학생에게 조건 중심의 탐색 구조를 제공해 지원 가능한 장학금을 빠르게 찾도록 도움

# 4. 팀프로젝트 주제 및 트랙 확정
## 4.1 팀 주제 확정
- 팀을 2\~3명으로 구성(사전 확정)
- 다른 팀과의 중복과 범위를 검토(아이디어 현황표로 확인)
- 교수자 조정 후 최종 주제 1개를 확정
### 좋은 프로젝트 주제의 조건
- 사용자와 사용 상황을 한 문장으로 설명할 수 있음
- JSON으로 구성할 기본 데이터가 충분함
- 검색·필터·정렬·상세보기 중 여러 기능이 자연스럽게 필요함
- LocalStorage 개인화가 사용자 경험에 실제로 의미가 있음
- 14주차까지 핵심 흐름을 완성할 수 있음
- 팀마다 도메인 특화 핵심 기능을 하나 이상 설계할 수 있음
---
### 피해야 할 주제
- 화면 소개만으로 끝나는 홍보 사이트
- 데이터가 5개 이하라 검색과 필터가 의미 없는 서비스
- 실시간 다중 사용자 기능이 없으면 성립하지 않는 서비스
- 결제, 실시간 채팅, 복잡한 관리자 기능이 핵심인 서비스
- <span color="red">**같은 반 공통 레퍼런스 프로젝트와 거의 동일한 서비스 절대 불가**</span>

## 4.2 트랙 방향 검토
아직 판단이 어렵다면 필수 트랙으로 시작하고 11\~12주차에 심화 여부를 다시 결정해도 무관함. 팀프로젝트 등록 시 우선 필수 트랙으로 체크 
### 필수 트랙
- 서비스의 핵심 가치가 미리 준비한 데이터 탐색과 개인 저장으로 완성되면 필수 트랙을 선택
- 심화 기능 없이도 핵심 사용자 목표가 끝까지 완료되어야 함
---
### 심화 트랙
- 최신 외부 데이터가 없으면 서비스 가치가 크게 떨어지는지 확인
- 사용자 간 공유 데이터가 반드시 필요한지 확인
- API나 클라우드 DB가 실패해도 기본 서비스가 완전히 멈추지 않도록 대체 흐름을 설계할 수 있는지 확인
