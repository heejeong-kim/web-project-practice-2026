# 1. 사용자 시나리오와 기능 구조
## 1.1 핵심 사용자 시나리오(User Scenario)
### 1.1.1 시나리오가 필요한 이유
시나리오를 먼저 작성하면 화면을 그리는 단계에서 “이 버튼이 왜 여기 있는가”를 설명할 근거가 생기고, 반대로 시나리오에 등장하지 않는 기능은 우선순위를 낮출 수 있음
- 3주차에서 작성한 페르소나와 문제 정의문은 누가 어떤 어려움을 겪는지를 설명하지만, 그 사용자가 실제로 서비스를 어떻게 사용하는지는 아직 문장으로 남아 있지 않은 상태
- 사용자 시나리오는 페르소나가 특정 상황에서 서비스에 들어와 목표를 달성하기까지의 과정을 이야기 형태로 서술한 것으로, 기능과 화면을 결정하기 직전에 팀이 같은 장면을 떠올리게 만드는 역할을 함

## 1.2 사용자 문제에서 기능으로 연결하기
### 1.2.1 기능을 먼저 정하면 안 되는 이유
기능은 사용자 문제를 해결하기 위한 수단으로 좋아 보이는 기능부터 넣기 시작하면 프로젝트 범위가 빠르게 커지고 실제 사용자 문제와 연결되지 않는 화면과 기능이 쌓일 수 있으므로, 기능 후보를 정할 때는 이 기능이 어떤 사용자 문제를 줄이는지를 먼저 설명하고 답하기 어려운 기능은 우선순위를 낮추거나 제외하는 방식으로 범위를 관리
- 3주차에서 이미 \[사용자문제 → 요구 → 기능\] 순서로 정리했으므로 4주차에서는 새로운 기능을 추가하기보다 3주차 표를 그대로 가져와 기능 후보를 확정하는 방식으로 진행

## 1.3 최소 기능 제품(Minimum Viable Product, MVP)
### 1.3.1 MVP의 의미
MVP는 화면 수가 적은 프로젝트가 아니라 사용자가 최소한의 기능으로 핵심 목표를 처음부터 끝까지 완료할 수 있는 상태를 의미하며 탐색 서비스라면 목록만 존재하는 것보다 검색·필터·상세 확인처럼 핵심 판단 흐름이 이어져야 함
- MVP를 정할 때는 기능 개수보다 대표 사용자 흐름이 중간에서 끊기지 않는지를 우선 확인하고, 3주차에 작성한 가치 제안 한 문장이 실제로 달성되는지를 기준으로 판단
<table fit-page-width="true" header-row="true">
<colgroup><col width="130"><col width="344"><col width="357"></colgroup>
<tr><td>구분</td><td>기능은 많지만 MVP가 아닌 상태</td><td>기능은 적어도 MVP인 상태</td></tr>
<tr><td>구성</td><td>목록·지도·랭킹·테마 설정이 있으나 상세정보가 없음</td><td>목록·필터·상세·저장만 있으나 흐름이 끝까지 이어짐</td></tr>
<tr><td>사용자 결과</td><td>후보를 좁혔지만 최종 판단을 하지 못함</td><td>조건에 맞는 항목을 정하고 다시 찾을 수 있음</td></tr>
<tr><td>판단</td><td>핵심 목표 미완료</td><td>MVP 성립</td></tr>
</table>
> <span color="gray">예시) 프로그램 목록과 검색은 있지만 신청 대상과 마감일을 확인할 상세화면이 없다면 기능은 두 개뿐이어도 사용자는 최종 판단을 할 수 없으므로 MVP로 보기 어려움</span>
---
### 1.3.2 MVP 판단 질문
MVP 범위를 정할 때는 기능 수를 세는 대신 핵심 사용자가 목표를 끝까지 완료할 수 있는지를 확인해야 하므로 아래 질문에 답했을 때 흐름이 끊기는 지점이 있다면 해당 기능이나 화면이 우선 보완 대상
- 핵심 사용자가 첫 화면에서 무엇을 시작하는가
- 어떤 조건으로 정보를 좁히는가
- 어떤 정보를 보고 판단하는가
- 상세정보를 어디에서 확인하는가
- 다시 보고 싶은 항목을 어떻게 저장하는가
- 데이터가 없거나 결과가 없을 때 다음 행동을 알 수 있는가
- 저장한 항목을 다시 방문했을 때 어디에서 확인하는가
---
### 1.3.3 이미 제외로 판정된 범위 재확인
2주차 경쟁서비스 분석에서 유지·개선·제외를 이미 판정했으므로 4주차에서 기능 목록을 다시 만들 때 제외 판정 항목이 Must로 돌아오지 않도록 먼저 확인해야 하며, 특히 여러 사용자가 같은 최신 상태를 공유해야 하는 기능은 필수 트랙의 LocalStorage 범위로 구현할 수 없음을 재확인해야 함
예시) 
<table fit-page-width="true" header-row="true">
<colgroup><col width="200"><col width="130"><col width="401"></colgroup>
<tr><td>기능</td><td>2주차 판정</td><td>4주차에서의 처리</td></tr>
<tr><td>실시간 잔여 좌석·실시간 재고</td><td>제외</td><td>공유 DB 필요. 기능 목록에 남기되 MVP 범위에서 제외</td></tr>
<tr><td>예약·결제</td><td>제외</td><td>인증·결제 연동 필요. 외부 링크 이동으로 대체 검토</td></tr>
<tr><td>지도 렌더링</td><td>제외</td><td>외부 API 의존. 심화 트랙 검토 팀만 연결 위치 표시</td></tr>
<tr><td>리뷰 작성</td><td>제외</td><td>사용자 생성 데이터 필요. 개인 메모로 축소 검토</td></tr>
</table>
<callout icon="📌" color="blue_bg">
	제외한 기능은 삭제하지 않고 제외 사유와 함께 기록하여 13\~14주차 사용자 테스트에서 개선 항목을 판단할 때 왜 이 기능이 없는지 설명하는 근거로 사용
</callout>
---
### 1.3.4 Must / Should / Could 구분
기능 우선순위는 MoSCoW(Must·Should·Could·Won't) 기법을 단순화해 세 단계로 구분하고, 각 기능이 3주차 문제 우선순위 중 몇 번 문제와 연결되는지를 함께 기록해야 판단 근거가 남음
<table fit-page-width="true" header-row="true">
<colgroup><col width="110"><col><col width="280"></colgroup>
<tr><td>구분</td><td>의미</td><td>예시</td></tr>
<tr><td>Must</td><td>없으면 핵심 목표가 완료되지 않음</td><td>목록, 검색, 조건 필터, 상세보기</td></tr>
<tr><td>Should</td><td>중요하지만 없어도 최소 목표는 가능함</td><td>즐겨찾기, 최근 본 항목, 정렬</td></tr>
<tr><td>Could</td><td>시간이 남을 때 추가할 수 있음</td><td>보기 방식 변경, 테마 설정</td></tr>
<tr><td>제외</td><td>이번 학기 범위에서 구현하지 않음</td><td>공유 데이터·실시간·결제 기능</td></tr>
</table>
- Must는 4\~6개, Should는 1\~3개, Could는 1\~2개 정도로 제한
- 3주차 문제 우선순위 1순위를 해결하는 기능은 반드시 Must에 포함
- Must 기능이 7개를 넘으면 사용자 문제 기준으로 다시 통합하거나 Should로 이동
---
### 1.3.5 Must 기능의 완료 조건 작성
Must 기능은 발표용 목록이 아니라 이후 구현 일정과 평가의 기준이 되므로 완료 조건을 한 문장으로 작성해 언제 끝난 것으로 볼지 팀이 같은 기준을 갖도록 함
<table fit-page-width="true" header-row="true">
<colgroup><col width="110"><col width="532"></colgroup>
<tr><td>기능</td><td>완료 조건 문장</td></tr>
<tr><td>조건 필터</td><td>두 개 이상의 조건을 동시에 선택했을 때 조건을 모두 만족하는 항목만 남고 현재 선택된 조건이 화면에 표시되면 완료</td></tr>
<tr><td>상세보기</td><td>목록에서 선택한 항목의 id와 일치하는 상세정보가 표시되고 목록으로 되돌아갈 수 있으면 완료</td></tr>
</table>
> <span color="gray">예시) “필터 기능 구현”은 완료 여부를 판단할 수 없지만 “조건 2개를 동시에 적용했을 때 결과 건수가 화면에 표시된다”는 테스트로 확인할 수 있는 완료 조건</span>

# 2. 정보구조와 사용자 흐름 설계
## 2.1 정보구조(Information Architecture, IA)
### 2.1.1 설계 관점의 정보구조
정보구조(IA)는 사용자가 원하는 정보와 기능을 쉽게 찾을 수 있도록 콘텐츠를 분류하고 페이지와 탐색 경로를 연결하는 구조이며, 여기서 정한 카테고리 구조는 이후 검색·필터 기능과 6주차 JSON 필드 설계에 그대로 연결
- 정보구조를 정할 때는 화면을 먼저 그리는 대신 어떤 정보 묶음이 필요한지, 각 묶음을 어떤 기준으로 나눌지, 사용자가 몇 단계 만에 목표 정보에 도달하는지를 먼저 결정
<table fit-page-width="true" header-row="true">
<colgroup><col width="113"><col width="320"><col width="300"></colgroup>
<tr><td>결정 항목</td><td>확인할 질문</td><td>이후 연결되는 작업</td></tr>
<tr><td>정보 묶음</td><td>어떤 콘텐츠 단위가 반복되는가</td><td>JSON 항목 구조 설계</td></tr>
<tr><td>분류 기준</td><td>사용자가 이해할 수 있는 기준으로 나뉘는가</td><td>필터 카테고리 설계</td></tr>
<tr><td>탐색 진입점</td><td>검색·카테고리 중 어디에서 시작하는가</td><td>첫 화면 구성</td></tr>
<tr><td>정보 깊이</td><td>자주 확인하는 정보가 몇 단계 안에 있는가</td><td>목록 카드에 노출할 항목 결정</td></tr>
</table>
---
### 2.1.2 페이지를 늘리기 전에 확인할 것
페이지가 많다고 정보구조가 좋은 것은 아니며, 사용자가 같은 목적을 위해 여러 화면을 오가거나 비슷한 화면이 중복되면 탐색 비용이 커지므로, 새 페이지를 추가하기 전에 아래 기준으로 중복·과잉·단절을 점검
- 같은 목적의 화면이 중복되어 있지 않은가
- 한 화면에 지나치게 많은 기능이 몰려 있지 않은가
- 목록과 상세가 명확하게 구분되는가
- 사용자 저장 상태를 확인할 위치가 있는가
- 메인에서 핵심 과업까지 불필요한 단계가 많지 않은가
> <span color="gray">예시) “전체 목록”과 “인기 목록”을 별도 페이지로 만들면 두 화면의 구조가 거의 같아 중복이 발생하므로, 하나의 목록 화면에서 정렬 조건으로 처리하는 편이 탐색 단계를 줄임</span>
---
### 2.1.3 화면을 늘리지 않고 요구를 수용하는 방법
서로 다른 사용자 유형이나 추가 요구가 등장할 때 화면을 새로 만들면 구현 범위가 빠르게 늘어나므로 3주차에서 보조 사용자를 별도 화면 없이 필터 값으로 수용하기로 결정한 것처럼, 요구의 차이가 조건 값의 차이로 표현될 수 있다면 화면이 아니라 데이터 항목으로 해결
<table fit-page-width="true" header-row="true">
<colgroup><col width="230"><col width="230"><col width="319"></colgroup>
<tr><td>요구</td><td>화면을 늘리는 방식</td><td>데이터로 수용하는 방식</td></tr>
<tr><td>보조 사용자의 다른 조건</td><td>보조 사용자 전용 목록 화면 추가</td><td>기존 목록에 필터 값 추가</td></tr>
<tr><td>인기순으로 보고 싶음</td><td>인기 페이지 신설</td><td>목록 화면의 정렬 옵션 추가</td></tr>
<tr><td>저장한 항목만 보고 싶음</td><td>저장 전용 서비스 영역 신설</td><td>마이 화면 안의 탭 또는 목록 필터로 처리</td></tr>
</table>
---
## 2.2 사이트맵(Sitemap)
### 2.2.1 사이트맵 기본 구조
사이트맵(Sitemap)은 서비스에 필요한 모든 화면과 화면 간의 계층 관계를 한눈에 보여주는 구조도
- 메뉴에 노출되는 화면뿐 아니라 목록에서 선택해 진입하는 상세화면, 저장 목록처럼 메뉴 없이 도달하는 화면까지 모두 포함해야 이후 와이어프레임 단계에서 누락 없음 
- 본 프로젝트에서는 2\~3단계 깊이를 권장하며, 페이지 수를 많이 만드는 것보다 핵심 과업이 자연스럽게 이어지는 구조가 중요
- 각 페이지에는 그 화면에서 보여줄 핵심 데이터와 기능을 함께 표시해야 이후 와이어프레임 작업으로 바로 이어짐
<table fit-page-width="true" header-row="true">
<colgroup><col width="90"><col width="120"><col width="180"><col></colgroup>
<tr><td>1뎁스</td><td>2뎁스</td><td>3뎁스</td><td>주요 역할</td></tr>
<tr><td>홈</td><td>—</td><td>—</td><td>서비스 소개와 탐색 진입</td></tr>
<tr><td>홈</td><td>목록</td><td>—</td><td>검색·필터·정렬로 후보를 좁힘</td></tr>
<tr><td>홈</td><td>목록</td><td>상세</td><td>선택 항목의 판단 정보를 확인</td></tr>
<tr><td>홈</td><td>마이</td><td>즐겨찾기·최근 본 항목</td><td>저장한 항목을 다시 확인</td></tr>
</table>
- 3단계를 넘어가면 사용자가 목표 정보에 도달하기까지의 이동이 많아지므로 통합을 먼저 검토
- 심화 트랙을 검토하는 팀은 API·클라우드 DB·인증과 연결되는 화면을 별도로 표시
<callout icon="📌" color="blue_bg">
	검색엔진에 페이지 목록을 알려주는 `sitemap.xml` 파일과는 다른 개념으로 여기서 말하는 사이트맵은 기획 단계에서 화면 구조를 정리하는 설계 문서로 실무에서는 정보구조(IA) 문서의 일부로 작성하며, `sitemap.xml`은 14주차 배포 단계에서 검색 노출을 위해 생성하는 별도의 파일
</callout>
---
### 2.2.2 페이지 목록 작성 방법
- 필요한 페이지를 모두 카드 단위로 작성
- 같은 목적의 페이지를 그룹으로 묶음
- 불필요한 페이지와 중복 페이지를 제거
- 각 페이지에서 보여줄 핵심 데이터와 기능을 함께 표시
- 1.3.4에서 정한 Must 기능이 어느 페이지에 배치되는지 확인하고, 어떤 페이지에도 배치되지 않은 Must 기능이 있다면 화면 구성을 다시 검토
---
## 2.3 사용자 흐름(User Flow)
### 2.3.1 사용자 흐름의 구성
사용자 흐름은 페이지 목록이 아니라 사용자가 목표를 달성하기 위해 거치는 행동 순서를 말하며 서비스에서 사용자가 어떤 순서로 판단하도록 설계할지를 결정하는 단계
- 각 단계는 행동, 판단, 결과를 함께 표현하고 정상 흐름뿐 아니라 결과 없음, 잘못된 입력, 외부 연결 실패 같은 예외 흐름도 함께 고려

### 2.3.2 좋은 사용자 흐름과 부족한 사용자 흐름

</table>
- 각 단계마다 화면에 남아 있어야 하는 상태를 함께 기록
- 사용자가 중간에 되돌아가거나 조건을 초기화하는 경로도 반드시 포함

### 2.3.3 핵심 흐름 2개 선정
- 흐름 A는 서비스의 대표 탐색 과업으로 정함
- 흐름 B는 개인화 또는 프로젝트 특화 기능으로 정함
- 각 흐름의 시작 조건과 완료 조건을 명확하게 작성
- 두 흐름은 서로 연결되어야 하며 흐름 B는 흐름 A에서 저장한 결과를 사용하는 형태가 자연스러움
> <span color="gray">예시) 흐름 A가 “조건에 맞는 항목을 찾아 저장”이라면 흐름 B는 “저장한 항목을 다시 열어 최종 선택”처럼 재방문 상황을 다루면 LocalStorage 개인화의 필요성이 분명해짐</span>
<callout icon="📌" color="blue_bg">
	- 사용자 흐름(User Flow)은 제품 안에서 흔히 수행되는 하나의 과업을 완료하는 데 필요한 전형적이거나 이상적인 상호작용의 묶음으로 정의되며, 사용자 여정(User Journey)과 달리 단일 제품 안의 구체적인 행동과 시스템 반응만 다룸
	- 와이어플로우·순서도·과업 다이어그램 같은 산출물로 표현할 수 있으며, 감정과 생각으로 과정을 맥락화하지 않는다는 점이 1.1의 사용자 시나리오·여정 지도와의 차이
	- 참고｜[Nielsen Norman Group \| User Journeys vs. User Flows](https://www.nngroup.com/articles/user-journeys-vs-user-flows/)
</callout>

- 사용자가 조건을 초기화하거나 이전 단계로 되돌아가는 경로를 표시
- 심화 트랙을 적용하는 팀은 API·클라우드 DB 실패 시 필수 트랙 데이터로 대체되는 흐름을 반드시 설계

# 3. 와이어프레임과 데이터 연결
## 3.1 와이어프레임(Wireframe)
### 3.1.1 와이어프레임에서 확인할 것
와이어프레임은 디자인 완성본이 아니라 구현 전에 정보와 상호작용을 검증하는 도구로서 색상과 이미지 대신 정보의 우선순위와 행동의 위치를 확인하는 것이 목적이므로 흑백과 사각형만으로 작성해도 충분
- 이번 주차에서 작성하는 것은 **로우파이(Lo-fi) 와이어프레임**으로 흑백 도형과 텍스트만 사용해 정보 배치와 행동 위치를 빠르게 검증하는 단계
- 색상·타이포그래피·아이콘이 적용된 하이파이(Hi-fi) 시안과 클릭 가능한 프로토타입은 이번 주차 범위가 아님
- 색상과 이미지보다 정보 우선순위를 먼저 확인
- 사용자가 가장 먼저 봐야 할 정보가 상단 또는 주요 영역에 있는지 확인
- 검색, 필터, 상세보기, 저장 버튼의 위치가 사용자 흐름과 맞는지 확인
- 2.4에서 정의한 화면 상태가 모두 그려져 있는지 확인
- 모바일 화면에서 조작하기 어려운 요소가 없는지 확인
> <span color="gray">예시) 카드에 이미지를 크게 배치했는데 사용자가 실제로 비교하는 정보가 마감일과 대상이라면, 이미지 크기를 줄이고 조건 정보를 먼저 보이도록 배치하는 편이 판단 시간을 줄임</span>
---
### 3.1.2 목록 화면 구성 예시
- 서비스 제목과 현재 탐색 범위
- 검색창
- 주요 필터와 현재 선택된 조건 표시
- 정렬 선택
- 결과 건수
- 데이터 카드 목록과 카드별 조건 정보
- 결과 없음 상태
- 초기화 또는 다시 탐색 행동
---
### 3.1.3 상세 화면 구성 예시
- 제목과 핵심 이미지
- 사용자가 판단하는 데 가장 중요한 정보
- 보조 정보와 설명
- 태그 또는 조건 정보
- 즐겨찾기 또는 개인화 행동과 현재 저장 여부 표시
- 목록으로 돌아가기와 이전 조건 유지
---

필수 트랙 기준에 모바일에서도 핵심 사용자 흐름을 완료할 수 있어야 한다는 조건이 있고 3주차 페르소나의 제약 조건도 스마트폰 세로 화면이므로, 와이어프레임은 모바일 화면을 먼저 그린 뒤 데스크톱으로 확장하는 순서로 작성

## 3.4 필수 트랙과 심화 트랙 설계 표시
### 3.4.1 필수 트랙 표시
- JSON에서 오는 기본 데이터를 표시
- JavaScript가 처리할 검색·필터·정렬 기능을 표시
- LocalStorage에 저장할 사용자 상태와 그 상태가 보이는 화면 위치를 표시
- 2.4에서 정의한 화면 상태를 각 화면에 표시
---
### 3.4.2 심화 트랙 표시
심화 트랙을 검토 중인 팀만 작성하며, 아직 결정하지 않았다면 필수 트랙 기준으로만 설계하고 11\~12주차에 다시 판단
- 외부 API 데이터가 들어오는 위치를 표시
- 클라우드 DB에 저장하거나 조회하는 데이터가 있다면 표시
- 인증이 필요한 행동과 인증 없이 가능한 행동을 구분
- 심화 기능이 실패했을 때 보여줄 대체 상태를 표시

## 4.1 사용자 관점 검토
설계 결과는 문서의 양이 아니라 사용자·기능·화면·데이터가 같은 방향을 가리키는지로 판단

## 4.2 개발 관점 검토
- 화면별 필요한 데이터가 정리되어 있는가
- 검색·필터·정렬에 필요한 데이터와 자료형이 빠지지 않았는가
- 상세화면으로 연결할 식별 기준이 있는가
- 개인화 상태를 저장할 위치와 그 상태가 보이는 화면이 설계되어 있는가
- 화면 상태 다섯 가지가 모두 정의되어 있는가
- 심화 기능 없이도 필수 사용자 흐름이 유지되는가
