# 1. 사용자 시나리오와 기능 구조
## 1.1 핵심 사용자 시나리오(User Scenario)
### 1.1.1 시나리오가 필요한 이유
시나리오를 먼저 작성하면 화면을 그리는 단계에서 “이 버튼이 왜 여기 있는가”를 설명할 근거가 생기고, 반대로 시나리오에 등장하지 않는 기능은 우선순위를 낮출 수 있다.
- 사용자 시나리오는 페르소나가 특정 상황에서 서비스에 들어와 목표를 달성하기까지의 과정을 이야기 형태로 서술한 것
- 기능과 화면을 결정하기 직전에 팀이 같은 사용 장면을 떠올리게 만드는 역할을 함

## 1.3 최소 기능 제품(Minimum Viable Product, MVP)
### 1.3.1 MVP의 의미
MVP는 화면 수가 적은 프로젝트가 아니라 사용자가 최소한의 기능으로 핵심 목표를 처음부터 끝까지 완료할 수 있는 상태를 의미한다.
- 기능 개수보다 대표 사용자 흐름이 중간에서 끊기지 않는지를 우선 확인
- 3주차 가치 제안 한 문장이 실제로 달성되는지를 기준으로 판단
---
### 1.3.2 MVP 판단 질문
- 핵심 사용자가 첫 화면에서 무엇을 시작하는가
- 어떤 조건으로 정보를 좁히는가
- 어떤 정보를 보고 판단하는가
- 상세정보를 어디에서 확인하는가
- 다시 보고 싶은 항목을 어떻게 저장하는가
- 데이터가 없거나 결과가 없을 때 다음 행동을 알 수 있는가
- 저장한 항목을 다시 방문했을 때 어디에서 확인하는가
---
### 1.3.3 제외 범위 재확인
2주차 경쟁서비스 분석에서 제외한 기능이 4주차 Must로 다시 들어오지 않도록 점검한다.
<table fit-page-width="true" header-row="true">
<tr><td>기능</td><td>4주차에서의 처리</td></tr>
<tr><td>실시간 잔여 좌석·실시간 재고</td><td>공유 DB 필요. MVP 범위에서 제외</td></tr>
<tr><td>예약·결제</td><td>인증·결제 연동 필요. 외부 링크 이동으로 대체 검토</td></tr>
<tr><td>지도 렌더링</td><td>외부 API 의존. 심화 트랙 검토 팀만 연결 위치 표시</td></tr>
<tr><td>리뷰 작성</td><td>사용자 생성 데이터 필요. 개인 메모로 축소 검토</td></tr>
</table>
---
### 1.3.4 Must / Should / Could 구분
<table fit-page-width="true" header-row="true">
<tr><td>구분</td><td>의미</td><td>예시</td></tr>
<tr><td>Must</td><td>없으면 핵심 목표가 완료되지 않음</td><td>목록, 검색, 조건 필터, 상세보기</td></tr>
<tr><td>Should</td><td>중요하지만 없어도 최소 목표는 가능함</td><td>즐겨찾기, 최근 본 항목, 정렬</td></tr>
<tr><td>Could</td><td>시간이 남을 때 추가할 수 있음</td><td>보기 방식 변경, 테마 설정</td></tr>
<tr><td>제외</td><td>이번 학기 범위에서 구현하지 않음</td><td>공유 데이터·실시간·결제 기능</td></tr>
</table>
- Must는 4~6개, Should는 1~3개, Could는 1~2개 정도로 제한
- 3주차 문제 우선순위 1순위를 해결하는 기능은 반드시 Must에 포함
- Must 기능은 이후 테스트 가능한 완료 조건을 한 문장으로 작성
---
## <span color="blue">1.4 🖇️ 실습｜기능 우선순위와 MVP 범위 결정</span>
- 3주차 페르소나와 문제 정의문을 바탕으로 사용자 시나리오 1개를 5~8문장으로 작성
- 3주차 문제 우선순위 1~3순위별로 기능 후보를 작성
- 각 기능이 없을 때 사용자가 무엇을 못하는지 한 문장으로 작성
- 2주차 제외 판정 목록을 확인해 중복 검토
- Must 4~6개, Should 1~3개, Could 1~2개로 구분하고 필수·심화 트랙 표시
- 각 Must 기능의 완료 조건을 한 문장으로 작성

**프로젝트 예시: 카공 공간 조건 탐색 서비스**

- Must: 공간 목록, 지역 검색, 체류 조건 복수 필터, 목록 카드 조건 배지, 상세보기

- Could: 보기 방식 변경, 개인 메모 저장
- 제외: 실시간 좌석, 예약·결제, 지도 렌더링
- MVP 범위: 지역과 체류 조건으로 후보를 좁히고 목록과 상세를 비교해 방문할 공간 한 곳을 결정할 수 있으면 성립
</details>

## 2.2 사이트맵(Sitemap)

## 2.3 사용자 흐름(User Flow)
사용자 흐름은 페이지 목록이 아니라 사용자가 목표를 달성하기 위해 거치는 행동 순서다. 각 단계는 행동·판단·결과를 함께 표현하고 정상 흐름뿐 아니라 예외 흐름도 고려한다.
- 흐름 A는 서비스의 대표 탐색 과업
- 흐름 B는 개인화 또는 프로젝트 특화 기능
- 각 흐름의 시작 조건과 완료 조건을 명확하게 작성
- 두 흐름은 서로 연결되도록 설계
---

<tr><td>로딩</td><td>JSON 데이터를 불러오는 중</td><td>불러오는 중임을 알리는 표시</td></tr>
<tr><td>결과 없음</td><td>조건을 만족하는 항목이 0건</td><td>조건 완화 안내와 초기화 행동</td></tr>
<tr><td>오류</td><td>데이터를 불러오지 못함</td><td>다시 시도 행동과 상황 설명</td></tr>

## <span color="blue">2.5 🖇️ 실습｜사이트맵과 User Flow 설계</span>
- 필요한 페이지를 카드 단위로 모두 작성한 뒤 중복·과잉 페이지 제거
- 각 페이지에 배치할 핵심 데이터와 Must 기능 표시
- 2~3단계 깊이의 사이트맵으로 정리
- 대표 탐색 과업을 흐름 A, 개인화 과업을 흐름 B로 작성
- 각 단계에 행동·판단·결과와 유지되어야 할 상태 기록
- 결과 없음과 오류를 포함한 예외 흐름 추가
- 사이트맵의 모든 페이지가 두 흐름 중 한 곳에 등장하는지 확인
<details>
<summary><span color="blue">**[참고] 사이트맵과 핵심 User Flow 예시**</span></summary>
**카공 공간 조건 탐색 서비스**
- 홈 → 공간 목록 → 공간 상세
- 홈 → 마이 → 즐겨찾기 / 최근 본 공간
- 흐름 A: 지역 선택 → 복수 필터 → 카드 비교 → 상세 확인 → 즐겨찾기 저장
- 흐름 B: 재방문 → 마이 → 저장 항목 비교 → 상세 이동 또는 저장 해제
- 예외: 결과 0건, 지역 검색 실패, 목록 복귀 시 필터 유지, 저장 항목 0건, JSON 로드 오류
</details>

# 3. 와이어프레임과 데이터 연결
## 3.1 와이어프레임(Wireframe)
이번 주차에서 작성하는 것은 **로우파이(Lo-fi) 와이어프레임**이다. 색상과 이미지보다 정보의 우선순위와 행동 위치를 검증한다.
- 검색, 필터, 상세보기, 저장 버튼의 위치가 사용자 흐름과 맞는지 확인
- 2.4에서 정의한 화면 상태가 모두 그려져 있는지 확인
- 모바일 화면에서 조작하기 어려운 요소가 없는지 확인
---
## 3.2 모바일 우선 화면 설계
<table fit-page-width="true" header-row="true">
<tr><td>확인 항목</td><td>모바일에서의 문제</td><td>설계 방향</td></tr>

<table fit-page-width="true" header-row="true">

## 3.4 필수 트랙과 심화 트랙 설계 표시
### 3.4.1 필수 트랙
- JSON에서 오는 기본 데이터 표시
- JavaScript가 처리할 검색·필터·정렬 기능 표시
- LocalStorage에 저장할 사용자 상태와 그 상태가 보이는 화면 위치 표시
- 화면 상태를 각 화면에 표시
### 3.4.2 심화 트랙
- 외부 API 데이터가 들어오는 위치 표시
- 클라우드 DB 저장·조회 위치 표시
- 인증이 필요한 행동과 인증 없이 가능한 행동 구분
- 심화 기능 실패 시 대체 상태 표시
