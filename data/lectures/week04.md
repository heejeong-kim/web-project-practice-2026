- 3주차에 확정한 사용자 문제를 서비스 기능과 화면 구조로 변환할 수 있다.
- 정보구조(Information Architecture, IA), 사용자 흐름(User Flow), 와이어프레임(Wireframe)을 연결해 구현 전 서비스 구조를 설계할 수 있다.
- 최소 기능 제품(Minimum Viable Product, MVP) 기준으로 필수 기능과 선택 기능을 구분할 수 있다.

# 1. \[이론+실습\] 기능 구조와 MVP 설계
## 1.1 사용자 문제에서 기능으로 연결하기
### 1.1.1 기능을 먼저 정하면 안 되는 이유
- 기능은 사용자 문제를 해결하기 위한 수단이다.
- 좋아 보이는 기능을 먼저 넣으면 프로젝트 범위가 빠르게 커지고 실제 사용자 문제와 연결되지 않을 수 있다.
- 기능 후보를 정할 때는 이 기능이 어떤 사용자 문제를 줄이는가를 먼저 설명한다.
<table header-row="true">
<tr><td>사용자 문제</td><td>요구</td><td>기능 후보</td></tr>
<tr><td>장학금 지원 조건을 일일이 읽어야 한다.</td><td>나에게 해당되는 공고만 보고 싶다.</td><td>학년·소득·성적 조건 필터</td></tr>
<tr><td>마감일을 자주 놓친다.</td><td>마감이 가까운 항목을 먼저 보고 싶다.</td><td>마감일 정렬과 마감 임박 표시</td></tr>
</table>
---
### 1.1.2 핵심 기능(Core Feature)과 보조 기능(Supporting Feature)
- 핵심 기능은 없으면 사용자의 대표 과업이 완료되지 않는 기능이다.
- 보조 기능은 핵심 과업을 더 편리하게 만들지만 없어도 기본 목표는 완료할 수 있는 기능이다.
- 운영 기능은 서비스 운영에는 필요하지만 이번 수업 프로젝트에서 핵심 경험이 아닌 기능이다.
- 첫 프로젝트에서는 핵심 기능 4\~6개 정도로 범위를 제한한다.
---
## 1.2 최소 기능 제품(Minimum Viable Product, MVP)
### 1.2.1 MVP의 의미
- MVP는 화면 수가 적은 프로젝트가 아니라 사용자가 최소한의 기능으로 목표를 끝까지 완료할 수 있는 상태다.
- 목록만 있고 상세 확인이나 저장이 되지 않으면 탐색 서비스의 MVP로 보기 어렵다.
- 기능 수보다 사용자 흐름이 끊기지 않는지가 중요하다.
---
### 1.2.2 MVP 판단 질문
- 핵심 사용자가 첫 화면에서 무엇을 시작하는가
- 어떤 조건으로 정보를 좁히는가
- 어떤 정보를 보고 판단하는가
- 상세정보를 어디에서 확인하는가
- 다시 보고 싶은 항목을 어떻게 저장하는가
- 데이터가 없거나 결과가 없을 때 다음 행동을 알 수 있는가
---
### 1.2.3 Must / Should / Could 구분
<table header-row="true">
<tr><td>구분</td><td>의미</td><td>예시</td></tr>
<tr><td>Must</td><td>없으면 핵심 목표가 완료되지 않음</td><td>목록, 검색, 필터, 상세보기</td></tr>
<tr><td>Should</td><td>중요하지만 없어도 최소 목표는 가능함</td><td>즐겨찾기, 최근 본 항목</td></tr>
<tr><td>Could</td><td>시간이 남을 때 추가할 수 있음</td><td>보기 방식 변경, 테마 설정</td></tr>
</table>
---
### 1.2.4 실습｜기능 우선순위 결정
- 사용자 문제별 기능 후보를 작성한다.
- 각 기능이 없을 때 사용자가 무엇을 못하는지 작성한다.
- Must 4\~6개, Should 1\~3개, Could 1\~2개로 구분한다.
- 필수 트랙과 심화 트랙 기능을 별도 표시한다.
- 각 Must 기능의 완료 조건을 한 문장으로 작성한다.
---
# 2. \[이론+실습\] 정보구조와 사용자 흐름 설계
## 2.1 정보구조(Information Architecture, IA)
### 2.1.1 정보구조란 무엇인가
- 정보구조는 사용자가 원하는 정보와 기능을 쉽게 찾을 수 있도록 콘텐츠를 분류하고 연결하는 구조다.
- 메뉴 이름, 페이지 관계, 콘텐츠 그룹, 탐색 경로가 포함된다.
- 데이터의 카테고리 구조는 이후 검색·필터 구조와 직접 연결된다.
---
### 2.1.2 페이지를 늘리기 전에 확인할 것
- 같은 목적의 화면이 중복되어 있지 않은가
- 한 화면에 지나치게 많은 기능이 몰려 있지 않은가
- 목록과 상세가 명확하게 구분되는가
- 사용자 저장 상태를 확인할 위치가 있는가
- 메인에서 핵심 과업까지 불필요한 단계가 많지 않은가
---
## 2.2 사이트맵(Sitemap)
### 2.2.1 사이트맵 기본 구조
- 사이트맵은 페이지와 메뉴 간의 관계를 한눈에 보여주는 구조도다.
- 첫 학기 프로젝트에서는 2\~3단계 깊이를 권장한다.
- 페이지 수를 많이 만드는 것보다 핵심 과업이 자연스럽게 이어지는 구조가 중요하다.
<table header-row="true">
<tr><td>1단계</td><td>2단계</td><td>주요 역할</td></tr>
<tr><td>홈</td><td>목록</td><td>전체 데이터 탐색 시작</td></tr>
<tr><td>목록</td><td>상세</td><td>선택 항목의 세부정보 확인</td></tr>
<tr><td>마이</td><td>즐겨찾기</td><td>저장한 항목 다시 확인</td></tr>
</table>
---
### 2.2.2 실습｜사이트맵 만들기
- 필요한 페이지를 모두 포스트잇 또는 카드 단위로 작성한다.
- 같은 목적의 페이지를 그룹으로 묶는다.
- 불필요한 페이지와 중복 페이지를 제거한다.
- 각 페이지에서 보여줄 핵심 데이터와 기능을 함께 표시한다.
- 심화 트랙은 API·DB·인증과 연결되는 화면을 별도 표시한다.
---
## 2.3 사용자 흐름(User Flow)
### 2.3.1 사용자 흐름의 구성
- 사용자 흐름은 페이지 목록이 아니라 사용자가 목표를 달성하기 위해 거치는 행동 순서다.
- 행동, 판단, 결과를 함께 표현한다.
- 정상 흐름뿐 아니라 결과 없음, 잘못된 입력, 외부 연결 실패 같은 예외 흐름도 고려한다.
---
### 2.3.2 좋은 사용자 흐름 예시
- 서비스 진입 → 관심 분야 선택 → 지역과 일정 필터 적용 → 결과 6건 확인 → 항목 1개 선택 → 상세정보 확인 → 즐겨찾기 저장
- 홈 → 목록 → 상세처럼 화면명만 나열하면 사용자의 판단과 행동을 알기 어렵다.
---
### 2.3.3 핵심 흐름 2개 선정
- 흐름 A는 서비스의 대표 탐색 과업으로 정한다.
- 흐름 B는 개인화 또는 프로젝트 특화 기능으로 정한다.
- 각 흐름의 시작 조건과 완료 조건을 명확하게 작성한다.
- 사용자가 중간에 돌아가거나 조건을 초기화하는 경로도 확인한다.
---
# 3. \[실습\] 와이어프레임과 데이터 연결
## 3.1 와이어프레임(Wireframe)
### 3.1.1 와이어프레임에서 확인할 것
- 색상과 이미지보다 정보 우선순위를 먼저 확인한다.
- 사용자가 가장 먼저 봐야 할 정보가 상단 또는 주요 영역에 있는지 확인한다.
- 검색, 필터, 상세보기, 저장 버튼의 위치가 사용자 흐름과 맞는지 확인한다.
- 모바일 화면에서 조작하기 어려운 요소가 없는지 확인한다.
---
### 3.1.2 목록 화면 구성 예시
- 서비스 제목과 현재 탐색 범위
- 검색창
- 주요 필터
- 정렬 선택
- 결과 건수
- 데이터 카드 목록
- 결과 없음 상태
- 초기화 또는 다시 탐색 행동
---
### 3.1.3 상세 화면 구성 예시
- 제목과 핵심 이미지
- 사용자가 판단하는 데 가장 중요한 정보
- 보조 정보와 설명
- 태그 또는 조건 정보
- 즐겨찾기 또는 개인화 행동
- 목록으로 돌아가기
---
## 3.2 기능과 데이터 항목 연결
### 3.2.1 화면에 필요한 데이터 찾기
- 와이어프레임의 모든 정보 요소를 데이터 항목 후보로 표시한다.
- 검색에 쓰는 정보, 필터에 쓰는 정보, 정렬에 쓰는 정보, 상세에만 쓰는 정보를 구분한다.
- 화면에는 보이지 않지만 데이터 식별에 필요한 ID도 고려한다.
<table header-row="true">
<tr><td>화면 요소</td><td>필요 데이터</td><td>사용 목적</td></tr>
<tr><td>카드 제목</td><td>title</td><td>목록 표시와 검색</td></tr>
<tr><td>분야 태그</td><td>category</td><td>필터</td></tr>
<tr><td>마감일</td><td>deadline</td><td>상세 표시와 정렬</td></tr>
<tr><td>항목 식별</td><td>id</td><td>상세 연결과 즐겨찾기</td></tr>
</table>
---
## 3.3 필수 트랙과 심화 트랙 설계 표시
### 3.3.1 필수 트랙 표시
- JSON에서 오는 기본 데이터를 표시한다.
- JavaScript가 처리할 검색·필터·정렬 기능을 표시한다.
- LocalStorage에 저장할 사용자 상태를 표시한다.
---
### 3.3.2 심화 트랙 표시
- 외부 API 데이터가 들어오는 위치를 표시한다.
- 클라우드 DB에 저장하거나 조회하는 데이터가 있다면 표시한다.
- 인증이 필요한 행동과 인증 없이 가능한 행동을 구분한다.
- 심화 기능이 실패했을 때 보여줄 대체 상태를 표시한다.
---
## 3.4 설계 검토 체크리스트
### 3.4.1 사용자 관점
- 페르소나의 문제와 핵심 기능이 연결되는가
- 대표 사용자 흐름이 처음부터 끝까지 완료되는가
- 사용자가 다음 행동을 예상할 수 있는가
---
### 3.4.2 개발 관점
- 화면별 필요한 데이터가 정리되어 있는가
- 검색·필터·정렬에 필요한 데이터가 빠지지 않았는가
- 상세화면으로 연결할 식별 기준이 있는가
- 개인화 상태를 저장할 위치가 설계되어 있는가
- 심화 기능 없이도 필수 사용자 흐름이 유지되는가
---
# 4주차 핵심 정리
- 기능은 사용자 문제를 해결하기 위한 수단으로 선정한다.
- MVP는 기능 수가 적은 상태가 아니라 핵심 사용자 목표가 끝까지 완료되는 최소 완성 상태다.
- 정보구조는 콘텐츠와 화면을 조직하고 사용자 흐름은 목표 달성 과정의 행동 순서를 설명한다.
- 와이어프레임은 디자인 완성본이 아니라 구현 전에 정보와 상호작용을 검증하는 도구다.
- 화면 설계 단계에서 필요한 데이터 항목까지 함께 찾으면 6주차 JSON 설계가 쉬워진다.
---
