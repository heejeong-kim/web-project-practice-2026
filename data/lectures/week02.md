# 1. 서비스 역분석 방법
<figure class="chapter-image"><img src="/web-project-practice-2026/asset/2_1.png" alt="1장 서비스 역분석 방법" loading="eager"></figure>
## 1.1 서비스 역분석의 개념
### 1.1.1 역분석이란 무엇인가
서비스 역분석은 이미 완성된 웹서비스를 관찰하고, 화면 뒤에 숨어 있는 사용자 문제·서비스 목적·핵심 기능·데이터 구조·사용자 흐름을 거꾸로 추론하는 활동이다. 단순히 화면이 예쁜지, 기능이 많은지를 평가하는 것이 아니라 왜 이 정보가 먼저 보이는지, 왜 이 기능이 필요한지, 사용자는 어떤 순서로 행동하도록 설계되어 있는지를 해석한다.
<table header-row="true">
<tr><td>관찰 관점</td><td>확인할 질문</td></tr>
<tr><td>사용자</td><td>누가 이 서비스를 가장 많이 사용할 것으로 보이는가</td></tr>
<tr><td>문제</td><td>사용자는 어떤 불편이나 어려움을 해결하려고 들어오는가</td></tr>
<tr><td>기능</td><td>검색·필터·저장 같은 기능은 어떤 문제를 해결하는가</td></tr>
<tr><td>데이터</td><td>화면에 반복되는 정보는 어떤 데이터 구조로 관리될 수 있는가</td></tr>
<tr><td>사용자 흐름</td><td>사용자는 어떤 순서로 행동해 목표를 완료하는가</td></tr>
</table>
> 예시) 비교과 프로그램 탐색 서비스의 첫 화면에 분야·대상·일정 필터가 먼저 보인다면 단순한 UI 요소가 아니라, 많은 프로그램 중 자신에게 맞는 항목을 빠르게 찾기 어려운 사용자 문제를 해결하기 위한 탐색 구조로 해석한다.
---
### 1.1.2 디자인 분석과 서비스 역분석의 차이
디자인 분석은 화면이 어떻게 보이는지를 중심으로 살펴보고, 서비스 역분석은 사용자의 목적과 기능·데이터·행동이 어떻게 연결되어 있는지를 중심으로 살펴본다.
<table header-row="true">
<tr><td>구분</td><td>디자인 분석</td><td>서비스 역분석</td></tr>
<tr><td>중심 질문</td><td>어떻게 보이는가</td><td>왜 이렇게 작동하는가</td></tr>
<tr><td>주요 관찰 요소</td><td>색상, 타이포그래피, 레이아웃, 스타일</td><td>사용자, 문제, 기능, 데이터, 흐름</td></tr>
<tr><td>분석 결과</td><td>시각적 특징과 표현 방식</td><td>서비스 구조와 문제 해결 방식</td></tr>
<tr><td>프로젝트 활용</td><td>화면 스타일 참고</td><td>기능·데이터·사용자 흐름 설계 근거</td></tr>
</table>
---
### 1.1.3 역분석이 필요한 이유
기존 서비스가 문제를 어떻게 해결하는지 관찰하면 반복되는 문제 해결 패턴과 사용자의 기본 기대를 빠르게 이해할 수 있다. 여러 서비스에서 공통으로 나타나는 기능은 기본 기대 기능일 가능성이 높고, 특정 서비스에만 존재하는 기능은 특정 사용자나 상황을 위한 차별화 요소가 될 수 있다. 여러 서비스에서 같은 불편이 반복된다면 아직 충분히 해결되지 않은 문제일 가능성이 있다.
---
### 1.1.4 역분석에서 중요한 판단
**관찰 → 사용자 문제 추정 → 기능의 역할 해석 → 한계 확인 → 프로젝트 적용 여부 판단**의 흐름으로 정리한다. 기존 서비스의 기능을 그대로 복제하지 않고 우리 사용자의 문제와 반복 행동에 실제로 필요한지를 판단한다.
---
### 1.1.5 좋은 역분석 vs 좋지 않은 역분석
<table header-row="true">
<tr><td>구분</td><td>좋지 않은 분석</td><td>좋은 분석</td></tr>
<tr><td>사용자</td><td>대학생이 사용</td><td>공강 시간에 참여할 비교과 프로그램을 빠르게 찾고 싶은 1~2학년 학생이 사용</td></tr>
<tr><td>문제</td><td>검색이 필요함</td><td>프로그램 수가 많아 자신에게 맞는 정보를 짧은 시간 안에 찾기 어려움</td></tr>
<tr><td>기능</td><td>필터가 있음</td><td>분야·대상·일정 필터로 신청 가능한 프로그램만 좁혀볼 수 있음</td></tr>
<tr><td>장점</td><td>깔끔함</td><td>목록에서 일정과 대상 정보를 동시에 보여줘 상세화면을 반복해서 열 필요가 적음</td></tr>
</table>
- 좋은 분석은 관찰 가능한 화면과 행동을 근거로 작성한다.
- 좋다·예쁘다·편하다·불편하다처럼 이유 없는 표현은 피한다.
- 기능 이름만 나열하지 않고 그 기능이 해결하는 사용자 문제를 함께 작성한다.
---
## 1.2 서비스 역분석의 일곱 가지 관점
### 1.2.1 핵심 사용자(Target User)
나이·성별 같은 인구통계만으로 정의하지 않고 실제 사용 상황과 목적, 현재 행동이 함께 드러나게 작성한다. 첫 분석에서는 핵심 사용자 1~2개에 집중한다.
---
### 1.2.2 사용자 문제(Pain Point)와 요구(Needs)
**Pain Point → Needs → Feature** 순서로 연결한다. “검색 기능이 필요함”은 문제 정의가 아니라 해결 방법이므로 사용자의 상황과 어려움을 먼저 서술한다.
<table header-row="true">
<tr><td>구분</td><td>작성 예시</td><td>판단</td></tr>
<tr><td>Pain Point</td><td>정보가 너무 많아 원하는 프로그램을 빠르게 찾기 어려움</td><td>현재 겪는 문제</td></tr>
<tr><td>Needs</td><td>나에게 해당되는 프로그램만 빠르게 좁혀보고 싶음</td><td>필요한 상태</td></tr>
<tr><td>Feature</td><td>대상·분야·일정 필터</td><td>문제를 해결하기 위한 구현 방법</td></tr>
</table>
---
### 1.2.3 핵심 가치(Value Proposition)
기능 이름보다 사용자가 얻는 결과를 중심으로 작성한다. 빠르게 찾기, 비교하기, 기록하기, 맞춤형으로 보기, 신뢰할 수 있는 정보를 얻기처럼 사용자의 변화를 한 문장으로 표현한다.
---
### 1.2.4 핵심 기능(Core Feature)과 보조 기능(Supporting Feature)
<table header-row="true">
<tr><td>구분</td><td>예시</td><td>판단 기준</td></tr>
<tr><td>핵심 기능</td><td>검색, 필터, 목록 탐색, 상세 확인</td><td>없으면 사용자의 핵심 과업 수행이 어려운가</td></tr>
<tr><td>보조 기능</td><td>즐겨찾기, 최근 본 항목, 보기 방식 변경</td><td>없어도 기본 과업은 가능하지만 반복 이용이 불편해지는가</td></tr>
<tr><td>운영 기능</td><td>공지, 정책 안내, 고객센터</td><td>프로젝트 핵심 경험과 직접 관련이 적은가</td></tr>
</table>
---
### 1.2.5 데이터(Data / Data Entity / Attribute)
화면에 반복되는 제목·분야·대상·일정·장소·설명·이미지는 JSON 기본 데이터 후보가 되고, 즐겨찾기·최근 본 항목·개인 메모는 사용자 상태 데이터로 구분한다.
<table header-row="true">
<tr><td>구분</td><td>화면에서 보이는 예</td><td>프로젝트에서의 역할</td></tr>
<tr><td>기본 데이터</td><td>제목, 분야, 대상, 일정, 장소, 설명, 이미지</td><td>JSON에 저장하고 모든 사용자에게 공통 제공</td></tr>
<tr><td>사용자 상태</td><td>즐겨찾기, 최근 본 항목, 개인 메모</td><td>LocalStorage 등에 저장하고 사용자 행동에 따라 변경</td></tr>
<tr><td>화면 표시용 값</td><td>검색 결과 수, 선택된 필터, 정렬 상태</td><td>현재 화면 상태를 설명하기 위해 계산하거나 임시 사용</td></tr>
</table>
---
### 1.2.6 정보구조(Information Architecture, IA)
메뉴 이름 자체보다 카테고리·검색·필터·추천 영역·목록·상세화면이 어떤 관계로 연결되는지, 중요한 정보가 어느 단계에서 제공되는지를 확인한다.
---
### 1.2.7 사용자 흐름(User Flow)
화면 이름만 나열하지 않고 사용자의 판단과 행동을 연결한다.
> 예시) 서비스 진입 → 관심 분야 선택 → 일정 필터 → 결과 비교 → 상세 확인 → 관심 항목 저장
---
## 1.3 관찰과 추정을 구분하는 방법
화면에서 직접 확인한 사실과 분석자가 해석한 추정을 구분한다. 중요한 판단에는 화면 관찰, 공식 설명, 사용 후기, 개인 추정 중 어떤 근거를 사용했는지 표시하고 사용자 리뷰 하나를 전체 사용자 문제로 일반화하지 않는다.
<callout icon="📌" color="blue_bg">
- 역분석은 실제 사용자 연구를 대신하지 않는다.
- 역분석 단계에서는 기존 서비스의 구조를 이해하고 다음 단계에서 검증할 가설을 만드는 것이 목적이다.
- 참고｜[Nielsen Norman Group UX Research Methods](https://www.nngroup.com/articles/which-ux-research-methods/)
</callout>

## <span color="blue">1.4 🖇️ 실습｜서비스 한 개를 단계별로 역분석하기</span>
<table header-row="true">
<tr><td>단계</td><td>확인 내용</td><td>기록 결과</td></tr>
<tr><td>① 서비스 기본 정보</td><td>서비스명·URL·분야·플랫폼과 대표 과업을 정함</td><td>한 문장 서비스 설명</td></tr>
<tr><td>② 첫 화면 관찰</td><td>처음 보이는 정보, 가장 강조된 행동, 탐색 시작점을 확인</td><td>첫 화면 관찰 메모</td></tr>
<tr><td>③ 핵심 사용자와 문제</td><td>사용자 후보를 비교하고 가장 잘 연결되는 한 유형을 선택</td><td>사용자 정의와 문제 문장</td></tr>
<tr><td>④ 핵심 기능</td><td>핵심·보조·운영 기능으로 구분</td><td>핵심 기능 4~6개와 각 기능의 역할</td></tr>
<tr><td>⑤ 데이터 항목</td><td>반복 정보와 사용자가 저장하는 상태를 구분</td><td>데이터 후보 8개 이상</td></tr>
<tr><td>⑥ 사용자 흐름</td><td>시작과 종료를 정하고 행동과 판단을 연결</td><td>5단계 이상의 대표 사용자 흐름</td></tr>
<tr><td>⑦ 강점과 불편점</td><td>목표 달성 속도·이해도·실수 가능성 기준으로 판단</td><td>근거가 포함된 강점 3개, 불편점 3개</td></tr>
<tr><td>⑧ 한 문장 구조</td><td>누가 + 어떤 문제를 + 어떤 데이터와 기능으로 해결하는지 압축</td><td>서비스 구조 한 문장</td></tr>
</table>

# 2. 시장 트랜드 분석
<figure class="chapter-image"><img src="/web-project-practice-2026/asset/2_2.png" alt="2장 시장 트랜드 분석" loading="eager"></figure>
## 2.1 이번 수업에서 말하는 시장 분석
시장 분석은 기업 가치나 매출 규모를 계산하는 활동보다 사용자가 어떤 문제를 반복해서 겪고, 현재 어떤 방법으로 해결하며, 여러 서비스에서 어떤 기능과 정보가 반복되는지 확인하는 과정으로 본다.
<table header-row="true">
<tr><td>확인 관점</td><td>확인할 질문</td><td>프로젝트에서 얻는 것</td></tr>
<tr><td>문제 반복성</td><td>같은 어려움을 겪는 사용자가 반복해서 존재하는가</td><td>프로젝트로 다룰 가치가 있는 문제인지 판단</td></tr>
<tr><td>현재 대안</td><td>사용자는 지금 어떤 서비스나 방법으로 문제를 해결하는가</td><td>직접 경쟁·간접 경쟁·대체재 후보 확인</td></tr>
<tr><td>기본 기대</td><td>여러 서비스에서 공통으로 반복되는 기능과 정보는 무엇인가</td><td>기본 기능과 데이터 구조 후보 도출</td></tr>
<tr><td>비어 있는 영역</td><td>여러 서비스에서 반복되는 불편이 있는가</td><td>프로젝트 기회 영역 후보 도출</td></tr>
</table>
---
## 2.2 시장 자료를 읽는 방법
정량 자료는 관심의 크기와 변화 방향을, 정성 자료는 불편의 이유와 발생 상황을 이해하는 데 사용한다. 조사 시점·대상·출처를 함께 기록하고 서로 다른 근거가 같은 방향을 가리키는지 확인한다.
---
## 2.3 Google Trends를 활용한 관심도 조사
Google Trends는 실제 검색 횟수가 아니라 특정 기간·지역 안의 상대적 관심도를 보여준다. 키워드 2~3개를 동일 조건에서 비교하고, 대한민국 기준 최근 12개월과 최근 5년을 각각 확인해 단기·장기 변화를 함께 본다.
<callout icon="📌" color="blue_bg">
Google Trends의 100은 검색 100회를 의미하지 않는다. 관심도가 높다는 이유만으로 좋은 프로젝트 주제가 되는 것도 아니므로 서비스 분석과 사용자 문제 근거를 함께 확인한다.
</callout>
---
## 2.4 시장 트랜드를 프로젝트 관점에서 해석하기
트랜드는 최근 많이 보이는 기능이나 디자인을 수집하는 활동이 아니라 여러 서비스에서 반복되는 해결 방식과 사용자 기대를 관찰하는 과정이다. “요즘 많이 사용한다”가 아니라 왜 반복되는지, 우리 사용자의 문제를 줄이는 데 필요한지를 설명한다.
---
## <span color="blue">2.5 🖇️ 실습｜시장 트랜드 분석 하기</span>
[Google 트렌드](https://trends.google.co.kr/trends/)
- 관련 후보 키워드 2~3개 비교
- 최근 12개월과 5년 변화 확인
- 상승·하락 시점과 배경 해석
- 연관 검색어에서 반복되는 사용자 문제 표현 확인
- 결과를 프로젝트 기회 영역과 연결

# 3. 경쟁서비스 분석 및 UIUX 분석
<figure class="chapter-image"><img src="/web-project-practice-2026/asset/2_3.png" alt="3장 경쟁서비스 분석 및 UIUX 분석" loading="eager"></figure>
## 3.1 경쟁서비스를 비교하는 이유
경쟁서비스 분석은 어떤 서비스가 더 좋은지 순위를 정하는 활동이 아니라 같은 사용자 문제를 서로 다른 서비스가 어떻게 해결하는지 비교해 선택 가능한 해결 패턴을 찾는 과정이다.
---
## 3.2 경쟁서비스의 세 가지 범위
<table header-row="true">
<tr><td>구분</td><td>의미</td><td>공모전 탐색 예시</td><td>분석에서 얻는 것</td></tr>
<tr><td>① 직접 경쟁</td><td>같은 문제를 비슷한 서비스 방식으로 해결</td><td>다른 공모전 정보 플랫폼</td><td>기능 구조와 화면 흐름 비교</td></tr>
<tr><td>② 간접 경쟁</td><td>같은 문제를 다른 서비스 구조로 해결</td><td>검색엔진, SNS 해시태그</td><td>전문 서비스를 사용하지 않는 이유</td></tr>
<tr><td>③ 대체재</td><td>디지털 서비스가 아니어도 같은 목적을 달성</td><td>학과 단체채팅, 친구 추천, 게시판</td><td>기존 서비스가 놓치는 편의와 신뢰 요소</td></tr>
</table>
---
## 3.3 비교 대상을 선정하는 기준
- 동일한 사용자 문제를 다루는가
- 같은 문제를 서로 다른 해결 방식으로 접근하는가
- 현재 화면과 기능을 실제로 확인 가능한가
- 모든 서비스에서 동일한 대표 과업을 수행할 수 있는가
---
## 3.4 UIUX 분석의 핵심 관점
<table header-row="true">
<tr><td>번호</td><td>비교 관점</td><td>확인할 질문</td></tr>
<tr><td>①</td><td>탐색 시작점</td><td>검색·카테고리·추천 중 어디에서 행동을 시작하도록 유도하는가</td></tr>
<tr><td>②</td><td>검색·필터·정렬</td><td>조건을 조합하고 현재 선택 상태를 이해하기 쉬운가</td></tr>
<tr><td>③</td><td>목록 정보</td><td>비교에 필요한 핵심 정보가 목록에서 충분히 보이는가</td></tr>
<tr><td>④</td><td>상세보기</td><td>최종 판단에 필요한 추가 정보와 다음 행동이 명확한가</td></tr>
<tr><td>⑤</td><td>개인화·저장</td><td>사용자 행동이 이후 화면과 다음 방문에 어떻게 반영되는가</td></tr>
<tr><td>⑥</td><td>상태 안내</td><td>로딩·결과 없음·오류·저장 완료 상태를 이해할 수 있는가</td></tr>
<tr><td>⑦</td><td>반응형·접근성</td><td>작은 화면에서도 핵심 과업을 완료하고 상태를 구분할 수 있는가</td></tr>
</table>
---
## <span color="blue">3.5 🖇️ 실습｜유사 서비스 2~3개 비교하기</span>
같은 대표 과업을 세 서비스에서 동일하게 수행하고 첫 화면부터 결과 확인·상세보기·저장까지 같은 기준으로 기록한다.
<table header-row="true">
<tr><td>단계</td><td>실행 내용</td><td>기록 결과</td></tr>
<tr><td>1</td><td>대표 과업 하나 정의</td><td>시작 상태와 최종 목표</td></tr>
<tr><td>2</td><td>직접 경쟁을 포함한 서비스 2~3개 선정</td><td>선정 이유</td></tr>
<tr><td>3</td><td>첫 화면에서 탐색 시작점 확인</td><td>강조 정보와 첫 행동</td></tr>
<tr><td>4</td><td>같은 과업 실제 수행</td><td>행동 단계·막힘·되돌아간 지점</td></tr>
<tr><td>5</td><td>검색·필터·목록·상세·저장 구조 비교</td><td>공통 기능·차별 기능·불편점</td></tr>
<tr><td>6</td><td>비교 결과를 프로젝트 관점으로 해석</td><td>유지·개선·제외 판단</td></tr>
</table>

# 4. 프로젝트 기회 영역 도출
<figure class="chapter-image"><img src="/web-project-practice-2026/asset/2_4.png" alt="4장 프로젝트 기회 영역 도출" loading="eager"></figure>
## 4.1 기회 영역이란 무엇인가
기회 영역은 새로운 기능을 하나 더 추가하는 아이디어가 아니라 기존 서비스가 충분히 해결하지 못한 사용자 문제 또는 특정 사용자 상황을 더 나은 방식으로 해결할 수 있는 영역이다. 기능 이름보다 어떤 사용자가 어떤 상황에서 무엇 때문에 어려움을 겪는지를 먼저 설명한다.
---
## 4.2 기회 영역의 세 가지 출발점
<table header-row="true">
<tr><td>출발점</td><td>관찰 신호</td><td>확인할 질문</td></tr>
<tr><td>① 반복되는 불편</td><td>여러 서비스에서 같은 막힘이나 혼란이 발생</td><td>왜 아직 충분히 해결되지 않았는가</td></tr>
<tr><td>② 특정 사용자 소외</td><td>초보자·특정 상황의 사용자가 기존 구조에서 불리함</td><td>누가 현재 서비스에서 가장 불편한가</td></tr>
<tr><td>③ 데이터 탐색의 어려움</td><td>정보는 있지만 비교·필터·정렬하기 어려움</td><td>어떤 데이터 구조와 기능이 판단을 도울 수 있는가</td></tr>
</table>
---
## 4.3 좋은 기회 영역으로 바꾸는 방법
‘필터를 더 많이 넣음’, ‘정보를 한 곳에 모음’, ‘즐겨찾기를 만듦’처럼 해결책만 적지 않고 **사용자·상황·문제·필요한 경험**의 구조로 바꿔 쓴다.
---
## 4.4 프로젝트 후보의 가능성 점검
<table header-row="true">
<tr><td>평가 기준</td><td>낮음</td><td>보통</td><td>높음</td></tr>
<tr><td>문제 중요도</td><td>가끔 발생</td><td>반복적으로 불편</td><td>핵심 과업을 방해</td></tr>
<tr><td>데이터 확보</td><td>30건 구성이 어려움</td><td>일부 확보 가능</td><td>30건 이상과 의미 있는 필드 구성 가능</td></tr>
<tr><td>기술 구현</td><td>공유 DB·실시간 기능이 필수</td><td>범위 조정이 필요</td><td>JSON·JavaScript·LocalStorage로 핵심 경험 구현 가능</td></tr>
</table>
심화 트랙을 고려하는 경우에도 API나 클라우드 DB 사용 자체를 기회 영역으로 삼지 않고 사용자 문제 해결에 실제 필요한 이유가 있는지를 먼저 확인한다.
---
## <span color="blue">4.5 🖇️ 실습｜3주차로 넘길 문제 후보 만들기</span>
개인별 후보 2개 이상을 준비하고 3주차 사용자 분석에서 실제 대상 사용자와 사용 상황을 더 구체화한 뒤 팀별 우선순위를 결정한다.
<table header-row="true">
<tr><td>후보 판단</td><td>확인 내용</td></tr>
<tr><td>사용자 문제</td><td>어떤 사용자가 어떤 상황에서 반복적으로 겪는 문제인지 설명 가능</td></tr>
<tr><td>데이터</td><td>30건 이상과 검색·필터용 속성을 구성 가능</td></tr>
<tr><td>기술 범위</td><td>JSON·JavaScript·LocalStorage 중심으로 핵심 경험 구현 가능</td></tr>
<tr><td>차별 가능성</td><td>기존 서비스의 반복 불편이나 특정 사용자 상황과 연결됨</td></tr>
</table>
<callout icon="💡" color="yellow_bg">
2주차의 목표는 프로젝트 이름을 빨리 정하는 것이 아니라 어떤 사용자가 어떤 문제를 겪고 있는지 설명할 근거를 확보하는 것이다. 시장·경쟁서비스·UIUX 분석 결과가 3주차 사용자 분석의 출발점이다.
</callout>
