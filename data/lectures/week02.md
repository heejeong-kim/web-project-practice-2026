# 1. \[이론+실습\] 서비스 역분석 방법
## 1.1 서비스 역분석의 개념
### 1.1.1 역분석이란 무엇인가
- 서비스 역분석은 이미 완성된 웹서비스를 관찰하고 화면 뒤에 숨어 있는 사용자 문제, 서비스 목적, 핵심 기능, 데이터 구조, 사용자 흐름을 거꾸로 추론하는 활동으로 이해한다.
- 사용자가 보는 화면만 평가하지 않고 왜 이런 정보가 먼저 보이는지, 왜 이 기능이 이 위치에 있는지, 왜 이런 순서로 행동하게 하는지를 함께 살펴본다.
- 화면의 디자인을 분석하는 활동과 서비스 구조를 분석하는 활동은 구분한다.
- 디자인 분석은 색상, 타이포그래피, 배치, 스타일의 특징을 중심으로 본다.
- 서비스 역분석은 사용자 목적, 정보 구조, 기능 관계, 데이터 흐름, 행동 흐름을 중심으로 본다.
- 이번 교과목에서는 디자인의 완성도보다 서비스가 사용자의 목적 달성을 어떻게 지원하는지를 우선적으로 분석한다.
---
### 1.1.2 역분석이 필요한 이유
- 처음부터 새로운 서비스를 떠올리는 것은 어렵기 때문에 기존 서비스의 해결 방식을 관찰하면 문제 해결의 기본 패턴을 빠르게 학습할 수 있다.
- 여러 서비스에서 반복되는 기능은 사용자가 이미 익숙하게 받아들이는 기능일 가능성이 높다.
- 서비스마다 다른 기능은 특정 사용자나 상황을 위한 차별화일 수 있다.
- 사용 과정에서 반복적으로 발생하는 불편점은 새로운 프로젝트의 기회 영역이 될 수 있다.
- 시장에 이미 존재하는 서비스를 그대로 복제하는 것이 아니라 기존 해결 방식의 장단점을 이해한 뒤 다른 사용자나 상황에 맞게 재구성하는 것이 중요하다.
- 프로젝트 아이디어를 개인의 감이나 취향만으로 결정하지 않고 관찰 근거를 바탕으로 설명할 수 있게 된다.
---

## 1.2 서비스 역분석의 일곱 가지 관점
### 1.2.1 핵심 사용자(Target User)
- 가장 자주 사용할 가능성이 높은 사용자를 구체적으로 추정한다.
- 나이, 성별처럼 인구통계 정보만으로 사용자를 설명하지 않는다.
- 사용자가 서비스를 이용하는 상황과 목적을 함께 기록한다.
- 대학생보다 이번 학기에 취업 준비를 시작해 교내 취업 프로그램을 찾는 3학년 학생처럼 작성한다.
- 한 서비스에 여러 사용자가 존재하더라도 첫 분석에서는 핵심 사용자 1\~2개에 집중한다.
---
### 1.2.2 사용자 문제(Pain Point)와 요구(Needs)
- Pain Point는 사용자가 현재 겪고 있는 불편, 장애물, 어려움을 의미한다.
- Needs는 그 문제를 해결하기 위해 사용자가 필요로 하는 상태나 요구를 의미한다.
- Pain Point와 Needs는 연결되지만 같은 뜻으로 사용하지 않는다.
- 예를 들어 '정보가 너무 많아 원하는 프로그램을 빠르게 찾기 어렵다'는 Pain Point에 해당한다.
- '나에게 해당되는 프로그램만 빠르게 좁혀보고 싶다'는 Needs에 해당한다.
- 검색 기능이 필요하다는 표현은 해결 방법을 먼저 제시한 것이므로 Pain Point나 Needs 자체로 보기 어렵다.
- 기능을 먼저 정하기보다 Pain Point → Needs → Feature의 순서로 연결한다.
- 문제는 사용자의 상황, 행동, 어려움이 드러나도록 작성한다.
---
### 1.2.3 핵심 가치(Value Proposition)
- 사용자가 이 서비스를 선택하는 가장 중요한 이유를 한 문장으로 정리한다.
- 빠르게 찾기, 비교하기, 기록하기, 맞춤형으로 보기, 신뢰할 수 있는 정보를 얻기 등이 핵심 가치가 될 수 있다.
- 핵심 가치는 서비스가 제공하는 기능의 목록이 아니라 사용자가 얻는 결과로 표현한다.
- 예를 들어 필터 기능 제공보다 나에게 해당되는 프로그램만 빠르게 좁혀볼 수 있음이 더 적절하다.
---
### 1.2.4 핵심 기능(Core Feature)과 보조 기능(Supporting Feature)
- 핵심 기능은 사용자의 주된 목표 달성에 직접 필요한 기능으로 정의한다.
- 보조 기능은 없어도 기본 목적은 달성할 수 있지만 사용성과 편의성을 높이는 기능으로 정의한다.
- 서비스의 모든 버튼을 기능으로 기록하지 않는다.
- 서로 연결된 작은 버튼이나 동작은 하나의 기능 단위로 묶어 정리한다.

### 1.2.5 데이터(Data / Data Entity / Attribute)
- 화면에서 반복적으로 나타나는 정보 항목을 찾아 데이터로 추정한다.
- 카드, 목록, 상세화면에서 공통으로 반복되는 항목은 JSON 데이터 후보가 될 수 있다.
- 사용자의 행동에 따라 달라지는 값은 사용자 상태 데이터 후보로 볼 수 있다.
- 예를 들어 프로그램 탐색 서비스라면 제목, 분야, 대상, 일정, 장소, 설명, 이미지, 신청 상태 등이 기본 데이터 후보가 된다.
- 즐겨찾기 여부, 최근 본 항목, 개인 메모와 같은 값은 사용자 상태 후보가 된다.
- 아직 실제 구현을 하지 않더라도 화면을 보며 어떤 데이터가 필요할지 추정하는 연습을 한다.
---
### 1.2.6 정보구조(Information Architecture, IA)
- 사용자가 원하는 정보에 도달하기 위해 어떤 메뉴와 화면을 거치는지 살펴본다.
- 메뉴 이름만 나열하지 않고 정보가 어떤 기준으로 묶여 있는지 본다.
- 카테고리, 검색, 필터, 추천 영역, 상세화면이 서로 어떻게 연결되는지 정리한다.
- 중요한 정보가 첫 화면에 있는지 상세화면 안쪽에 숨겨져 있는지 확인한다.
- 사용자가 자주 확인해야 하는 정보가 너무 깊은 단계에 있다면 개선 기회가 될 수 있다.
---
### 1.2.7 사용자 흐름(User Flow)
- 사용자가 서비스에 들어온 순간부터 하나의 목표를 완료할 때까지의 행동 순서를 정리한다.
- 페이지 이동만 기록하지 않고 사용자가 무엇을 판단하고 어떤 행동을 선택하는지를 기록한다.
- 메인 → 목록 → 상세보다 서비스 진입 → 관심 분야 선택 → 조건 필터 → 결과 비교 → 상세 확인 → 관심 항목 저장처럼 과업 중심으로 작성한다.
- 한 서비스에서도 목적에 따라 여러 사용자 흐름이 존재할 수 있다.
- 첫 분석에서는 대표 과업 1개를 선택해 최소 5단계 이상으로 작성한다.
---
## 1.3 관찰과 추정을 구분하는 방법
### 1.3.1 관찰 가능한 사실
- 실제 화면에서 직접 확인할 수 있는 내용을 사실로 기록한다.
- 검색창이 상단에 있다, 카테고리가 6개다, 상세페이지에서 신청 버튼을 제공한다처럼 작성한다.
- 화면 캡처나 공식 안내 페이지로 근거를 남길 수 있어야 한다.
---
### 1.3.2 분석자의 추정
- 화면을 바탕으로 사용자의 의도나 서비스의 목적을 해석한 내용은 추정으로 구분한다.
- 사용자가 빠르게 비교하도록 카드에 가격을 강조한 것으로 보인다처럼 작성한다.
- 추정은 틀릴 수 있으므로 사실처럼 단정하지 않는다.
---
### 1.3.3 근거 수준 표시
- 중요한 분석 내용 옆에 화면 관찰, 공식 설명, 사용 후기, 개인 추정과 같이 근거 종류를 기록한다.
- 프로젝트 아이디어에 직접 영향을 주는 판단일수록 여러 근거를 함께 확인한다.
- 사용자 리뷰 하나만으로 전체 사용자의 문제라고 일반화하지 않는다.
<callout icon="📌" color="blue_bg">
	- 역분석은 실제 사용자 연구를 대신하지 않는다.
	- 역분석 단계에서는 기존 서비스의 구조를 이해하고 다음 단계에서 검증할 가설을 만드는 것이 목적이다.
	- 참고｜[Nielsen Norman Group UX Research Methods](https://www.nngroup.com/articles/which-ux-research-methods/)
</callout>

## 1.4 실습｜서비스 한 개를 단계별로 역분석하기
### 1.4.1 Step 1｜서비스 기본 정보 기록
- 서비스명과 URL을 기록한다.
- 서비스를 한 문장으로 설명한다.
- 주요 서비스 분야를 기록한다.
- 웹서비스인지 앱 중심 서비스인지 구분한다.
- 오늘 분석할 대표 과업 1개를 정한다.
- 대표 과업은 상품 구매처럼 너무 큰 범위보다 조건에 맞는 상품을 찾아 상세정보를 확인한다처럼 한 번의 흐름으로 완료할 수 있게 정한다.
---
### 1.4.2 Step 2｜첫 화면 30초 관찰
- 서비스를 처음 보는 사용자라고 가정한다.
- 첫 화면에서 가장 눈에 띄는 요소 3개를 적는다.
- 서비스가 가장 먼저 유도하는 행동을 적는다.
- 어떤 정보가 강조되어 있는지 적는다.
- 사용자가 어디서 시작해야 하는지 명확한지 확인한다.
- 첫 화면만 보고도 서비스 목적을 추정할 수 있는지 확인한다.
---
### 1.4.3 Step 3｜핵심 사용자와 문제 추정
- 핵심 사용자 후보를 2개 작성한다.
- 각 사용자가 서비스에 들어오기 전 가지고 있을 문제를 작성한다.
- 두 후보 중 서비스의 핵심 기능과 가장 잘 연결되는 사용자 1개를 선택한다.
- 선택한 사용자를 상황 + 목적 + 특징 구조로 다시 작성한다.
- 사용자 문제는 한 문장으로 정리한다.
---
### 1.4.4 Step 4｜핵심 기능 분류
- 대표 과업을 완료하면서 사용하는 기능을 순서대로 기록한다.
- 각 기능을 핵심 기능, 보조 기능, 운영 기능으로 분류한다.
- 핵심 기능은 4\~6개 수준으로 압축한다.
- 기능 이름 옆에 이 기능이 없다면 사용자가 무엇을 못하는가를 한 줄로 작성한다.
---
### 1.4.5 Step 5｜데이터 항목 찾기
- 목록 화면에서 반복되는 정보 항목을 표시한다.
- 상세화면에서 추가로 제공되는 정보 항목을 표시한다.
- 사용자가 선택하거나 저장하는 값이 있는지 확인한다.
- 최소 8개 이상의 데이터 항목 후보를 작성한다.
- 각 항목을 기본 데이터, 사용자 상태, 화면 표시용으로 임시 구분한다.
---
### 1.4.6 Step 6｜사용자 흐름 작성
- 대표 과업의 시작과 종료를 명확히 정한다.
- 중간 행동을 최소 5단계 이상 작성한다.
- 각 단계에서 사용자가 어떤 판단을 하는지 함께 적는다.
- 불필요하게 반복되는 이동이 있는지 확인한다.
- 사용자가 이전 단계로 돌아가야 하는 상황이 있는지 확인한다.
---
### 1.4.7 Step 7｜강점과 불편점 도출
- 강점은 최소 3개 작성한다.
- 불편점은 최소 3개 작성한다.
- 각각 반드시 관찰 근거를 한 줄 이상 붙인다.
- 화면이 예쁘다처럼 개인 취향 중심의 평가는 제외한다.
- 사용자가 목표를 더 빠르게 달성하거나 실수를 줄이는 데 도움이 되는지를 기준으로 판단한다.
---
### 1.4.8 Step 8｜한 문장 서비스 구조 정리
- 누가 + 어떤 문제를 해결하기 위해 + 어떤 데이터를 + 어떤 기능으로 활용하는 서비스인가의 구조로 작성한다.
- 예시｜교내 활동 정보를 찾기 어려운 대학생이 프로그램 데이터를 검색·필터·비교하여 자신에게 맞는 활동을 찾도록 돕는 서비스처럼 작성한다.
---
## 1.5 역분석 결과 점검
### 1.5.1 사용자 점검
- 핵심 사용자가 너무 넓게 정의되어 있지 않은지 확인한다.
- 사용자의 상황과 목적이 함께 적혀 있는지 확인한다.
---
### 1.5.2 문제 점검
- 문제 정의 안에 기능 이름이 들어가 있지 않은지 확인한다.
- 사용자의 실제 불편이나 필요가 드러나는지 확인한다.
---
### 1.5.3 기능 점검
- 모든 버튼을 기능으로 나열하지 않았는지 확인한다.
- 핵심 기능과 보조 기능이 구분되어 있는지 확인한다.
---
### 1.5.4 데이터 점검
- 실제 화면에서 반복되는 정보를 데이터 항목으로 찾았는지 확인한다.
- 기본 데이터와 사용자 상태를 구분하려고 시도했는지 확인한다.
---
### 1.5.5 흐름 점검
- 화면 이름만 나열하지 않았는지 확인한다.
- 사용자의 판단과 행동이 드러나는지 확인한다.
---
# 2. \[이론+실습\] 경쟁서비스와 시장 분석
## 2.1 경쟁서비스를 찾는 이유
### 2.1.1 경쟁서비스 분석의 목적
- 경쟁서비스 분석은 어떤 서비스가 더 좋은지 순위를 정하기 위한 활동이 아니다.
- 같은 문제를 서로 다른 서비스가 어떻게 해결하는지 비교해 선택 가능한 해결 패턴을 찾는 활동이다.
- 공통적으로 반복되는 기능은 기본 기대 기능일 가능성이 있다.
- 한 서비스에만 존재하는 기능은 특정 사용자나 상황을 위한 차별 요소일 수 있다.
- 여러 서비스에서 공통으로 나타나는 불편점은 새로운 프로젝트가 해결할 수 있는 기회가 될 수 있다.
---
### 2.1.2 경쟁서비스를 너무 좁게 보면 생기는 문제
- 같은 종류의 서비스만 비교하면 비슷한 기능만 반복해서 발견할 수 있다.
- 기존 시장의 구조를 그대로 따라가게 될 가능성이 높아진다.
- 사용자가 실제로 사용하는 다른 대안을 놓칠 수 있다.
- 새로운 해결 방식을 찾기 어려워질 수 있다.
---
## 2.2 경쟁서비스의 세 가지 범위
### 2.2.1 직접 경쟁
- 같은 사용자에게 비슷한 문제를 비슷한 방식으로 해결하는 서비스를 직접 경쟁으로 본다.
- 기능 구조와 화면 흐름을 비교하기 가장 쉽다.
- 예를 들어 대학생 공모전 탐색 서비스와 다른 공모전 정보 플랫폼은 직접 경쟁에 해당할 수 있다.
---
### 2.2.2 간접 경쟁
- 같은 문제를 해결하지만 다른 서비스 구조나 접근 방식을 사용하는 대안을 간접 경쟁으로 본다.
- 예를 들어 공모전 정보를 찾기 위해 검색엔진이나 SNS 해시태그를 이용한다면 간접 경쟁이 될 수 있다.
- 간접 경쟁은 사용자가 왜 전문 서비스를 사용하지 않는지 이해하는 데 도움이 된다.
---
### 2.2.3 대체재
- 디지털 서비스가 아니더라도 같은 목적을 달성하기 위해 사용하는 방법을 대체재로 본다.
- 친구 추천, 학과 단체채팅, 게시판 포스터, 메모장, 스프레드시트도 상황에 따라 대체재가 될 수 있다.
- 대체재가 계속 사용되는 이유를 찾으면 디지털 서비스가 놓치고 있는 장점을 발견할 수 있다.
---
## 2.3 비교 대상을 선정하는 기준
### 2.3.1 동일한 사용자 문제
- 서비스 형태가 달라도 사용자가 해결하려는 문제가 비슷한지 확인한다.
- 문제 자체가 다르면 비교 결과를 프로젝트에 적용하기 어렵다.
---
### 2.3.2 충분히 다른 해결 방식
- 기능과 구조가 완전히 같은 서비스만 고르지 않는다.
- 탐색 중심, 추천 중심, 콘텐츠 중심 등 서로 다른 접근을 포함하면 비교 가치가 높아진다.
---
### 2.3.3 실제 사용 가능한 서비스
- 현재 접속하거나 기능을 확인할 수 있는 서비스를 우선 선택한다.
- 오래된 리뷰나 종료된 서비스만으로 분석하지 않는다.
- 앱을 직접 설치할 수 없다면 공식 소개 화면과 최신 도움말 자료를 함께 확인한다.
---
### 2.3.4 비교 가능한 범위
- 모든 기능을 비교하지 않고 이번 프로젝트에 중요한 대표 과업을 기준으로 비교한다.
- 예를 들어 여행 전체 경험보다 조건에 맞는 장소 찾기처럼 비교 범위를 좁힌다.
---
## 2.4 경쟁서비스 비교 기준
### 2.4.1 핵심 사용자 비교
- 각 서비스가 누구를 주된 사용자로 가정하는지 추정한다.
- 같은 분야의 서비스라도 초보자, 전문가, 가격 민감 사용자, 빠른 결정을 원하는 사용자처럼 타깃이 다를 수 있다.
---
### 2.4.2 해결 문제 비교
- 각 서비스가 사용자의 어떤 어려움을 가장 먼저 해결하려는지 작성한다.
- 홈페이지 문구와 실제 기능이 같은 방향을 향하고 있는지 확인한다.
---
### 2.4.3 핵심 가치 비교
- 빠른 탐색, 폭넓은 정보, 신뢰도, 개인화, 비교 편의성, 기록 편의성 등 핵심 가치를 비교한다.
- 같은 기능이라도 어떤 가치를 강조하는지에 따라 화면 구조가 달라질 수 있다.
---
### 2.4.4 핵심 기능 비교
- 검색, 필터, 정렬, 상세보기, 비교, 저장, 추천 등 주요 기능을 같은 기준으로 표시한다.
- 단순히 있음/없음만 표시하지 않고 기능이 어떤 방식으로 제공되는지 짧게 기록한다.
---
### 2.4.5 정보구조 비교
- 메인 메뉴 수, 카테고리 구조, 탐색 진입점, 목록과 상세화면의 관계를 비교한다.
- 원하는 정보에 도달하기까지 몇 단계가 필요한지 확인한다.
---
### 2.4.6 검색과 필터 비교
- 검색어 입력 방식, 자동완성 여부, 필터 종류, 다중 선택 여부, 초기화 방법, 적용 결과 표시 방식을 비교한다.
- 필터가 많다고 항상 좋은 것은 아니며 사용자가 이해하고 조합하기 쉬운지를 확인한다.
---
### 2.4.7 상세화면 비교
- 상세화면에서 어떤 정보를 우선 배치하는지 확인한다.
- 목록에서 이미 본 정보와 상세에서 새롭게 제공하는 정보를 구분한다.
- 사용자의 다음 행동을 유도하는 버튼이 무엇인지 확인한다.
---
### 2.4.8 개인화와 저장 기능 비교
- 즐겨찾기, 최근 본 항목, 완료 상태, 선호 설정, 추천 기록 등을 확인한다.
- 개인화 기능이 실제 사용자 목표와 연결되는지 확인한다.
- 단순 저장 기능인지 이후 화면을 변화시키는 상태인지 구분한다.
---
### 2.4.9 빈 상태와 오류 상태 비교
- 검색 결과가 없을 때 어떤 메시지를 보여주는지 확인한다.
- 저장 목록이 비어 있을 때 무엇을 안내하는지 확인한다.
- 잘못된 입력이나 연결 실패 상황에서 사용자가 다음 행동을 알 수 있는지 확인한다.
- 정상 화면뿐 아니라 예외 상황을 설계하는 것도 서비스 품질의 일부로 본다.
---
### 2.4.10 접근성과 반응형 경험 비교
- 작은 화면에서도 핵심 기능을 사용할 수 있는지 확인한다.
- 텍스트가 너무 작거나 버튼 간격이 지나치게 좁지 않은지 살펴본다.
- 색상만으로 상태를 구분하는 요소가 있는지 확인한다.
- 이미지에 대체 설명이 필요한 상황을 생각해본다.
<callout icon="📌" color="blue_bg">
	- 접근성은 특정 사용자만을 위한 추가 기능이 아니라 더 많은 사용자가 서비스를 이해하고 조작할 수 있게 하는 기본 품질 요소로 본다.
	- 참고｜[W3C WAI Accessibility Introduction](https://www.w3.org/WAI/fundamentals/accessibility-intro/)
</callout>
---
## 2.5 실습｜유사 서비스 2\~3개 비교하기
### 2.5.1 Step 1｜대표 과업 통일
- 비교할 모든 서비스에서 동일한 과업을 수행한다.
- 예시｜조건에 맞는 프로그램을 찾아 상세정보를 확인하고 관심 항목으로 저장한다처럼 정한다.
- 서비스마다 다른 과업을 수행하면 비교 기준이 달라져 결과를 해석하기 어렵다.
---
### 2.5.2 Step 2｜비교 서비스 선정
- 직접 경쟁 서비스 1개 이상을 포함한다.
- 가능하면 간접 경쟁 또는 대체재 1개를 포함한다.
- 각 서비스를 선택한 이유를 한 줄로 작성한다.
---
### 2.5.3 Step 3｜첫 화면 비교
- 첫 화면에서 가장 강조되는 정보와 행동을 기록한다.
- 검색이나 탐색을 어디서 시작하는지 기록한다.
- 사용자가 서비스 목적을 이해하기 쉬운지 비교한다.
---
### 2.5.4 Step 4｜탐색 과정 비교
- 대표 과업을 실제로 수행한다.
- 클릭 또는 주요 행동 단계를 순서대로 기록한다.
- 중간에 막히거나 다시 돌아간 지점을 표시한다.
- 필요한 정보가 언제 처음 등장하는지 확인한다.

### 2.5.6 Step 6｜공통 기능 찾기
- 2개 이상의 서비스에서 반복되는 기능을 표시한다.
- 공통 기능이 왜 반복되는지 사용자 문제와 연결해 설명한다.
- 다들 있으니까 필요하다가 아니라 사용자가 많은 항목 중 원하는 정보를 좁혀야 하므로 필터가 반복된다처럼 작성한다.
---
### 2.5.7 Step 7｜차별 기능 찾기
- 특정 서비스만 제공하는 기능을 표시한다.
- 그 기능이 어떤 사용자에게 유용한지 추정한다.
- 차별 기능이 정말 핵심 가치를 만드는지 아니면 부가 기능인지 구분한다.
---
### 2.5.8 Step 8｜불편점 비교
- 한 서비스에서만 나타나는 불편과 여러 서비스에서 반복되는 불편을 구분한다.
- 반복되는 불편은 시장 전체에서 충분히 해결되지 않은 문제일 가능성이 있다.
- 불편점마다 근거 화면 또는 행동 단계를 연결한다.
---
### 2.5.9 Step 9｜프로젝트 시사점 작성
- 반드시 가져오고 싶은 구조나 기능을 작성한다.
- 개선해서 적용하고 싶은 부분을 작성한다.
- 우리 프로젝트에서는 제외하고 싶은 부분을 작성한다.
- 단순 복제가 아니라 왜 가져오고 왜 바꾸는지를 한 줄씩 설명한다.
---
## 2.6 시장 분석을 프로젝트 관점에서 이해하기
### 2.6.1 이번 수업에서 말하는 시장 분석
- 이번 수업의 시장 분석은 기업 가치, 매출 규모, 투자 규모를 계산하는 활동이 아니다.
- 사용자가 어떤 문제를 가지고 있고 어떤 방식의 서비스를 선택하는지를 파악하는 활동이다.
- 프로젝트 규모가 작기 때문에 거대한 산업 전체보다 우리가 다룰 수 있는 사용자와 사용 상황을 중심으로 조사한다.
- 이 시장이 큰가보다 이 문제가 실제로 반복되는가, 사람들이 어떤 대안을 사용하고 있는가, 어떤 정보와 기능을 기대하는가를 확인한다.
---
### 2.6.2 확인해야 할 네 가지 질문
- 이 문제를 해결하려는 서비스가 실제로 여러 개 존재하는가
- 사용자들은 어떤 검색어와 표현을 사용해 이 문제를 찾는가
- 기존 서비스는 어떤 기능을 기본적으로 제공하는가
- 기존 해결 방식에서 반복되는 불편이나 비어 있는 영역이 있는가

## 2.7 Google Trends를 활용한 관심도 조사
### 2.7.1 Google Trends에서 확인할 수 있는 것
- 특정 검색어에 대한 상대적 관심도의 변화를 확인할 수 있다.
- 두 개 이상의 검색어를 비교할 수 있다.
- 기간과 지역을 변경해 관심도 차이를 살펴볼 수 있다.
- 연관 검색어를 통해 사용자가 어떤 표현을 함께 검색하는지 참고할 수 있다.
---
### 2.7.2 Google Trends에서 확인할 수 없는 것
- 표시되는 숫자를 실제 검색 횟수로 해석하지 않는다.
- 검색 관심도가 높다고 자동으로 좋은 프로젝트 주제가 되는 것은 아니다.
- 검색량만으로 사용자의 구체적인 문제를 알 수 없다.
- 관심도가 낮아도 특정 사용자에게 중요한 문제일 수 있다.
---
### 2.7.3 실습 방법
- 프로젝트와 관련된 키워드 후보 2\~3개를 입력한다.
- 대한민국 기준으로 지역을 설정한다.
- 최근 12개월과 최근 5년을 각각 비교해본다.
- 키워드별 관심도 변화가 다른지 확인한다.
- 급격한 상승이나 하락이 있다면 그 시기의 이유를 추가로 조사한다.
- 연관 검색어에서 반복되는 표현을 3개 이상 기록한다.
- 결과 화면을 캡처하고 조사 날짜를 함께 기록한다.

# 3. \[이론+실습\] UI·UX 트렌드 조사와 프로젝트 기회 영역 도출
## 3.1 트렌드를 조사하는 이유
### 3.1.1 트렌드는 유행 목록이 아니다.
- 트렌드는 단순히 최근 많이 보이는 색상이나 디자인 스타일을 모으는 활동이 아니다.
- 여러 서비스에서 반복되는 정보 구조, 상호작용 방식, 사용자 기대를 관찰하는 활동으로 이해한다.
- 새로운 기술을 사용한다는 이유만으로 좋은 트렌드라고 판단하지 않는다.
- 사용자의 목적 달성에 실제로 어떤 도움이 되는지를 함께 살펴본다.
---
### 3.1.2 프로젝트에서 트렌드를 활용하는 방법
- 그대로 따라 하기보다 우리 사용자의 문제와 연결되는 요소만 선택한다.
- 구현 가능성을 함께 고려한다.
- 이번 수업의 프로젝트 범위에서 JavaScript, JSON, LocalStorage로 구현 가능한지 판단한다.
- 백엔드, 로그인, 실시간 동기화가 반드시 필요한 기능은 아이디어 단계에서 분리한다.
---
## 3.2 기능 트렌드 관찰
### 3.2.1 탐색 기능
- 검색창의 위치와 형태를 확인한다.
- 카테고리 탐색과 검색이 함께 제공되는지 확인한다.
- 추천 키워드나 인기 항목을 제공하는지 확인한다.
- 검색 결과에서 다시 조건을 변경하기 쉬운지 확인한다.
---
### 3.2.2 필터와 정렬
- 필터 조건이 어떤 데이터 속성과 연결되는지 확인한다.
- 필터를 여러 개 동시에 선택할 수 있는지 확인한다.
- 현재 선택된 조건을 사용자가 쉽게 확인할 수 있는지 살펴본다.
- 전체 초기화가 가능한지 확인한다.
- 정렬 기준이 사용자의 실제 의사결정과 연결되는지 확인한다.
---
### 3.2.3 상세보기
- 목록에서 보여주는 정보와 상세에서 추가하는 정보를 구분한다.
- 상세페이지에서 사용자가 가장 먼저 확인하는 정보를 추정한다.
- 다음 행동 버튼이 어디에 배치되어 있는지 확인한다.
- 긴 정보를 섹션, 탭, 아코디언 등으로 나누는 방식을 관찰한다.
---
### 3.2.4 개인화
- 즐겨찾기, 최근 본 항목, 저장 목록, 완료 상태와 같은 기능을 관찰한다.
- 저장한 결과가 이후 화면에 어떤 영향을 주는지 확인한다.
- 단순히 데이터를 저장하는지, 개인화된 화면으로 재구성하는지 구분한다.
- 우리 프로젝트에서는 LocalStorage를 공동 데이터베이스가 아니라 개인 브라우저 상태로 사용한다는 점을 기억한다.
---
### 3.2.5 상태 안내
- 로딩 중, 결과 없음, 오류 발생, 저장 완료, 삭제 확인 등의 상태 표현을 관찰한다.
- 사용자가 현재 서비스가 어떤 상태인지 이해할 수 있는지 확인한다.
- 정상적인 성공 화면만 설계하는 서비스보다 예외 상황까지 안내하는 서비스가 더 완성도가 높다는 점을 이해한다.
---
## 3.3 UI 구조 트렌드 관찰
### 3.3.1 카드형 정보 구조
- 반복되는 데이터를 일정한 형식으로 보여줄 때 카드 구조를 많이 활용한다.
- 카드 안에 모든 정보를 넣기보다 탐색 단계에서 필요한 핵심 정보만 선택한다.
- 프로젝트에서는 JSON 항목 하나가 카드 하나로 연결될 수 있다.
---
### 3.3.2 태그와 배지
- 카테고리, 상태, 대상, 특징을 빠르게 구분할 때 태그와 배지를 활용한다.
- 색상만으로 의미를 전달하지 않고 텍스트를 함께 제공하는 것이 좋다.
- 필터 조건과 태그 데이터가 연결될 수 있다.
---
### 3.3.3 고정된 행동 영역
- 모바일 화면에서는 주요 버튼을 화면 하단이나 고정 영역에 배치하는 경우가 있다.
- 사용자가 긴 내용을 본 뒤에도 주요 행동에 쉽게 접근하도록 돕는다.
- 모든 버튼을 고정하는 것이 아니라 가장 중요한 행동을 선택한다.
---
### 3.3.4 반응형 우선순위
- 작은 화면에서는 모든 정보를 동일하게 유지하기보다 우선순위가 낮은 정보를 줄이거나 재배치한다.
- 데스크톱과 모바일에서 사용자 목표는 같지만 화면 공간과 조작 방식이 다르다는 점을 고려한다.
---
## 3.4 트렌드 근거 수집 방법
### 3.4.1 한 서비스에서 끝내지 않기
- 하나의 서비스에서 발견한 특징을 바로 트렌드라고 부르지 않는다.
- 최소 3개 이상의 서로 다른 서비스에서 반복되는지 확인한다.
- 반복 여부와 함께 왜 사용되는지 추정한다.
---
### 3.4.2 화면 캡처 기록
- 트렌드 근거가 되는 화면을 캡처한다.
- 서비스명, 화면명, 조사 날짜를 함께 기록한다.
- 어떤 특징을 보여주는 캡처인지 한 줄로 설명한다.
---
### 3.4.3 출처 기록
- 공식 서비스 화면, 공식 도움말, 공개 리서치 자료를 우선 사용한다.
- 블로그나 SNS 자료를 사용할 경우 작성 주체와 게시 시점을 확인한다.
- 수치가 포함된 자료는 출처 링크와 조사 시점을 반드시 기록한다.
---
## 3.5 실습｜트렌드 증거 카드 만들기
### 3.5.1 Step 1｜트렌드 후보 선택
- 이번 프로젝트에 중요할 가능성이 있는 기능 또는 UI 구조를 3개 선택한다.
- 예시｜다중 필터, 저장 목록, 상세정보 구조, 빈 상태 안내 등으로 정할 수 있다.
---
### 3.5.2 Step 2｜서비스별 근거 찾기
- 각 트렌드 후보마다 최소 3개의 서비스에서 사례를 찾는다.
- 같은 서비스의 다른 화면 3개를 근거로 사용하지 않는다.
- 서로 다른 서비스에서 반복되는지를 확인한다.
---
### 3.5.3 Step 3｜공통 패턴 작성
- 세 서비스가 공통으로 사용하는 구조를 한 문장으로 작성한다.
- 예시｜필터 적용 후 선택된 조건을 칩 형태로 표시해 현재 검색 상태를 보여준다처럼 작성한다.
---
### 3.5.4 Step 4｜사용자 가치 작성
- 이 패턴이 어떤 사용자 문제를 줄이는지 작성한다.
- 요즘 많이 쓴다가 아니라 사용자가 현재 적용된 조건을 잊지 않도록 돕는다처럼 설명한다.
---
### 3.5.5 Step 5｜우리 프로젝트 적용 가능성 판단
- 순수 JavaScript로 구현 가능한지 확인한다.
- JSON 데이터 구조가 필요한지 확인한다.
- LocalStorage가 필요한지 확인한다.
- 백엔드가 없어도 구현 가능한지 확인한다.
- 구현 난이도를 낮음 / 보통 / 높음으로 표시한다.
---
## 3.6 기회 영역을 도출하는 방법
### 3.6.1 기회 영역이란 무엇인가
- 기회 영역은 단순히 새로운 기능을 하나 추가하는 아이디어가 아니다.
- 기존 서비스가 충분히 해결하지 못한 사용자 문제 또는 특정 사용자가 더 나은 방식으로 해결할 수 있는 영역으로 이해한다.
- 기능보다 문제와 사용자 상황을 먼저 작성한다.
---
### 3.6.2 기회 영역의 세 가지 출발점
- 여러 서비스에서 반복되는 불편점에서 출발한다.
- 특정 사용자 집단이 기존 서비스에서 충분히 고려되지 않는 상황에서 출발한다.
- 데이터가 있지만 사용자가 원하는 방식으로 탐색하거나 비교하기 어려운 상황에서 출발한다.
---
### 3.6.3 좋지 않은 기회 영역 예시
- 다크모드를 추가한다.
- 필터를 더 많이 넣는다.
- 즐겨찾기를 만든다.
- UI를 더 예쁘게 만든다.
- 위 표현은 기능이나 디자인 아이디어일 뿐 어떤 사용자 문제를 해결하는지 드러나지 않는다.
---
### 3.6.4 좋은 기회 영역 예시
- 신입생은 비교과 프로그램의 대상 조건과 일정을 한눈에 비교하기 어려우므로 자신이 참여 가능한 프로그램만 빠르게 좁혀볼 수 있는 탐색 경험이 필요하다.
- 자격증 준비를 시작한 학생은 시험 일정과 난이도, 관련 직무를 여러 사이트에서 따로 확인하므로 하나의 데이터 구조에서 비교할 수 있는 경험이 필요하다.
- 반려동물 동반 장소 정보는 장소마다 허용 조건이 다르게 표시되어 방문 전 확인이 어렵기 때문에 조건 중심으로 필터링하고 개인 관심 목록으로 관리할 필요가 있다.
---
## 3.7 분석 결과를 프로젝트 후보로 연결하기
### 3.7.1 서비스에서 발견한 문제 정리
- 오늘 분석한 서비스의 반복 불편점 중 프로젝트로 다뤄볼 가치가 있는 것을 3개 선택한다.
- 각 문제마다 어떤 사용자가 영향을 받는지 작성한다.
- 기존 서비스에서 왜 충분히 해결되지 않는지 추정한다.
---
### 3.7.2 데이터 가능성 확인
- 해결하려는 문제에 필요한 데이터가 무엇인지 적는다.
- 최종 프로젝트 기준으로 기본 데이터 30건 이상을 구성할 수 있는 주제인지 확인한다.
- 각 항목에 검색과 필터에 사용할 수 있는 속성이 충분한지 확인한다.
- 데이터가 지나치게 개인적이거나 실시간 갱신이 필수인 주제는 제외 후보로 표시한다.
---
### 3.7.3 기술 범위 확인
- 서버 없이 구현 가능한지 확인한다.
- 여러 사용자가 같은 데이터를 실시간으로 공유해야 하는 서비스인지 확인한다.
- 실제 로그인이나 결제가 반드시 필요한지 확인한다.
- 공동 게시판이나 실시간 채팅처럼 공유 DB가 핵심인 주제는 이번 과목 범위에 적합하지 않다.
- JSON 기반 기본 데이터와 LocalStorage 기반 개인화 상태로 핵심 경험을 만들 수 있는지 확인한다.
---
### 3.7.4 3주차로 넘길 후보 만들기
- 팀프로젝트로 발전시켜 볼 수 있는 문제 영역 후보를 개인별로 2개 이상 작성한다.
- 아직 최종 주제를 확정하지 않는다.
- 3주차에는 사용자 분석을 통해 후보를 구체화하고 팀별 1·2·3순위 주제를 선정한다.
- 이후 5\~12주차에 공통 레퍼런스 프로젝트로 진행할 영화·도서 콘텐츠 탐색, 여행지 탐색, 학습 콘텐츠·목표 관리와 동일하거나 매우 유사한 주제는 최종 팀프로젝트 후보에서 제외한다.
- 이 세 주제는 팀프로젝트 후보가 아니라 구현 패턴을 함께 익히기 위한 수업용 공통 실습이라는 점을 미리 안내한다.
<callout icon="💡" color="yellow_bg">
	- 2주차에서는 프로젝트 이름을 빨리 정하는 것보다 어떤 사용자가 어떤 문제를 겪고 있는가에 대한 근거를 많이 확보하는 것이 중요하다.
	- 3주차에 약 30개의 팀프로젝트 예시 주제를 함께 살펴보고 팀별 후보 3개를 선정하므로 이번 주에는 문제와 기회 영역을 넓게 수집한다.
</callout>
---
## 3.8 팀 토의｜분석 결과 공유
### 3.8.1 개인 분석 공유
- 각자 분석한 서비스의 핵심 사용자와 문제를 설명한다.
- 가장 인상적이었던 핵심 기능 1개를 설명한다.
- 반복적으로 발견한 불편점 1개를 설명한다.
---
### 3.8.2 공통 문제 묶기
- 팀원들이 발견한 불편점 중 비슷한 내용을 묶는다.
- 표현은 다르지만 같은 문제를 설명하는 항목은 하나로 통합한다.
- 공통 문제가 어떤 사용자 상황에서 발생하는지 작성한다.
---
### 3.8.3 프로젝트 가능성 평가
- 문제의 중요성을 낮음 / 보통 / 높음으로 표시한다.
- 데이터 확보 가능성을 낮음 / 보통 / 높음으로 표시한다.
- 이번 기술 범위에서 구현 가능성을 낮음 / 보통 / 높음으로 표시한다.
- 세 항목이 모두 낮은 문제는 다음 주 후보에서 우선 제외한다.
---
# 2주차 핵심 정리
- 서비스 역분석은 화면을 평가하는 활동이 아니라 사용자 문제, 가치, 기능, 데이터, 흐름을 거꾸로 추론하는 활동이다.
- 관찰 가능한 사실과 분석자의 추정을 구분해야 한다.
- 기능은 이름만 나열하지 않고 어떤 사용자 문제를 해결하는지 연결해야 한다.
- 데이터는 화면에 반복되는 기본 데이터와 사용자 행동에 따라 달라지는 상태로 구분해 생각할 수 있다.
- 경쟁서비스는 직접 경쟁뿐 아니라 간접 경쟁과 대체재까지 살펴보면 더 다양한 해결 방식을 발견할 수 있다.
- 비교는 반드시 동일한 대표 과업과 동일한 기준으로 수행한다.
- 시장 분석은 시장 규모 계산보다 사용자의 선택 방식, 반복 문제, 기존 대안을 이해하는 데 초점을 둔다.
- 트렌드는 한 서비스의 특징이 아니라 여러 서비스에서 반복되는 패턴과 사용자 기대를 근거로 판단한다.
- 좋은 기회 영역은 새로운 기능 이름이 아니라 기존 서비스가 충분히 해결하지 못한 사용자 문제로 표현한다.
- 이번 주 분석 결과는 3주차 사용자 분석과 팀프로젝트 주제 선정의 직접적인 근거가 된다.
---
# 이번 주차 작업되어야 할 산출물
- 서비스 역분석 보고서 1부를 작성한다.
- 경쟁서비스 2\~3개 비교표를 작성한다.
- 대표 사용자 흐름 1개를 작성한다.
- 서비스별 강점과 불편점 근거를 각각 정리한다.
- UI·UX 또는 기능 트렌드 증거 카드 3개 이상을 작성한다.
- 시장·관심도 조사 자료와 출처를 기록한다.
- 프로젝트 기회 영역 후보를 최소 2개 작성한다.
- 3주차 팀프로젝트 주제 검토에 사용할 개인 문제 영역 후보 2개 이상을 준비한다.
<callout icon="📌" color="blue_bg">
	- 매주차 산출물을 별도로 제출하거나 체크하지 않으며 최종 팀 프로젝트 완료 시 한꺼번에 취합한다.
	- 매주 작업한 문서와 캡처, 링크, 분석표를 잃어버리지 않도록 팀 프로젝트 폴더에 주차별로 정리한다.
</callout>
