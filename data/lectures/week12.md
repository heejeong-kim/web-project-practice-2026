# 1. \[이론+실습\] LocalStorage 개인화 기능 완성
## 1.1 개인화 상태의 생명주기
### 1.1.1 저장 기능은 다섯 단계로 확인하기
- 사용자 행동이 발생한다.
- 현재 저장 상태를 읽는다.
- 새로운 상태를 계산한다.
- LocalStorage에 저장한다.
- 화면을 다시 렌더링해 변경 결과를 보여준다.
- 저장만 되고 화면이 바뀌지 않거나 화면만 바뀌고 저장되지 않는 상태를 피한다.
---
### 1.1.2 즐겨찾기 전체 흐름
- 사용자가 카드 또는 상세화면의 즐겨찾기 버튼을 누른다.
- 현재 즐겨찾기 ID 배열을 불러온다.
- 선택 ID가 이미 있는지 확인한다.
- 있으면 제거하고 없으면 추가한다.
- 새로운 배열을 저장한다.
- 목록과 상세의 즐겨찾기 아이콘을 모두 갱신한다.
---
## 1.2 여러 화면에서 상태 동기화
### 1.2.1 목록과 상세가 다르게 보이는 문제
- 목록에서 즐겨찾기를 해제했는데 상세에서는 계속 활성 상태로 보이면 사용자는 어느 상태가 맞는지 알 수 없다.
- 화면마다 별도의 상태를 만들지 않고 LocalStorage의 현재 값을 기준으로 다시 그리는 구조를 사용한다.
---
### 1.2.2 사용자 상태를 한 번 읽고 재사용하기
```javascript
const userState = {
  favorites: loadStoredArray('favorites'),
  recent: loadStoredArray('recent'),
  completed: loadStoredArray('completed')
};

function isFavorite(id) {
  return userState.favorites.includes(id);
}
```
- 렌더링할 때마다 LocalStorage를 반복 조회하기보다 화면 초기화 시 사용자 상태를 한 번 읽어 메모리에 보관한다.
- 즐겨찾기 상태가 바뀌면 userState.favorites와 LocalStorage를 함께 갱신한 뒤 화면을 다시 렌더링한다.
- 카드와 상세화면 모두 같은 userState를 사용하면 상태 판단 기준을 통일할 수 있다.
---
## 1.3 개인화 기능 세 가지 이상 구성
### 1.3.1 추천 조합
- 즐겨찾기 + 최근 본 항목 + 필터 설정 기억
- 즐겨찾기 + 완료 상태 + 개인 메모
- 관심 목록 + 최근 본 항목 + 보기 방식 설정
- 프로젝트 목적에 맞는 조합을 선택한다.
---
### 1.3.2 단순 기능 개수보다 연결성 확인
- 최근 본 항목을 누르면 상세보기로 이동되는가
- 즐겨찾기 목록에서 원본 JSON 정보를 정상적으로 다시 보여주는가
- 완료 상태를 변경하면 전체 목록과 완료 목록이 함께 바뀌는가
- 저장한 필터 설정이 다음 방문 때 탐색을 실제로 편하게 만드는가
---
## 1.4 개인 메모와 사용자 입력
### 1.4.1 메모를 저장할 때
- 메모가 어느 데이터에 연결되는지 ID를 함께 관리한다.
- 빈 메모를 저장할지 삭제로 처리할지 규칙을 정한다.
- 너무 긴 입력이나 예상하지 못한 값에 대한 기준을 정할 수 있다.
---
### 1.4.2 메모 저장과 불러오기 예시
```javascript
function loadNotes() {
  const saved = localStorage.getItem('notes');
  if (!saved) return {};

  try {
    const parsed = JSON.parse(saved);
    return parsed && typeof parsed === 'object' && !Array.isArray(parsed)
      ? parsed
      : {};
  } catch (error) {
    console.error('메모 데이터를 읽을 수 없습니다', error);
    return {};
  }
}

function saveNote(id, text) {
  const notes = loadNotes();
  const trimmedText = text.trim();

  if (!trimmedText) {
    delete notes[id];
  } else {
    notes[id] = trimmedText;
  }

  localStorage.setItem('notes', JSON.stringify(notes));
}
```
- 데이터 ID를 키처럼 사용해 항목별 개인 메모를 연결한다.
- 빈 문자열은 메모 삭제로 처리하는 규칙을 사용할 수 있다.
- 저장 규칙을 정한 뒤 상세화면의 입력 폼과 연결한다.

# 2. \[실습\] 공통 프로젝트 C 개인화 화면 통합
## 2.1 전체·완료·미완료·즐겨찾기 보기
### 2.1.1 기본 데이터와 사용자 상태 결합
- 전체 보기는 JSON 데이터 전체를 사용한다.
- 완료 보기는 완료 ID에 포함된 데이터만 골라 보여준다.
- 미완료 보기는 완료 ID에 포함되지 않은 데이터만 보여준다.
- 즐겨찾기 보기는 즐겨찾기 ID에 포함된 데이터만 보여준다.
---
### 2.1.2 ID 목록으로 데이터 찾기
```javascript
function getItemsByIds(items, ids) {
  return items.filter(item => ids.includes(item.id));
}
```
- LocalStorage에는 ID만 저장하고 실제 카드 내용은 JSON 원본에서 가져오는 구조를 유지한다.
---
## 2.2 최근 본 목록 제한
### 2.2.1 최근 5개 유지 예시
```javascript
function saveRecent(id) {
  const saved = localStorage.getItem('recent');
  const recent = saved ? JSON.parse(saved) : [];
  const next = [id, ...recent.filter(itemId => itemId !== id)].slice(0, 5);
  localStorage.setItem('recent', JSON.stringify(next));
}
```
- 최신 항목을 앞으로 이동한다.
- 중복을 제거한다.
- 필요한 개수만 유지한다.
---
## 2.3 저장 데이터 초기화
### 2.3.1 초기화가 필요한 이유
- 테스트 과정에서 이전 저장 상태 때문에 결과가 다르게 보일 수 있다.
- 발표용 환경에서 저장값이 없을 수 있다.
- 초기 상태와 저장된 상태를 모두 시험해야 한다.
---
### 2.3.2 초기화 기능 주의
- 전체 초기화 버튼은 사용자가 실수로 누르지 않도록 명확하게 표시한다.
- 필요하면 확인 절차를 제공한다.
- 특정 기능만 초기화할지 전체 개인화 상태를 초기화할지 구분한다.
---
# 3. \[이론+선택실습\] 심화 트랙 A｜외부 API 연결
## 3.1 응용 프로그램 인터페이스(Application Programming Interface, API)
### 3.1.1 API를 사용하는 이유
- 우리 프로젝트가 직접 보유하지 않은 최신 데이터를 외부 서비스에서 받을 수 있다.
- 공공데이터, 날씨, 행사, 지도 관련 정보처럼 지속적으로 바뀌는 데이터에 활용할 수 있다.
- API를 사용한다고 자동으로 서비스가 좋아지는 것은 아니며 핵심 사용자 문제와 직접 연결되어야 한다.
---
### 3.1.2 기본 데이터 흐름
- 사용자 또는 페이지가 데이터를 요청한다.
- JavaScript가 외부 API에 요청(Request)을 보낸다.
- API가 응답(Response)을 반환한다.
- JSON 형태의 응답을 우리 내부 데이터 구조로 변환한다.
- 기존 렌더링 함수에 전달한다.
---
## 3.2 fetch로 외부 데이터 요청
### 3.2.1 실제 실행 가능한 공개 API 예시
- 수업에서는 회원가입이나 비밀 키 없이 바로 호출할 수 있는 Open-Meteo 날씨 API로 요청·응답 구조를 먼저 연습할 수 있다.
- 아래 예시는 서울 좌표의 현재 기온과 강수량을 JSON으로 요청한다.
```javascript
async function loadSeoulWeather() {
  const url = 'https://api.open-meteo.com/v1/forecast?latitude=37.5665&longitude=126.9780&current=temperature_2m,precipitation&timezone=Asia%2FSeoul';

  try {
    const response = await fetch(url);

    if (!response.ok) {
      throw new Error(`HTTP ${response.status}`);
    }

    const data = await response.json();

    return {
      temperature: data.current.temperature_2m,
      precipitation: data.current.precipitation,
      time: data.current.time
    };
  } catch (error) {
    console.error('날씨 데이터를 불러오지 못했습니다', error);
    return null;
  }
}
```
- 외부 API의 응답 구조를 그대로 화면에 사용하기보다 우리 서비스에서 필요한 내부 데이터 구조로 변환한 뒤 렌더링 함수에 전달한다.
- 실제 팀 프로젝트에서는 프로젝트 주제와 직접 관련된 API를 선택하고 공식 문서에서 요청 파라미터, 호출 제한, 라이선스, CORS, 키 공개 가능 여부를 확인한다.
- 참고｜[Open-Meteo Forecast API 공식 문서](https://open-meteo.com/en/docs)
---
### 3.2.2 API 키(API Key)
- 일부 API는 사용자를 식별하기 위해 API 키를 요구한다.
- 공개 GitHub 저장소의 JavaScript 파일에 비밀 키를 그대로 넣으면 외부에 노출될 수 있다.
- 브라우저에서 직접 사용하도록 설계된 공개 키인지 비밀 키인지 공식 문서를 확인한다.
- 비밀 키가 필요한 서비스는 프론트엔드만으로 안전하게 사용할 수 없는 경우가 있으므로 다른 API를 선택하거나 서버 구성을 별도로 고려한다.
---

# 4. \[이론+선택실습\] 심화 트랙 B｜클라우드 데이터베이스
## 4.1 클라우드 데이터베이스(Cloud Database)가 필요한 경우
### 4.1.1 LocalStorage와 다른 점
- 여러 사용자에게 같은 데이터가 보여야 한다.
- 다른 기기에서 접속해도 저장 상태가 유지되어야 한다.
- 사용자가 등록한 데이터가 다른 사용자에게도 보여야 한다.
- 이런 요구가 핵심일 때 클라우드 DB를 고려한다.
---
### 4.1.2 선택 가능한 서비스 예시
- Supabase
- Firebase
- 수업에서는 직접 서버를 구축하기보다 서비스형 백엔드(Backend as a Service, BaaS)를 활용하는 방식을 선택할 수 있다.
---
## 4.2 기본 데이터 작업
### 4.2.1 생성·조회·수정·삭제(Create, Read, Update, Delete, CRUD)
- Create는 새로운 데이터를 추가한다.
- Read는 저장된 데이터를 조회한다.
- Update는 기존 데이터를 변경한다.
- Delete는 데이터를 삭제한다.
- 심화 트랙은 먼저 조회와 추가처럼 프로젝트에 필요한 최소 작업부터 적용한다.
---
### 4.2.2 데이터베이스 테이블 설계
- JSON 데이터 명세를 기반으로 필드 구조를 만든다.
- ID, 제목, 카테고리처럼 이미 정의한 내부 데이터 모델을 가능한 한 유지한다.
- 사용자 개인 데이터와 서비스 공통 데이터를 구분한다.
---
## 4.3 보안 규칙(Security Rules)과 권한
### 4.3.1 모든 데이터를 공개로 두지 않기
- 클라우드 DB를 연결할 때 누구나 모든 데이터를 수정·삭제할 수 있는 상태로 배포하면 안 된다.
- 서비스별 보안 규칙과 접근 권한을 확인한다.
- 인증을 적용하지 않는 프로젝트라면 읽기만 공개하고 쓰기는 제한하는 구조도 검토한다.
- 실제 개인정보와 민감 정보는 수업 프로젝트 데이터로 사용하지 않는다.
---
# 5. \[실습\] 트랙 선택과 프로젝트 적용
## 5.1 심화 기능 선택 질문
### 5.1.1 API가 필요한가
- 데이터가 자주 변경되는가
- 수동 JSON 업데이트로는 서비스 가치가 크게 떨어지는가
- 사용할 수 있는 공식 또는 신뢰 가능한 API가 존재하는가
- 호출 제한과 키 관리가 수업 범위에서 가능한가
---
### 5.1.2 클라우드 DB가 필요한가
- 여러 사용자가 같은 데이터를 공유해야 하는가
- 다른 기기에서도 같은 상태를 봐야 하는가
- 데이터 등록·수정이 서비스 핵심 흐름인가
- 공유 기능이 없어도 서비스가 성립한다면 우선 필수 트랙을 유지할 수 있는가
---
## 5.2 선택 후 구현 범위 제한
### 5.2.1 API 선택 팀
- API 한 개부터 연결한다.
- 필요한 응답 필드만 사용한다.
- 기존 내부 데이터 구조로 변환한다.
- 로딩과 실패 상태를 구현한다.
---
### 5.2.2 클라우드 DB 선택 팀
- 테이블 한 개 또는 핵심 데이터 구조부터 시작한다.
- 조회와 추가 등 핵심 동작부터 검증한다.
- 권한과 보안 설정을 확인한다.
- 필수 트랙 기능이 깨지면 심화 범위를 줄인다.
---
### 5.2.3 심화 기능을 선택하지 않는 팀
- LocalStorage 개인화 기능 3개 이상을 안정적으로 완성한다.
- 사용자 흐름과 빈 상태·오류 상태를 개선한다.
- 도메인 특화 핵심 기능의 완성도를 높인다.
---
# 12주차 핵심 정리
- LocalStorage는 개인화 기능을 구현하는 브라우저 저장소이며 여러 사용자 공유 DB가 아니다.
- 개인화 기능은 저장 자체보다 목록·상세·마이 화면이 같은 상태를 보여주는 것이 중요하다.
- API는 외부 최신 데이터를 가져오는 데 사용하고 클라우드 DB는 공유·동기화 데이터가 필요할 때 사용한다.
- 심화 기술은 프로젝트 문제 때문에 필요할 때만 선택한다.
- API 키와 클라우드 DB 권한 설정은 실제 배포 전에 반드시 확인한다.
