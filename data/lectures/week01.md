## 1.1 웹페이지에서 웹서비스로
웹프로젝트를 시작할 때 가장 먼저 구분해야 할 것은 무엇을 보여주는가와 사용자가 무엇을 할 수 있는가의 차이임. 웹페이지는 브라우저에서 보는 하나의 문서나 화면이고, 웹사이트는 여러 웹페이지가 하나의 목적과 정보구조로 연결된 형태를 의미
학과 소개 페이지나 행사 안내 페이지처럼 정해진 정보를 읽는 것이 중심이라면 정보 제공형 웹페이지에 가까움. 대학 홈페이지처럼 페이지가 많더라도 사용자의 주요 행동이 메뉴 이동과 정보 확인이라면 웹사이트의 성격이 강함
반대로 화면이 하나뿐이어도 사용자가 검색어를 입력하고 조건을 선택하며 그에 따라 결과가 달라지고, 관심 항목을 저장할 수 있다면 웹서비스의 성격을 가질 수 있음. 따라서 페이지 수보다 중요한 기준은 사용자의 행동이 데이터와 연결되는가임

## 1.2 웹서비스는 무엇이 다른가
웹서비스는 사용자가 특정 목적을 달성하도록 **정보·기능·데이터·상호작용**이 연결된 구조임. 화면 자체보다 중요한 것은 사용자가 왜 들어왔고, 어떤 행동을 거쳐 목표를 완료하는지임
예를 들어 지도 서비스의 핵심은 지도를 보여주는 것이 아니라 장소를 검색하고 조건을 비교해 이동할 목적지를 결정하도록 돕는 데 있음. 카페 탐색 서비스도 카페 사진을 나열하는 데서 끝나는 것이 아니라 사용자가 지역·가격·운영시간·편의시설을 기준으로 후보를 좁히고 저장할 수 있어야 함
**웹서비스의 기본 흐름**
사용자 입력·선택 → JavaScript 처리 → 데이터 검색·필터·정렬 → 화면 결과 변경 → 필요하면 사용자 상태 저장
이 흐름에서는 같은 화면을 보더라도 검색어, 필터 조건, 저장 상태가 다르면 서로 다른 결과를 볼 수 있음. 화면에 모든 정보를 고정해 두는 대신 데이터를 별도로 관리하고 JavaScript가 필요한 결과를 선택해 보여주기 때문

### 1.2.1 웹서비스를 바라보는 네 가지 질문
서비스를 분석할 때 화면의 색상이나 디자인부터 보기보다 사용자·문제·행동·데이터의 네 가지 질문을 먼저 확인하면 구조가 선명해짐
**① 누가 사용하는가**
대학생처럼 넓은 표현보다 “공강 시간에 참여할 비교과 프로그램을 찾는 1학년 학생”처럼 상황과 목적이 드러나게 정의
**② 무엇을 해결하는가**
“검색 기능이 필요함”처럼 기능을 문제로 쓰기보다 “정보가 여러 곳에 흩어져 있어 자신에게 맞는 프로그램을 빠르게 찾기 어려움”처럼 사용자의 불편을 설명
**③ 어떤 행동을 하는가**
검색 → 필터 → 비교 → 상세 확인 → 관심 항목 저장처럼 목표 달성까지의 행동 흐름을 실제 순서로 살펴봄
**④ 어떤 데이터를 사용하는가**
제목, 카테고리, 일정, 장소, 이미지, 설명처럼 모든 사용자에게 공통인 정보와 즐겨찾기, 최근 본 항목, 설정처럼 사용자마다 달라지는 상태를 구분

### 1.4.1 카페 라온 소개 페이지
카페 라온 소개 페이지의 목적은 한 개의 카페에 대한 정보를 전달하는 것임. 카페명, 위치, 운영시간, 대표 메뉴, 가격, 연락처와 소개 문구가 HTML 안에 직접 작성되어 있다면 사용자는 정보를 읽고 지도나 SNS 링크를 선택하는 정도의 행동을 수행

### 1.4.2 카페 탐색 서비스
카페 탐색 서비스는 여러 카페 중 사용자의 조건에 맞는 후보를 찾도록 돕는 것이 목적임. 학교 근처에서 공부할 카페를 찾는 대학생을 사용자로 가정하면 지역, 가격대, 운영시간, 콘센트·와이파이 여부와 같은 정보가 검색과 필터에 사용됨
최종 프로젝트에서는 30건 이상의 카페 데이터를 JSON으로 준비하고, 각 항목에 `id`, `name`, `area`, `priceLevel`, `openTime`, `closeTime`, `tags`, `hasOutlet`, `hasWifi`, `image` 같은 속성을 둘 수 있음. JavaScript는 이 데이터를 읽어 검색·필터·정렬하고, 사용자가 카드를 선택하면 상세정보를 보여줌

## 2.2 JSON의 역할
JSON은 구조화된 데이터를 텍스트 형태로 표현하는 형식으로, 하나의 항목을 여러 속성으로 설명하고 같은 구조를 가진 여러 항목을 배열로 묶어 관리할 수 있음
카페가 30곳이라면 HTML 카드 30개를 직접 작성하는 대신 카페 데이터 30건을 JSON으로 준비하고 JavaScript가 같은 카드 구조를 반복 생성할 수 있음. 검색·필터·정렬 기능도 화면에 적힌 글자를 직접 찾는 것이 아니라 JSON의 속성을 기준으로 처리
따라서 JSON 설계는 단순한 자료 입력이 아니라 어떤 기능을 구현할 수 있는지 결정하는 서비스 설계 작업임. 지역 필터를 만들려면 `area`, 마감일 순 정렬을 만들려면 일정한 형식의 날짜 필드가 필요함
```json
[
  {
    "id": 1,
    "name": "카페 라온",
    "area": "성수동",
    "priceLevel": 2,
    "hasOutlet": true,
    "hasWifi": true,
    "tags": ["카공", "조용함"]
  }
]
```
**JSON 데이터를 설계할 때 확인할 질문**
- 각 항목을 구분할 `id`가 있는가
- 검색할 텍스트 정보가 있는가
- 필터에 사용할 카테고리나 조건이 있는가
- 정렬할 숫자나 날짜가 있는가
- 상세화면에 보여줄 추가 정보가 있는가
- 모든 항목에서 필드와 자료형이 일관적인가

## 2.3 LocalStorage의 역할
LocalStorage는 웹브라우저가 제공하는 저장공간으로, 사용자가 선택한 값을 서버가 아니라 현재 브라우저에 저장함. 같은 사이트를 다시 열었을 때 저장된 값을 읽어 이전 상태를 복원할 수 있음
카페 7번과 12번을 즐겨찾기했다면 카페 전체 정보를 복사해 저장하기보다 `[7, 12]`처럼 식별자 목록을 저장하는 방식이 적절함. 화면을 다시 열 때 JSON의 기본 데이터와 LocalStorage의 식별자를 연결해 어떤 카드에 즐겨찾기 표시를 보여줄지 결정

## 2.4 JSON과 LocalStorage가 만나는 흐름
JSON과 LocalStorage는 모두 데이터를 다루지만 서로 다른 역할을 담당함. JSON은 서비스가 제공하는 **공통 원본 데이터**, LocalStorage는 사용자가 그 데이터에 대해 만든 **개인 상태**임
두 데이터는 보통 `id`를 기준으로 연결됨. 먼저 JSON에서 기본 목록을 읽고, LocalStorage에서 즐겨찾기 id를 읽은 뒤 JavaScript가 두 값을 결합해 화면을 그림
```javascript
const programs = await fetch('./data/programs.json')
  .then(response => response.json());

const favorites = JSON.parse(localStorage.getItem('favorites')) || [];

programs.forEach(program => {
  const isFavorite = favorites.includes(program.id);
  console.log(program.title, isFavorite);
});
```
**전체 데이터 흐름**
JSON 기본 데이터 → JavaScript 처리 → 화면 출력 → 사용자 행동 → LocalStorage 저장 → 페이지 재방문 시 상태 복원
<callout icon="📌" color="blue_bg">
	LocalStorage에는 기본 데이터 전체를 복사해 넣기보다 사용자가 만든 최소한의 상태를 저장. JSON 원본과 사용자 상태의 역할을 분리해야 검색·필터·상세보기·개인화 기능을 안정적으로 연결할 수 있음
</callout>

## 3.2 프로젝트 유형 탐색
**탐색형 서비스**는 많은 기본 데이터 중 사용자가 조건에 맞는 항목을 검색·필터·정렬해 찾는 구조. 비교과 프로그램, 자격증, 공모전, 전시회, 캠퍼스 시설 탐색처럼 목록을 좁혀 최종 후보를 선택하는 경험이 중심
**추천형 서비스**는 사용자의 조건이나 선택을 입력받아 적합한 기본 데이터를 제시하는 구조. 실제 AI 추천 시스템이 아니라 미리 정한 규칙과 조건을 이용해 결과를 좁히는 방식으로 구현할 수 있음
**기록·관리형 서비스**는 기본 정보와 사용자가 만든 개인 상태를 함께 관리하는 구조. 운동 루틴 완료 체크, 자격증 준비 상태, 식물 관리 체크처럼 한 브라우저 안에서 개인 상태를 관리하는 서비스에 적합
프로젝트의 핵심이 사용자 간 공유·댓글·공동 수정·실시간 상태에 있다면 LocalStorage만으로는 적합하지 않으므로 다른 주제를 선택하거나 심화 기술 적용 여부를 별도로 판단
---
## 3.3 학기 프로젝트 범위
### 3.3.1 필수 트랙
이번 학기의 기본 목표는 HTML·CSS와 JavaScript로 반응형 화면을 만들고, JSON 데이터셋을 검색·복수 필터·정렬·상세보기와 연결하며, LocalStorage로 의미 있는 개인화 기능을 구현한 뒤 실제 URL로 배포하는 것
**프로젝트 범위 확인 기준**
- 최종 데이터 30건 이상을 준비할 수 있는가
- 검색과 복수 필터가 실제로 필요한 주제인가
- 상세화면에서 보여줄 추가 정보가 충분한가
- 즐겨찾기·최근 본 항목·완료 상태·설정 등 개인화 기능을 2\~3가지 이상 연결할 수 있는가
- 모바일에서도 핵심 사용자 흐름을 완료할 수 있는가
- 서버 없이도 필수 사용자 목표를 끝까지 완료할 수 있는가
---
### 3.3.2 심화 트랙
필수 트랙을 먼저 완성한 팀은 프로젝트 목적에 필요한 경우 외부 API, Supabase·Firebase와 같은 클라우드 DB, 간단한 사용자 인증을 선택적으로 적용할 수 있음. 심화 기술은 필수 기능을 대체하는 것이 아니라 프로젝트의 필요에 따라 확장하는 방식으로 사용
<callout icon="🚀" color="purple_bg">
	API나 클라우드 DB를 적용했다는 사실 자체가 높은 평가를 보장하지 않음. 사용자 문제 해결과 서비스 완성도, 안정적인 동작이 우선
</callout>
---
### 3.3.3 공통 제외 및 주의 범위
결제, 실시간 채팅, 복잡한 공동 편집, 상용 수준의 회원 시스템처럼 보안과 서버 구조가 핵심인 기능은 기본 범위에서 제외. 여러 사용자가 같은 최신 상태를 동시에 봐야 하는 게시판·실시간 투표·좌석 예약·공동 할 일 관리 역시 필수 트랙의 LocalStorage만으로 구현하기에 적합하지 않음

# 활동내역 및 산출물
이번 주차에서는 자신이 자주 사용하는 웹서비스 사례를 공유하고, 서비스가 어떤 사용자 문제를 어떤 행동과 데이터로 해결하는지 분석. 분석 결과는 다음 주의 서비스 역분석과 이후 프로젝트 주제 구체화에 이어서 사용
- 웹서비스 사례 분석서 1부 작성
- 사용자, 해결 문제, 핵심 기능, 기본 데이터, 사용자 저장 데이터 항목 포함
- 다음 주 역분석에 사용할 비교 대상 서비스 2개 선정
<callout icon="📦" color="gray_bg">
	매주차 산출물을 개별 제출하지는 않지만 최종 팀프로젝트 완료 시 누적 자료를 취합. 1주차 산출물은 개인 문서에 보관하고 3주차 팀 구성 후 필요한 내용을 팀 프로젝트 문서로 옮겨 지속적으로 관리
</callout>
