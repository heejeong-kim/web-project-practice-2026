# 1. \[이론\] 웹프로젝트 실습의 이해
## 1.1 웹페이지에서 웹서비스로
### 1.1.1 웹페이지와 웹사이트
- 웹페이지는 브라우저에서 사용자가 보는 하나의 문서 또는 화면으로 이해한다.
- 예를 들어 대학 학과 소개 페이지, 카페 소개 페이지, 행사 안내 페이지처럼 특정 정보를 보여주는 하나의 화면이 웹페이지에 해당한다.
- 웹사이트는 여러 웹페이지가 하나의 목적과 정보구조에 따라 연결된 형태로 이해한다.
- 예를 들어 대학 홈페이지는 메인, 학과 소개, 입학 안내, 학사 안내, 공지사항 등의 여러 웹페이지가 메뉴 구조로 연결된 웹사이트이다.
- 정적 웹페이지는 작성된 HTML 콘텐츠를 그대로 보여주는 성격이 강하며 사용자의 행동에 따라 데이터 자체가 크게 달라지지 않는다.
- 페이지 수가 많다고 해서 자동으로 웹서비스가 되는 것은 아니다.
- 회사 소개 사이트처럼 수십 개의 페이지가 있어도 대부분의 사용자가 정보를 읽는 것이 중심이면 정보 제공형 웹사이트에 가깝다.
- 반대로 한 화면만 있어도 사용자가 검색 조건을 선택하고 결과가 바뀌며 선택 상태를 저장할 수 있다면 웹서비스의 성격을 가질 수 있다.

### 1.1.2 웹서비스
- 웹서비스는 사용자가 특정 목적을 달성할 수 있도록 정보, 기능, 데이터, 상호작용이 연결된 형태로 이해한다.
- 웹서비스에서 중요한 것은 화면 자체보다 사용자가 무엇을 하려고 들어왔고 어떤 행동을 거쳐 목표를 완료하는가이다.
- 검색, 필터, 비교, 정렬, 상세보기, 저장, 추천과 같은 행동은 사용자가 많은 정보 중 자신에게 필요한 결과를 찾도록 돕는다.
- 예를 들어 배달 서비스의 목적은 음식 사진을 보여주는 것이 아니라 사용자가 현재 상황에 맞는 식당과 메뉴를 찾아 주문 후보를 결정하도록 돕는 데 있다.
- 지도 서비스의 목적도 지도를 보여주는 것 자체보다 장소를 검색하고 조건을 비교해 이동할 목적지를 결정하도록 돕는 데 있다.
- 웹서비스는 보통 사용자의 입력 또는 선택을 받고 데이터를 처리한 뒤 그 결과를 다시 화면에 보여주는 흐름을 가진다.
- 사용자가 같은 화면에 들어오더라도 검색어, 필터 조건, 선택 상태가 다르면 서로 다른 결과를 볼 수 있다.
- 이러한 변화가 가능한 이유는 화면에 모든 정보를 고정해두는 것이 아니라 데이터를 별도로 관리하고 JavaScript가 필요한 결과를 선택해 보여주기 때문이다.

### 1.1.3 웹서비스를 바라보는 네 가지 질문
- 웹서비스를 분석할 때 화면의 색상이나 디자인부터 보지 않고 사용자, 문제, 행동, 데이터의 네 가지 질문부터 확인한다.
- 첫 번째 질문은 누가 사용하는가이다.
- 대학생처럼 넓은 표현보다 공강 시간에 참여할 비교과 프로그램을 찾는 1학년 학생처럼 상황과 목적이 드러나게 표현한다.
- 두 번째 질문은 무엇을 해결하는가이다.
- 검색 기능이 필요하다처럼 기능으로 작성하지 않고 정보가 여러 곳에 흩어져 있어 자신에게 맞는 프로그램을 빠르게 찾기 어렵다처럼 사용자의 불편을 작성한다.
- 세 번째 질문은 어떤 행동을 할 수 있는가이다.
- 사용자가 검색하고 필터하고 비교하고 상세정보를 확인하고 관심 항목을 저장하는 흐름을 실제 행동 순서로 살펴본다.
- 네 번째 질문은 어떤 데이터를 사용하는가이다.
- 화면에서 반복되는 제목, 카테고리, 일정, 장소, 이미지, 설명과 같은 기본 데이터를 찾아본다.
- 동시에 즐겨찾기 여부, 최근 본 항목, 개인 설정처럼 사용자마다 달라지는 상태도 구분한다.

### 정적 페이지인지 서비스인지 판단해보기
- 학과 소개 페이지에서 교육목표와 교수진을 읽는다면 정적 정보 제공의 성격이 강하다.
- 학과 교과목 100개 중 학년, 전공영역, 요일을 선택해 과목을 좁혀본다면 데이터 기반 서비스의 성격이 강하다.
- 음식점 소개 페이지에서 메뉴 10개를 HTML에 직접 작성했다면 콘텐츠가 많아도 정적 페이지에 가깝다.
- 메뉴 데이터를 별도로 관리하고 가격대, 카테고리, 알레르기 조건으로 결과를 바꿀 수 있다면 서비스로 확장된다.

### 1.3.2 카페 탐색 서비스
- 카페 탐색 서비스는 여러 카페 중 사용자의 조건에 맞는 카페를 찾도록 돕는 것이 목적이다.
- 예를 들어 학교 근처에서 공부하기 좋은 카페를 찾는 대학생을 핵심 사용자로 가정한다.
- 최종 프로젝트 기준으로는 30건 이상의 카페 데이터를 준비하고 각 카페마다 id, name, area, priceLevel, openTime, closeTime, tags, hasOutlet, hasWifi, image 등의 속성을 둘 수 있다.
- 사용자가 성수동, 콘센트 있음, 와이파이 있음, 가격대 보통을 선택하면 JavaScript가 전체 카페 데이터에서 조건에 맞는 항목만 다시 화면에 표시한다.
- 사용자가 카공이라는 검색어를 입력하면 이름이나 태그에 해당 단어가 포함된 카페만 보여줄 수 있다.
- 사용자가 가격 낮은 순을 선택하면 같은 데이터의 표시 순서를 바꿀 수 있다.
- 특정 카페를 선택하면 목록에서는 보이지 않던 상세 설명, 대표 메뉴, 이용 팁, 위치 정보를 상세화면에서 보여줄 수 있다.
- 마음에 드는 카페의 id를 LocalStorage에 저장하면 브라우저를 다시 열어도 즐겨찾기 상태를 유지할 수 있다.
- 최근 본 카페의 id를 저장하면 최근 본 카페 영역도 만들 수 있다.
- 이처럼 하나의 데이터셋을 검색·필터·정렬·상세보기·즐겨찾기와 연결하면 웹페이지가 데이터 기반 웹서비스로 확장된다.

## 2.1 웹서비스를 세 개의 층으로 이해하기
### 2.1.1 화면
- 화면은 사용자가 서비스를 보고 조작하는 접점으로 이해한다.
- HTML은 제목, 검색창, 필터, 카드 목록, 상세 영역처럼 정보의 구조를 만든다.
- CSS는 화면의 배치, 크기, 간격, 반응형 구조와 시각적 표현을 담당한다.
- JavaScript는 사용자가 검색하거나 필터를 선택했을 때 어떤 결과를 보여줄지 결정하고 화면 내용을 변경한다.
- 예를 들어 카페 탐색 서비스의 HTML에는 검색창과 결과 영역이 존재하지만 실제 카페 30개의 카드가 HTML에 미리 작성될 필요는 없다.
- JavaScript가 데이터 30개를 읽고 필요한 항목을 카드 형태로 만들어 결과 영역에 표시할 수 있다.
- 따라서 화면은 데이터를 보관하는 곳이라기보다 데이터를 사용자에게 보여주고 행동을 입력받는 인터페이스로 보는 것이 적절하다.

### 2.1.2 기본 데이터
- 기본 데이터는 서비스를 처음 실행했을 때 이미 준비되어 있으며 여러 사용자에게 공통으로 제공되는 원천 데이터로 이해한다.
- 카페 탐색 서비스라면 카페명, 지역, 가격대, 운영시간, 편의시설, 이미지, 설명 등이 기본 데이터에 해당한다.
- 비교과 프로그램 서비스라면 프로그램명, 분야, 대상 학년, 신청기간, 운영일정, 장소, 담당부서 등이 기본 데이터에 해당한다.
- 이러한 정보는 특정 사용자가 즐겨찾기를 눌렀다고 해서 내용 자체가 바뀌지 않는다.
- 이번 학기에는 팀원이 함께 관리해야 하는 기본 데이터셋을 JSON 파일로 구성한다.
- JSON 파일은 프로젝트 폴더에 포함해 GitHub로 공유할 수 있으므로 모든 팀원이 같은 기본 데이터를 기준으로 개발할 수 있다.
- 기본 데이터에는 검색과 필터에 사용할 속성이 충분히 포함되어야 한다.
- 예를 들어 지역 필터를 만들 예정인데 데이터에 지역 항목이 없다면 필터를 구현할 수 없다.
<callout icon="💡" color="yellow_bg">
	- 화면을 설계한 뒤 어떤 정보를 보여줄지만 생각하지 말고 어떤 기능으로 데이터를 찾고 비교할 것인지까지 생각해야 필요한 필드를 설계할 수 있다.
</callout>

### 2.1.3 사용자 데이터
- 사용자 데이터는 서비스를 이용하면서 사용자의 행동에 의해 만들어지거나 변경되는 개인 상태로 이해한다.
- 즐겨찾기, 최근 본 항목, 완료 여부, 선택한 보기 방식, 개인 메모 등이 대표적인 예이다.
- 같은 기본 데이터를 보더라도 사용자 A와 사용자 B의 즐겨찾기 목록은 서로 다를 수 있다.
- 이번 학기에는 로그인이나 서버 데이터베이스를 구현하지 않으므로 이러한 개인 상태를 LocalStorage에 저장한다.
- LocalStorage에 저장된 값은 해당 브라우저와 사이트를 기준으로 보관되므로 다른 팀원의 브라우저와 자동으로 공유되지 않는다.
- 따라서 LocalStorage를 팀 프로젝트의 공동 데이터 저장소나 서버 데이터베이스처럼 사용하지 않는다.
- 팀원이 함께 관리해야 하는 카페 목록, 프로그램 목록, 장소 목록은 JSON에 둔다.
- 사용자가 개인적으로 선택한 즐겨찾기, 최근 본 항목, 설정 값만 LocalStorage에 둔다.

## 2.2 JSON의 역할
### 2.2.1 JSON 기본 개념
- JSON은 구조화된 데이터를 텍스트 형태로 표현하는 형식으로 이해한다.
- 하나의 항목을 여러 속성으로 설명하고, 같은 구조를 가진 여러 항목을 배열로 묶어 관리할 수 있다.
- 예를 들어 카페 한 곳을 이름, 지역, 가격대, 운영시간, 콘센트 여부와 같은 여러 속성으로 표현할 수 있다.
- 카페가 30곳이라면 같은 속성 구조를 가진 데이터 30건을 하나의 목록으로 관리할 수 있다.
- 데이터와 HTML을 분리하면 HTML 카드 30개를 직접 작성하지 않고 JavaScript가 데이터 개수만큼 같은 카드 구조를 반복 생성할 수 있다.
- 검색, 필터, 정렬 기능은 화면의 글자를 직접 찾는 것이 아니라 이러한 구조화된 데이터의 속성을 기준으로 처리한다.
- 따라서 JSON 데이터 설계는 단순한 자료 입력 작업이 아니라 이후 구현할 기능의 기반을 만드는 작업이다.
### JSON 데이터를 볼 때 확인할 질문
- 각 항목을 서로 구분할 수 있는 식별자가 있는가
- 검색할 텍스트 정보가 있는가
- 필터에 사용할 카테고리나 조건 정보가 있는가
- 정렬할 수 있는 숫자나 날짜 정보가 있는가
- 상세화면에서 추가로 보여줄 정보가 있는가
- 모든 데이터가 동일한 필드 구조와 자료형을 사용하고 있는가
---

```json
[
  {
    "id": 1,
    "title": "AI 기초 특강",
    "category": "전공",
    "target": "1학년",
    "location": "공학관 201호"
  }
]
```

## 2.3 LocalStorage의 역할
### 2.3.1 저장 방식
- LocalStorage는 웹브라우저가 제공하는 Web Storage 기능 중 하나로 이해한다.
- 사용자가 선택한 값을 서버가 아니라 현재 브라우저에 저장한다.
- 같은 사이트를 다시 열었을 때 저장된 값을 읽어 이전 상태를 복원할 수 있다.
- 예를 들어 카페 7번과 12번을 즐겨찾기했다면 해당 카페 전체 정보를 복사해 저장하기보다 즐겨찾기한 식별자 목록을 저장하는 방식으로 설계할 수 있다.
- 화면을 다시 열 때 JSON에서 7번과 12번 카페를 찾아 즐겨찾기 상태를 표시한다.
- 이 방식은 서비스의 기본 데이터와 사용자의 개인 상태를 분리한다는 장점이 있다.
- LocalStorage는 브라우저와 기기별로 독립적으로 저장되므로 팀원 A가 저장한 즐겨찾기가 팀원 B의 컴퓨터에 나타나지 않는다.
- 브라우저 데이터를 삭제하거나 다른 브라우저를 사용하면 저장 상태가 달라질 수 있다.
- 따라서 발표 전에는 초기 상태와 저장된 상태를 모두 테스트한다.
---
### 2.3.2 프로젝트에서의 활용 범위
- 즐겨찾기 항목을 저장해 사용자가 다시 찾기 쉽게 한다.
- 최근 본 항목을 저장해 이전에 확인한 정보를 빠르게 다시 열 수 있게 한다.
- 학습 콘텐츠나 운동 루틴처럼 완료 여부가 필요한 서비스에서는 체크 상태를 저장할 수 있다.
- 정렬 방식, 카드 보기 방식, 다크모드처럼 사용자 설정을 저장할 수 있다.
- 간단한 개인 메모를 저장할 수 있지만 여러 사용자가 함께 수정해야 하는 게시글이나 댓글 데이터로 사용하지 않는다.
- 개인정보, 로그인 정보, 비밀번호와 같은 민감정보는 저장하지 않는다.

### 한 가지 서비스에서 두 데이터가 만나는 예

- 사용자가 프로그램 4번과 15번을 관심 프로그램으로 선택한다.
- 프로그램 자체의 정보는 JSON에 그대로 유지한다.
- LocalStorage에는 사용자가 선택한 4번과 15번이라는 상태만 저장한다.
- 화면을 다시 그릴 때 JavaScript가 JSON 기본 데이터와 LocalStorage의 선택 상태를 연결한다.

## 2.5 실습｜서비스 데이터 구분하기
### 2.5.1 프로젝트 유형 이해 및 선택
- 프로젝트 유형을 먼저 이해한 뒤 자신의 아이디어와 가장 가까운 유형을 선택한다.
- 탐색형 서비스는 여러 기본 데이터 중에서 검색, 필터, 정렬, 비교를 통해 원하는 항목을 찾는 구조이다.
- 예를 들어 공모전 탐색, 비교과 프로그램 탐색, 장학금 탐색, 자격증 탐색 서비스가 해당한다.
- 추천형 서비스는 사용자가 선택한 조건이나 선호에 따라 적합한 기본 데이터를 좁혀 제안하는 구조이다.
- 예를 들어 운동 종목 추천, 취미 클래스 추천, 식물 추천, 디지털 도구 추천 서비스가 해당한다.
- 기록·관리형 서비스는 기본 데이터와 사용자의 개인 상태를 함께 사용해 진행 여부나 선택 기록을 관리하는 구조이다.
- 예를 들어 운동 루틴 완료 체크, 자격증 준비 상태 관리, 식물 관리 체크, 관심 활동 관리 서비스가 해당한다.

- 탐색형은 많은 데이터 중 조건에 맞는 항목을 찾는 데 초점을 둔다.
- 추천형은 사용자의 조건이나 선택을 입력받아 적합한 항목을 좁혀 제안하는 데 초점을 둔다.
- 기록·관리형은 기본 데이터와 사용자가 저장한 상태를 함께 보여주는 데 초점을 둔다.
- 선택한 유형을 한 문장으로 설명하고 사용자가 무엇을 완료하면 서비스 이용이 끝나는지 작성한다.
- 예시｜공모전 탐색 서비스에서 사용자가 자신의 전공과 지원 대상에 맞는 공모전 3개를 찾아 관심 목록에 저장한다.

### 2.5.2 기본 데이터 찾기
- 서비스가 모든 사용자에게 공통으로 제공해야 하는 데이터 항목을 5개 이상 작성한다.
- 화면에 보여줄 정보뿐 아니라 검색, 필터, 정렬에 필요한 데이터도 포함한다.
- 예를 들어 공모전 서비스라면 제목, 주최기관, 분야, 지원대상, 마감일, 시상내역, 이미지, 상세설명 등을 생각할 수 있다.
- 분야 필터를 만들 예정이라면 분야 데이터가 반드시 있어야 한다.
- 마감 임박 순 정렬을 만들 예정이라면 마감일 데이터가 일정한 형식으로 존재해야 한다.
- 데이터 항목을 정한 뒤 각 항목이 모든 데이터에서 같은 의미와 형식으로 사용될 수 있는지 확인한다.

### 2.5.3 사용자 데이터 찾기
- 사용자의 행동에 따라 달라지는 개인 상태를 3개 이상 작성한다.
- 사용자가 다음에 다시 방문했을 때 유지되면 실제로 편리한 상태인지 판단한다.
- 즐겨찾기, 최근 본 항목, 완료 상태, 보기 설정 등이 대표적인 후보이다.
- 단순히 저장 기능을 늘리기 위해 의미 없는 값을 추가하지 않는다.
- 서비스의 핵심 사용자 행동과 연결되는 상태를 우선한다.
- 예를 들어 공모전 탐색 서비스에서는 관심 공모전, 최근 본 공모전, 선택한 분야 필터를 저장할 수 있다.
- 반면 전체 공모전 목록 자체를 LocalStorage에 복사해 저장하는 것은 역할 분리가 잘못된 설계이다.
### 판단 질문
- 이 값은 사용자마다 달라지는가
- 브라우저를 다시 열었을 때 유지되면 유용한가
- 다른 사용자의 값과 공유할 필요가 없는가
- 기본 데이터 전체를 중복 저장하지 않고 식별자나 상태만 저장할 수 있는가
---
### 2.5.4 데이터 흐름 작성
- JSON 기본 데이터 → JavaScript 처리 → 화면 출력 → 사용자 행동 → LocalStorage 저장의 흐름으로 정리한다.
- 각 화살표에서 실제로 어떤 일이 일어나는지 자신의 서비스 예시로 설명한다.
- 예를 들어 공모전 서비스에서는 JSON의 공모전 30건을 JavaScript가 읽고 전체 목록을 화면에 표시한다.

- 사용자가 특정 공모전을 관심 목록에 저장하면 해당 공모전의 식별자가 LocalStorage에 저장된다.

### 3.1.3 핵심 사용자 분석

- 서비스를 자주 사용하는 사용자와 가끔 사용하는 사용자의 목적이 다르다면 핵심 사용자를 먼저 선정한다.

- 상황｜저녁 수업이 끝난 뒤 3시간 정도 과제를 해야 함
- 목적｜늦게까지 운영하며 콘센트와 와이파이가 있는 카페를 찾고 싶음
- 행동 특성｜모바일로 여러 장소를 빠르게 비교하고 마음에 드는 후보를 저장함
- 제약 조건｜도보 15분 이내, 1인 음료 가격 6,000원 이하를 선호함

### 3.1.4 핵심 행동 분석
- 사용자가 서비스에 접속한 뒤 목표를 달성하기까지의 행동을 최소 5단계로 작성한다.
- 접속 → 검색 → 필터 → 비교 → 상세보기 → 저장처럼 실제 흐름으로 정리한다.
- 화면 이름만 나열하지 않고 사용자가 무엇을 판단하고 선택하는지 행동 중심으로 작성한다.
- 예를 들어 카페 탐색 서비스라면 다음과 같이 작성할 수 있다.
- 1단계｜학교 근처 카페 목록을 확인한다.
- 2단계｜운영시간과 콘센트 조건을 선택한다.
- 3단계｜조건에 맞는 결과 중 가격과 거리를 비교한다.
- 4단계｜후보 카페의 상세정보를 확인한다.
- 5단계｜방문 후보를 즐겨찾기에 저장한다.
- 6단계｜즐겨찾기 목록에서 최종 방문 장소를 다시 확인한다.
- 핵심 행동 흐름을 작성하면 이후 필요한 화면, 기능, 데이터가 자연스럽게 도출된다.

## 3.2 프로젝트 유형 탐색
### 3.2.1 탐색형 서비스
- 여러 기본 데이터 중 사용자가 조건에 맞는 항목을 검색·필터·정렬해 찾는 구조로 이해한다.
- 데이터의 개수와 속성이 충분해야 탐색 기능이 의미를 가진다.
- 예시 주제로는 비교과 프로그램, 자격증, 공모전, 전시회, 캠퍼스 시설 탐색 등이 있다.
- 핵심 기능은 목록 보기, 검색, 복수 필터, 정렬, 상세보기, 관심 항목 저장 등으로 구성할 수 있다.
- 사용자가 결과를 좁혀 최종 후보를 선택하는 과정이 서비스의 핵심 경험이 된다.
---
### 3.2.2 추천형 서비스
- 사용자의 조건이나 선택을 입력받아 적합한 기본 데이터를 제시하는 구조로 이해한다.
- 실제 인공지능 추천 시스템을 구현하는 것이 아니라 미리 정의한 규칙과 조건을 이용해 결과를 좁히는 방식으로 구현할 수 있다.
- 예를 들어 운동 종목 추천 서비스에서는 운동 목적, 가능한 시간, 선호 장소, 난이도를 선택하면 조건에 맞는 운동을 보여줄 수 있다.
- 식물 추천 서비스에서는 채광, 물주기 빈도, 관리 난이도 조건을 이용할 수 있다.
- 추천 결과만 보여주지 않고 왜 이 결과가 선택되었는지 사용자가 이해할 수 있게 조건 정보를 함께 보여주는 것이 좋다.
---
### 3.2.3 기록·관리형 서비스
- 기본 정보와 사용자가 만든 개인 기록 또는 상태를 함께 관리하는 구조로 이해한다.
- 수업에서는 여러 사용자가 공유하는 업무 관리 도구보다 한 브라우저 안에서 개인 상태를 관리하는 서비스에 적합하다.
- 예를 들어 운동 루틴 서비스는 JSON에 운동 목록을 두고 LocalStorage에 사용자의 완료 여부와 즐겨찾기 상태를 저장할 수 있다.
- 식물 관리 서비스는 JSON에 식물별 관리 정보를 두고 LocalStorage에 사용자가 관심 있는 식물과 관리 체크 상태를 저장할 수 있다.
- 프로젝트의 핵심이 사용자 간 공유, 댓글, 공동 수정에 있다면 LocalStorage만으로는 적합하지 않으므로 다른 주제를 선택한다.
---
## 3.3 학기 프로젝트 범위 확인
### 3.3.1 필수 트랙｜이번 학기 구현 범위
- HTML·CSS 기반으로 서비스의 주요 화면과 반응형 레이아웃을 구성한다.
- JavaScript로 사용자의 입력과 행동을 처리하고 화면을 동적으로 변경한다.
- JSON 기본 데이터셋을 활용해 반복되는 목록과 상세정보를 생성한다.
- 검색 기능을 구현해 제목이나 설명 등 필요한 필드를 찾을 수 있게 한다.
- 두 개 이상의 조건을 조합하는 필터 기능을 구현한다.
- 이름, 날짜, 가격, 난이도 등 프로젝트에 적합한 기준으로 정렬 기능을 구현한다.
- 목록에서 선택한 항목의 상세정보를 확인할 수 있게 한다.
- 검색 결과가 없거나 데이터가 비어 있는 경우의 안내 상태를 구현한다.
- LocalStorage로 즐겨찾기, 최근 본 항목, 완료 상태, 사용자 설정 등 프로젝트에 의미 있는 개인화 기능을 구현한다.
- JSON 기본 데이터와 LocalStorage 사용자 상태를 결합한 화면을 최소 하나 이상 만든다.
- 모바일 화면에서도 핵심 사용자 흐름을 완료할 수 있도록 구성한다.
- GitHub Pages, Netlify, Vercel 등 정적 호스팅을 이용해 실제 URL로 배포한다.
### 범위를 판단하는 기준
- 최종 데이터가 30건 이상 준비될 수 있는가
- 검색과 복수 필터가 실제로 필요한 주제인가
- 상세화면에서 추가로 보여줄 정보가 충분한가
- 개인화 상태를 최소 2\~3가지 연결할 수 있는가
- 서버 없이도 핵심 사용자 목표를 끝까지 완료할 수 있는가
---
### 3.3.2 심화 트랙｜선택 구현 범위
- 필수 트랙을 먼저 완성한 팀이 프로젝트 목적에 필요할 때 선택하여 적용한다.
- 외부 API를 연결해 공공데이터, 실시간 정보, 외부 서비스 데이터를 불러올 수 있다.
- Supabase 또는 Firebase와 같은 클라우드 데이터베이스 서비스를 연결해 여러 브라우저에서 공유되는 데이터를 구성할 수 있다.
- 프로젝트 필요에 따라 간단한 사용자 인증 기능을 적용할 수 있다.
- 필수 트랙의 정적 배포를 완료한 뒤 필요하면 환경 변수, 외부 API, 클라우드 DB가 포함된 배포 환경으로 확장할 수 있다.
- 심화 기술을 많이 사용하는 것보다 서비스 문제 해결에 필요한 기술을 적절하게 선택하는 것을 우선한다.
- 심화 트랙은 필수 트랙의 검색·필터·상세보기·개인화 기능을 대체하지 않고 확장하는 방식으로 적용한다.
<callout icon="🚀" color="purple_bg">
	- 심화 트랙은 선택 사항이며 적용하지 않아도 필수 트랙을 충실하게 완성하면 프로젝트를 정상적으로 수행할 수 있다.
	- API와 클라우드 DB를 적용한 것 자체가 높은 평가를 보장하지 않으며 사용자 문제 해결과 완성도를 중심으로 평가한다.
</callout>

### 3.3.3 공통 제외 및 주의 범위
- 결제 기능은 구현하지 않는다.
- 실시간 채팅과 복잡한 공동 편집 기능은 구현하지 않는다.
- 보안과 개인정보 처리가 필요한 실제 상용 수준의 회원 시스템은 구현하지 않는다.
- 심화 트랙에서 인증을 적용하는 경우 학습용 최소 범위로 제한한다.
- API 키, 비밀키, 관리자 권한 키 등 공개하면 안 되는 값은 클라이언트 코드나 GitHub 저장소에 직접 노출하지 않는다.
- 클라우드 DB를 사용할 경우 공개 쓰기 권한을 무제한으로 열어두지 않고 서비스의 보안 규칙을 확인한다.
- 사용자가 작성한 게시글과 댓글을 여러 기기에서 공유해야 하는 커뮤니티형 서비스는 제외한다.
- 판매자가 상품을 등록하고 구매자가 동시에 확인해야 하는 실제 중고거래 구조는 제외한다.
- 여러 팀원이 같은 일정이나 할 일을 실시간으로 수정해야 하는 협업 서비스는 제외한다.
- 실시간 투표 결과, 예약 가능 좌석, 재고 수량처럼 모든 사용자가 같은 최신 상태를 봐야 하는 기능은 제외한다.
